Scope and problem framing

Support one-to-one and group conversations over long-lived connections, multi-device history sync, offline delivery, presence and receipts without pretending one global order exists.

Requirements

Functional requirements

  • Send a message into a conversation and assign it a monotonic per-conversation sequence, so that ordering is a property of the store rather than of arrival time.
  • Deliver to every online device over a persistent connection, and leave a durable trail that an offline device can catch up from by sequence.
  • Track delivered and read cursors per device, and reconcile them when the same account is signed in on several devices at once.
  • Support group conversations, history pagination, and push notification for devices with no live connection.

Quality attributes

  • A message that the sender saw acknowledged must never disappear. Acknowledgement means persisted and sequenced, not accepted into a buffer.
  • Ordering within a conversation is total and stable; ordering across conversations is not, and promising it is how a chat system acquires a global sequencer it does not need.
  • A reconnect must be cheap and incremental:the client sends its last sequence and receives the delta, never the conversation.
  • The fan-out path may lag under load; the persist-and-sequence path may not, because it is what makes the message recoverable at all.

Capacity and constraints

  • Size the system by message peak with the daily volume beside it: ~25 rps peak (100k messages/day) at T2, ~250 rps peak (1M/day) at T3, ~25,000 rps peak (100M/day) at T4. Chat is consumer traffic with evening peaks, so plan 10–20× the average and expect a reconnect storm to exceed even that.
  • Concurrent sockets, not message rate, is what sizes the gateway tier. At T3 a few hundred thousand concurrent connections is normal, and a connection costs memory and a file descriptor whether or not anyone is typing.
  • Group size drives delivery amplification:one message to a 500-member group is 500 delivery attempts, so a modest message rate in large groups outweighs a high message rate in one-to-one chats. Model the two separately.
  • Judge a separate presence service per tier:not needed at T1 and T2, where presence can ride the connection state on the gateway itself; worth it at T3, where presence fan-out starts to compete with message fan-out for the same sockets; mandatory once presence updates outnumber messages, which happens earlier than teams expect; needs its own scaling story at T4, where presence is a higher-volume, lower-value stream than chat and must be shed first.
  • Budget the reconnect storm explicitly:if a gateway holding 100k connections dies, those clients reconnect within seconds and each asks for a delta. That is the real peak, and it is what the catch-up query and the connection handshake must be sized for.
  • History storage grows without bound and is read almost never. Keep the recent window on fast storage and move the tail to cheaper storage on an explicit schedule, rather than letting one table carry both access patterns.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Conversation and membership

participants, roles, a membership version and the last sequence each member is entitled to read from. The version is what makes "who was in the group when this was sent" answerable.

02Message

conversation id as the partition key with sequence as the clustering key, plus sender, a client-supplied idempotency id, content reference and server time. The sequence is assigned by the server, never by the client clock.

03Device cursor

user and device, delivered sequence, read sequence and last sync state. Per device rather than per user, because the same account catching up on a phone and a laptop are two independent positions.

04Outbox or delivery log

pending deliveries by device, so a device that was offline at send time is served by the same mechanism as one that was merely slow.

05Attachment reference

content id, size, type and lifecycle, kept out of the message row so that history pagination never drags media bytes through the hot path.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01Stateless WebSocket gateways with a session registry

the gateway holds the socket, the registry maps device to gateway. Keeping routing state out of the gateway is what lets a gateway die without taking its conversations with it.

02The sequencer is the heart of…

The sequencer is the heart of the design and it is per conversation, not global. A per-partition counter or a conditional write on (conversation_id, seq) gives total order where it is needed and avoids a single global bottleneck.

03Wide-column store for messages, partitioned by…

Wide-column store for messages, partitioned by conversation with sequence as the clustering key. History pagination is then a bounded range scan inside one partition, which is the access pattern these stores are built for.

04A log or queue between persist…

A log or queue between persist and fan-out so that delivery is retried independently of the send acknowledgement, and a slow device cannot hold a sender's request open.

05Push notification as a distinct downstream…

Push notification as a distinct downstream with its own rate limits and its own failure mode, not an inline call inside delivery. Provider throttling must never become send latency.

06Observability

sockets per gateway, sequence assignment latency, delivery lag by group size bucket, catch-up query duration at p99, redelivery rate, and reconnects per minute against the storm budget.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

Sequence a message without a global counter

The conditional insert is what makes the sequence total per conversation. Two concurrent senders race, one loses, and the loser retries with the next sequence rather than corrupting the order.

sql
CREATE TABLE message (
  conversation_id  bigint,
  seq              bigint,        -- server-assigned, monotonic per conversation
  sender_id        bigint,
  client_msg_id    uuid,          -- dedup key from the client
  body_ref         text,
  sent_at          timestamp,
  PRIMARY KEY ((conversation_id), seq)
) WITH CLUSTERING ORDER BY (seq DESC);

-- dedup first: a retried send must return the original sequence
SELECT seq FROM message_by_client_id
WHERE conversation_id = :cid AND client_msg_id = :client_msg_id;

-- then claim the next sequence; IF NOT EXISTS makes the race safe
INSERT INTO message (conversation_id, seq, sender_id, client_msg_id, body_ref, sent_at)
VALUES (:cid, :next_seq, :sender, :client_msg_id, :body_ref, :now)
IF NOT EXISTS;

Catch up by delta, never by conversation

Abridged. The cap is the important line: an unbounded catch-up is what turns a reconnect storm into an outage of the store rather than of the gateway.

java
void onReconnect(Session session, long conversationId, long lastSeenSeq) {
    // the client states its position; the server never guesses it from a timestamp
    long head = sequences.head(conversationId);

    if (head - lastSeenSeq > CATCH_UP_LIMIT) {
        // too far behind to stream: hand back a snapshot pointer and let the
        // client paginate history instead of replaying a million messages
        session.send(new ResyncRequired(conversationId, head));
        return;
    }

    for (Message m : messages.range(conversationId, lastSeenSeq + 1, head)) {
        session.send(m);
    }
    cursors.markDelivered(session.deviceId(), conversationId, head);
}

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
A per-conversation sequence gives total order…

A per-conversation sequence gives total order cheaply and gives up cross-conversation ordering. A global sequencer buys that back and becomes the bottleneck for every message in the system; almost no chat product needs it.

02
Client-generated ids make send idempotent and…

Client-generated ids make send idempotent and retry-safe, but they cannot be trusted for ordering. Accept the id for deduplication and assign the sequence on the server, or a client with a skewed clock reorders a conversation for everyone.

03
Fan-out on send is simple until…

Fan-out on send is simple until groups get large; a pull-on-read model scales with group size but makes the common one-to-one case slower. Splitting the strategy by group size is the same hybrid decision the feed design makes.

04
Read receipts are a product feature…

Read receipts are a product feature with a fan-out cost that can exceed messages themselves in large groups. Per-message receipts in a 500-member group is a 500× amplification for information most users never look at.

05
Storing every delivery attempt makes debugging…

Storing every delivery attempt makes debugging easy and the delivery log enormous. Bound it by retention rather than by count, and accept that a very old undelivered message is dropped rather than kept forever.

06
Encrypting message content end to end…

Encrypting message content end to end removes the server's ability to search, moderate and re-render history. That is a product decision with a permanent architectural consequence, and it must be made before the first message is stored.

Failure review — answers for this design
01

Which invariant can break?

An acknowledged message must be readable at a stable position in its conversation, exactly once. It breaks when a client id is accepted twice and produces two sequences, and when a delivery is retried without the receiver deduplicating — one shows the sender their message twice, the other shows the receiver.

02

Which metric detects it first?

Reconnects per minute and catch-up query duration, watched together. A gateway loss shows first as a reconnect spike, and the damage shows as catch-up p99 climbing — long before message latency moves, because sends are still fine while reads are collapsing.

03

How is the blast radius contained?

Gateways are stateless and hold no conversation state, so losing one costs a reconnect rather than data. Catch-up is capped per session, push notification is a separate downstream with its own limits, and presence can be shed independently of messages.

04

Can retry duplicate or reorder work?

Yes on both counts.

  • Send retries are deduplicated by the client message id, which is why that id must be generated once per message and not once per attempt.
  • Delivery retries can arrive out of order, which is harmless because the client sorts by sequence rather than by receipt.
05

How do we repair and prove recovery?

Rebuild device cursors from the delivery log and let clients resync by sequence — the message store is the source of truth and is never rewritten. Recovery is proven when catch-up p99 is back inside budget, the reconnect rate is at baseline, and a sampled set of conversations shows no sequence gap and no duplicate client message id.

Engineering deep dives

Asynchronous delivery and replay

Moving work off the request path trades immediate failure for lag, duplicates, ordering constraints and operational backlog.

Define delivery semantics

  • Assume at-least-once at service boundaries. Give each event a stable ID, partition key, schema version and event time; make every side effect idempotent.
  • Guarantee order only within the business entity that needs it. Global order limits parallelism and usually encodes no useful invariant.

Treat lag as user impact

  • Observe oldest-message age, input/output rate, retry count, poison messages and partition skew. Queue depth alone hides slow old work behind new small messages.
  • Use retry topics or delayed queues with expiry and a DLQ; DLQ is not resolution until it has ownership, alerting and a safe replay tool.

Evolve safely

  • Use backward/forward-compatible schemas and tolerant readers. Deploy consumers before producers when adding fields and preserve raw events for bounded replay.
  • Replay into an isolated output or shadow consumer first; throttle it so historical traffic cannot starve live processing or repeat external effects.

Observability and security review

Instrumentation should explain user impact and the responsible dependency without leaking identity or creating unbounded telemetry cost.

Start from user SLIs

  • Define success, latency, freshness and correctness SLIs at the system boundary; alert on error-budget burn, then use dependency metrics for diagnosis.
  • Correlate traces, metrics and structured logs with trace/span IDs. Preserve request, policy and schema versions but redact secrets and sensitive payloads.

Keep telemetry bounded

  • Never use user ID, object ID or raw URL as a metric label. Use logs/traces for high-cardinality detail and explicitly monitor cardinality overflow.
  • Sample by value: retain errors, slow paths and rare business failures at higher rates while keeping predictable storage and query cost.

Review the trust boundary

  • Authorize the object and action on every request, use least-privilege service identities and short-lived credentials, encrypt in transit/at rest and audit privileged changes.
  • Threat-model abuse, replay, enumeration, tenant crossover and data retention. Security controls need degraded behavior and recovery drills like every other dependency.

Define ordering before choosing storage: most chat systems promise accepted order within one conversation, not one global order across all conversations.

▸ DEEP DIVE · SENIOR
  • assign a durable per-conversation sequence through one partition owner or sequencer. A Kafka partition keyed by conversation can preserve append order, while idempotent client message IDs prevent duplicate submission.
  • model Cassandra partitions with a bounded key such as conversation ID plus time bucket, and cluster by sequence or timeuuid. An unbounded partition keyed only by conversation eventually becomes hot and hard to repair.
  • separate connection gateways from durable message handling. Keep a user/device-to-gateway registry, deliver through durable logs or queues, and retain per-device sync cursors for offline catch-up.
  • define at-least-once delivery, duplicate handling, read/delivery receipt semantics, retention, and multi-device synchronization. Bound slow consumers with queues, deadlines, and disconnect or catch-up policy.
  • large groups need hybrid fan-out and backpressure, not one broadcast loop. E2E encryption also removes server-side search, preview, and content moderation capabilities while leaving metadata and device/key management concerns.
