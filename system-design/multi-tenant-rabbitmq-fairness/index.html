Fair multi-tenant work scheduling with RabbitMQ

Users submit URLs into a multi-stage worker pipeline. Tenant A can enqueue 1,000 jobs while tenant B submits one latency-sensitive job. The goal is bounded wait and predictable resource share without creating one queue and consumer per tenant. RabbitMQ remains the durable delivery layer; a cost-aware scheduler owns fairness. The key distinction is that routing is not scheduling: hashing tenants, raising prefetch or assigning message priority can improve distribution or throughput, but none alone guarantees that a noisy tenant cannot monopolize downstream capacity.

Scope and problem framing

Users submit URLs into a multi-stage worker pipeline.

Tenant A can enqueue 1,000 jobs while tenant B submits one latency-sensitive job.

  • The goal is bounded wait and predictable resource share without creating one queue and consumer per tenant.
  • RabbitMQ remains the durable delivery layer; a cost-aware scheduler owns fairness.
  • The key distinction is that routing is not scheduling: hashing tenants, raising prefetch or assigning message priority can improve distribution or throughput, but none alone guarantees that a noisy tenant cannot monopolize downstream capacity.

Requirements

Functional requirements

  • Accept a job with a tenant id, idempotency key, service class, estimated cost and deadline; return accepted, deferred or rejected explicitly.
  • Apply per-tenant rate, pending-work and concurrent-cost limits before publishing runnable work.
  • Schedule active tenants with Deficit Round Robin, allowing tier weights while guaranteeing progress for every tenant inside its contract.
  • Route admitted jobs to a bounded number of interactive and bulk queues, then preserve tenant context through every processing stage.
  • Retry transient failures with a separate budget and quarantine poison jobs without resetting their tenant cost.
  • Expose job state and cancellation without using RabbitMQ queue position as the product source of truth.

Quality attributes

  • Fairness:a sustained bulk producer cannot make another admitted tenant wait indefinitely; define maximum runnable age per service tier.
  • Backpressure:per-tenant and global backlog are bounded in jobs and estimated cost; overload returns 429 or a truthful deferred state before broker memory becomes the limit.
  • Isolation:one tenant's retries, slow target host or downstream rate limit cannot consume every worker, connection or retry slot.
  • Delivery:assume at-least-once; ACK only after an idempotent stage effect is durable, and make redelivery safe.
  • Availability:scheduler failover may pause dispatch but cannot lose accepted jobs or duplicate an irreversible effect.
  • Operability:tenant identity must not become an unbounded metrics label; retain drill-down through sampled logs or a queryable fairness ledger.

Capacity and constraints

  • Size the pipeline by peak submission rate with the daily volume beside it: ~25 rps peak (100k jobs/day) at T2, ~250 rps peak (1M jobs/day) at T3, ~25,000 rps peak (100M jobs/day) at T4. Tenant submission is steady B2B traffic, so plan 3–5× the average — except for a tenant running a bulk import, which concentrates like campaign traffic at 10–20×.
  • Judge the cost-aware scheduler per tier:not needed at T1, where one worker pool drains everything before anyone waits; worth it at T2, once a second tenant can delay the first; mandatory at T3, where one bulk import fills every worker for minutes; needs its own scaling story at T4, because the active-tenant set, the deficit state and the lease table stop fitting one scheduler process.
  • Model arrival rate, active tenants, jobs per burst, cost distribution and downstream limits separately; 10,000 registered users are not 10,000 simultaneously active queues.
  • Set each tenant's pending-cost cap from useful waiting time:admitted backlog must drain before its deadline at the tenant's guaranteed service rate.
  • Choose a fixed shard count from broker CPU, recovery time and hot-key skew, then benchmark it; hashing spreads load but does not provide fairness inside a shard.
  • Set consumer prefetch near measured executor concurrency and processing-time variance. Prefetch 1 is not a network round trip per message under steady push delivery, while a large value reserves invisible work at consumers.
  • Scale workers from oldest runnable age, admitted cost, service time and downstream headroom—not raw queue depth alone.
  • Reserve explicit capacity for interactive work and cap bulk share; shed bulk before borrowing capacity required by the interactive SLO.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Job

job_id, tenant_id, idempotency_key, stage, service_class, estimated_cost, deadline, attempt and state. The durable job store owns lifecycle; a broker delivery is a command to attempt one transition.

02Tenant budget

tenant_id, tier, arrival rate, burst, pending_cost_limit, max_in_flight_cost and retry_budget. Version policy so an operator can explain why a job was admitted or rejected.

03Scheduler state

active tenant, deficit, quantum, cursor and leased cost. Persist enough to rebuild safely; Redis may accelerate active-set operations but must not be the only record of accepted work.

04Stage result

job_id, stage, input_version, output_reference and completed_at under a uniqueness constraint. The constraint turns redelivery into a no-op instead of a duplicate side effect.

05Fairness event

decision id, tenant, policy version, charged cost, wait age and reason code. Keep it queryable with bounded retention rather than attaching tenant_id to every time-series metric.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01Admission API plus relational job store

commit accepted work and an outbox atomically, enforce idempotency and pending limits, and return 429 with Retry-After when the tenant budget is exhausted.

02Deficit Round Robin dispatcher over active tenants

charge estimated work rather than message count, apply tier weights, lease jobs transactionally and publish through the outbox. Weighted Fair Queuing is an alternative when tighter latency bounds justify more scheduling cost.

03RabbitMQ quorum queues for durable stage…

RabbitMQ quorum queues for durable stage commands where replicated delivery is required; use a bounded set of queues by service class and shard, publisher confirms, manual ACKs and explicit dead-letter policy.

04Separate channels/consumers with bounded executors

tune per-consumer prefetch to actual concurrency. RabbitMQ consumer priority selects preferred consumers; it is not tenant priority or a fairness algorithm.

05Token buckets and bulkheads at downstream boundaries

enforce tenant/host/API concurrency after delivery because fair dispatch cannot prevent a long job from occupying every scarce connection.

06Observability

publish scheduler lag, oldest runnable age by bounded tier, admitted/served cost share, in-flight cost, redelivery and DLQ age; provide sampled tenant drill-down outside high-cardinality metric labels.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

Lease one fair batch

The scheduler selects the tenant first; SKIP LOCKED only lets dispatcher replicas lease different runnable rows safely.

sql
BEGIN;

SELECT job_id, estimated_cost
FROM job
WHERE tenant_id = :tenant_id
  AND state = 'RUNNABLE'
  AND estimated_cost <= :deficit
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT :batch_size;

UPDATE job
SET state = 'LEASED', lease_until = now() + interval '30 seconds'
WHERE job_id = ANY(:job_ids);

COMMIT;

Runpsql scheduler.sql --set tenant_id=tenant-b --set deficit=20

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
Queue per tenant vs bounded queues

dedicated queues give hard isolation and simple per-tenant visibility, but every queue replica is a broker process with metadata and recovery cost. Use them for a small active set or contractual isolation, not automatically for every registered account.

02
Hash shards vs fair scheduler

hashing is cheap and preserves tenant affinity, but collisions leave head-of-line blocking inside a shard. A scheduler adds state and a dispatch hop in exchange for an enforceable service share.

03
Message priority vs service classes

priority can move urgent ready messages ahead, but it does not measure tenant consumption and strict priority can starve lower classes. Prefer a few isolated queues with reserved worker shares when starvation is unacceptable.

04
Prefetch throughput vs fairness

larger prefetch amortizes delivery overhead and keeps workers busy, but reserves work outside broker visibility. Bound it by executor slots and variability instead of raising it until queue depth falls.

05
Exact cost vs estimated cost

message count is simple but unfair for heterogeneous jobs; perfect cost is unknowable before execution. Start with coarse weights, feed observed duration back into policy and cap estimation error with max in-flight cost.

06
Scheduler database vs Redis

a database makes accepted work and leases recoverable in one authority; Redis makes active-set scheduling fast. If Redis is used, rebuild it from durable job state and define behavior during cache loss.

07
Reserved interactive pool vs utilization

reservation protects latency during bulk floods but can idle. Allow controlled borrowing only when it is preemptible and the reserved capacity can be restored before the SLO is breached.

Failure review — answers for this design
01

What invariant can break?

An admitted tenant must make progress within its service contract, and a stage effect must occur at most once logically despite at-least-once delivery. Quotas, DRR deficit and idempotent stage records protect those two invariants.

02

Which metric detects unfairness first?

Oldest runnable age and served-to-admitted cost share by bounded service tier reveal starvation before aggregate queue depth. Correlate them with scheduler lag, in-flight cost and downstream saturation.

03

How is the blast radius contained?

Bound pending and in-flight cost per tenant, separate interactive from bulk capacity, and scope retry, connection and downstream limiters. A noisy tenant can exhaust only its own budget and shared bulk allowance.

04

Can retry duplicate or reorder work?

Yes.

  • ACK loss and consumer failure redeliver work, while delayed retries reorder it.
  • Consumers fence state transitions by job/stage version, persist effects idempotently and guarantee ordering only for entities that require it.
05

How do we repair and prove recovery?

Rebuild scheduler state from durable runnable and leased jobs, expire abandoned leases, replay the outbox with stable message IDs and reconcile stage results. Recovery is complete when old runnable age drains without duplicate effects or tier-share violations.

Engineering deep dives

Multi-tenant fairness over RabbitMQ

RabbitMQ transports admitted work; it does not infer tenant fairness. Keep the broker topology bounded and make quota, scheduling cost and in-flight ownership explicit.

Separate the three fairness boundaries

  • Admission fairness bounds accepted backlog and rate per tenant before work enters the broker. Dispatch fairness chooses which active tenant runs next; execution fairness limits concurrent downstream cost after delivery.
  • A fair message count is not fair resource use when jobs vary in duration or API cost. Deficit Round Robin can charge an estimated cost and preserve unused credit without scanning every inactive tenant.

Use broker controls for their real purpose

  • Prefetch limits unacknowledged deliveries per consumer and can improve throughput, but a large prefetch also creates an invisible client-side backlog. Size it near measured worker concurrency; do not treat it as a tenant scheduler.
  • Message priority expresses a small number of service classes, not fairness among arbitrary tenants. Hash exchanges spread routing keys across bounded shards, but a noisy tenant can still block neighbors in the same shard.

Operate fairness as an SLO

  • Measure oldest runnable age and admission rejections by tenant tier, plus scheduler lag, in-flight cost, redeliveries and downstream saturation. Aggregate queue depth can look healthy while one tenant waits indefinitely.
  • Give retries a separate bounded budget, preserve tenant and cost metadata, and make effects idempotent. A poison workload must reach quarantine without repeatedly consuming another tenant’s reserved share.

Asynchronous delivery and replay

Moving work off the request path trades immediate failure for lag, duplicates, ordering constraints and operational backlog.

Define delivery semantics

  • Assume at-least-once at service boundaries. Give each event a stable ID, partition key, schema version and event time; make every side effect idempotent.
  • Guarantee order only within the business entity that needs it. Global order limits parallelism and usually encodes no useful invariant.

Treat lag as user impact

  • Observe oldest-message age, input/output rate, retry count, poison messages and partition skew. Queue depth alone hides slow old work behind new small messages.
  • Use retry topics or delayed queues with expiry and a DLQ; DLQ is not resolution until it has ownership, alerting and a safe replay tool.

Evolve safely

  • Use backward/forward-compatible schemas and tolerant readers. Deploy consumers before producers when adding fields and preserve raw events for bounded replay.
  • Replay into an isolated output or shadow consumer first; throttle it so historical traffic cannot starve live processing or repeat external effects.

Policy and distributed enforcement

A limiter protects a scarce resource; its key, cost model and failure mode matter more than the counter algorithm.

Model the budget

  • Scope by authenticated tenant/user/API key before IP where possible. Charge weighted cost for expensive queries instead of pretending every request costs one token.
  • Separate sustained rate, burst capacity and concurrency. Version policy and shadow new rules before enforcement to measure false positives.

Bound distributed error

  • Use atomic server-side updates for a precise shared bucket; use local token leases only when bounded overshoot is acceptable and measurable.
  • Choose fail-open or fail-closed per endpoint. Authentication, checkout and public reads have different abuse risk and availability cost.

Operate the control

  • Track allowed, rejected and shadow decisions by policy version plus limiter latency, hot keys and degraded-mode duration—without putting user IDs in metric labels.
  • Return a stable error contract and Retry-After where meaningful; combine rate limits with quotas, bot controls and origin concurrency protection.
