Scope and problem framing

Serve roughly one million requests a day where the overwhelming majority are searches and only a small fraction become bookings.

Raw throughput is not the question: 1M/day averages about 12 requests a second, so the peak-to-average ratio and two conflicting workloads determine the design.

Keep search fast with bounded staleness; keep booking correct even when it is slower.

Requirements

Functional requirements

  • Search read path:Search availability by date, location and filters, returning ranked results from an index rather than the transactional store.
  • Hold a specific unit for a bounded TTL so a user can complete checkout without another user taking it.
  • Confirm a booking through payment, then issue confirmation and release the hold atomically with respect to the order.
  • Expire abandoned holds and reconcile payments whose outcome is unknown, without operator intervention.

Quality attributes

  • No two confirmed bookings may consume the same unit; overselling is a correctness failure, not a capacity one.
  • Search may serve slightly stale availability, but the hold step always re-validates against the authoritative store.
  • A slow or failed payment provider must degrade booking latency, never search availability.
  • Every asynchronous consumer is idempotent:Kafka gives at-least-once delivery, so duplicates are normal traffic.

Capacity and constraints

  • Peak traffic:1M requests/day is about 12 rps average; size for the peak instead — a 10-20x daily peak puts the search path near 150-250 rps.
  • Booking write rate:Assume a 100:1 search-to-booking ratio: roughly 10k bookings/day, about 2-5 writes per second at peak on the correctness path.
  • Serialization boundary:Search is cacheable and horizontally scalable; the inventory write path is the only component that must serialize per unit.
  • Event retention:Size Kafka for booking events plus retries and replay: modest volume, but retention must cover a full reconciliation window.
  • Judge each component per tier rather than adopting the split wholesale:
    • the read/write path separation is not needed at T1, worth it at T2, and mandatory at T3 where the search load would otherwise size the database that must serialize bookings
    • the Kafka hop is not needed at T1 and T2, worth it at T3 to keep payment and indexing off the request, and needs its own scaling story at T4 alongside partition count, consumer lag and replay.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Inventory unit

the authoritative row, sharded by resource id so contention for one unit stays inside one shard.

02Hold

unit id, user, expiry timestamp and state; the uniqueness constraint that prevents double-selling lives here.

03Order

the booking aggregate with an idempotency key, its payment reference and an explicit state machine.

04Search document

a denormalized, eventually consistent projection rebuilt from events, never read during confirmation.

05Outbox

booking state changes written in the same transaction as the order and relayed to Kafka at least once with stable event ids; consumers deduplicate effects.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01API gateway plus separately deployed search…

API gateway plus separately deployed search and booking services, so the two scale on their own traffic shape.

02Distributed SQL (CockroachDB, TiDB, Yugabyte) or a sharded relational store

booking needs real transactions, so range-sharding by resource keeps them single-shard.

03Kafka as the event backbone

partition by booking or resource id so events for one entity keep their order.

04A search index (Elasticsearch or OpenSearch)…

A search index (Elasticsearch or OpenSearch) plus a cache for hot queries, both fed asynchronously from Kafka.

05The transactional-outbox pattern rather than dual writes

a database commit and a Kafka publish cannot be made atomic.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

The one line that must serialize

Everything else in this design scales horizontally. This statement is the serialization boundary, and the WHERE clause is what makes it safe without holding a lock across the request.

sql
-- conditional decrement: the row is only updated if inventory is actually there,
-- so two concurrent bookings cannot both succeed on the last unit
UPDATE inventory
   SET available = available - :qty,
       version   = version + 1
 WHERE unit_id  = :unit_id
   AND available >= :qty;

-- zero rows updated means sold out — that is the answer, not an error to retry.
-- Reading the balance first and then updating is the race this replaces.

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
At this volume a single well-indexed relational primary would likely cope. Sharding and microservices are being bought for isolation and independent deployment, not for throughput

say so rather than justifying them with the request count.

02
Kafka moves payment and notification off the request path, but converts booking into an asynchronous workflow

the user now sees a pending state, and every consumer needs idempotency and a dead-letter path.

03
A distributed database removes the single-primary…

A distributed database removes the single-primary ceiling and adds cross-shard latency; the design only pays off because bookings for one unit stay within one shard.

04
Holds trade inventory utilization for user experience

a long TTL blocks real demand, a short one loses checkouts under slow payments.

05
Failure review

the highest-risk paths are a payment whose result is unknown, a consumer replaying old events after a rollback, and index lag making search advertise units that are already gone.

Failure review — answers for this design
01

Which invariant can break?

A unit of inventory may be booked at most once, and a booking that a customer was shown as confirmed must exist downstream. The first is protected by the conditional decrement; the second by publishing the event in the same transaction as the booking rather than after it.

02

Which metric detects it first?

Consumer lag on the booking topic, read beside booking confirmation latency. A search-path incident is visible immediately, but a broken write path shows first as lag: bookings still succeed while payment, notification and indexing fall behind them.

03

How is the blast radius contained?

Search is cacheable and horizontally scalable, so its failure never reaches the booking path. The only serializing component is the inventory row, and everything downstream of the booking is asynchronous, so a payment or indexing outage delays follow-up rather than blocking a sale.

04

Can retry duplicate or reorder work?

Yes.

  • A retried booking request must be deduplicated by an idempotency key or the conditional decrement runs twice and sells two units to one customer.
  • Consumers are at-least-once, so payment and notification must both be idempotent on the booking id.
05

How do we repair and prove recovery?

Replay the booking topic from the last committed offset; the inventory table is the source of truth and never needs reconstructing. Recovery is proven when consumer lag returns to baseline, a sampled set of bookings has exactly one payment and one notification each, and the search index matches the booking table for the affected window.

Engineering deep dives

Correctness across money and inventory

The database protects local invariants; idempotency, state machines and reconciliation protect the workflow around it.

Make commands repeatable

  • Persist idempotency key, request fingerprint and original response together. Reject key reuse with different parameters and define retention from the maximum retry window.
  • Represent pending and unknown outcomes explicitly. After a timeout, query authoritative provider state before retrying or compensating an irreversible action.

Keep invariants local

  • Put uniqueness, balance and legal state transitions in one transaction and enforce them with constraints, conditional updates or locks—not a cache lock.
  • Choose isolation from the anomaly to prevent. Serializable transactions can abort under contention, so the whole transaction needs a bounded retry path.

Close the distributed gap

  • Write business state and an outbox record atomically; consumers deduplicate effects. Exactly-once inside one platform does not make an external PSP or airline atomic.
  • Reconcile independent statements, retain immutable audit history and repair by compensating entries. Monitor aged pending states and unmatched totals as correctness SLIs.

Asynchronous delivery and replay

Moving work off the request path trades immediate failure for lag, duplicates, ordering constraints and operational backlog.

Define delivery semantics

  • Assume at-least-once at service boundaries. Give each event a stable ID, partition key, schema version and event time; make every side effect idempotent.
  • Guarantee order only within the business entity that needs it. Global order limits parallelism and usually encodes no useful invariant.

Treat lag as user impact

  • Observe oldest-message age, input/output rate, retry count, poison messages and partition skew. Queue depth alone hides slow old work behind new small messages.
  • Use retry topics or delayed queues with expiry and a DLQ; DLQ is not resolution until it has ownership, alerting and a safe replay tool.

Evolve safely

  • Use backward/forward-compatible schemas and tolerant readers. Deploy consumers before producers when adding fields and preserve raw events for bounded replay.
  • Replay into an isolated output or shadow consumer first; throttle it so historical traffic cannot starve live processing or repeat external effects.

A travel marketplace receives 1M requests/day, a 100:1 search-to-booking ratio, and 250 search requests/sec at peak. Design its availability and booking paths. What may search promise, which write is authoritative, and how do holds, Kafka fan-out, and replay keep one unit from being confirmed twice?11-system-design-cases.the-big-prompts.q13

Contract: Search reads a cache/index projection and returns its observed_at time or version. It may be stale and is never a promise of stock.

Only a short transaction on the inventory unit may create an active hold and order; a conditional write or uniqueness constraint prevents double-selling, and confirmation revalidates there.

Flow: Persist the idempotency key and canonical request fingerprint with the hold/order and an outbox record in that same transaction. Relay events at least once; payment, notification, and index consumers deduplicate using a stable event ID or aggregate version.

Call the PSP outside the database transaction.

Failure path: Index lag may advertise a unit that has gone, so the hold returns the truthful result. A PSP timeout is UNKNOWN; query and reconcile before finalising, then release or compensate through explicit state transitions. Search stays isolated from booking backlog.

Case metadata:

  • Workload: 1M requests/day, 100:1 search-to-booking ratio, peak search rate, hold concurrency and supplier quota
  • Freshness: search exposes observed version/time while hold/booking authority is synchronous
  • Duplicate tolerance: search replay is harmless, hold/order key and event version are not
  • Recovery owner: inventory/booking authority and reconciliation owner

A checkout returns `PENDING` after a PSP timeout, then a provider webhook arrives after the hold may have expired. Design the state machine and recovery path. How do expiry, event publishing, retries, and late success avoid confirming or charging one unit twice during queue lag and consumer replay?11-system-design-cases.the-big-prompts.q14

Durable state: Keep a versioned hold, order, payment attempt, provider idempotency key, and explicit PENDING, UNKNOWN, CONFIRMED, FAILED, and RELEASED states. Expiry is a conditional transition: it may release only the expected active version.

If payment authorization has started, use a bounded, durable policy rather than letting a timer blindly reclaim stock. Local expiry does not prove that a supplier/GDS released inventory.

Persist the supplier reference, quote/hold version, and correlation ID, then query the chosen supplier authority before confirming late success or issuing compensation; exact expiry and idempotency behavior belongs to that provider contract.

External boundary: Commit the order transition and outbox locally, then let a worker call the PSP with the same provider key on every safe retry. Never retry an unknown charge with a fresh key. Webhooks and status queries are idempotently recorded before they advance state.

Recovery: A late success reloads the authoritative hold and order. If stock can no longer be confirmed, do not allocate silently; reconcile, cancel or refund according to policy, and record the compensation. Outbox consumers use stable IDs, so replay cannot duplicate downstream effects.

Case metadata:

  • Workload: hold expiry rate, provider latency/lag, queue depth and late-callback volume
  • Freshness: hold/order version is authoritative while provider status has an unknown-age budget
  • Duplicate tolerance: hold version, provider idempotency key and webhook/event ID
  • Recovery owner: expiry worker, payment owner and reconciliation/compensation owner

State transition guard: A possible graph is:

  • hold: ACTIVE_HOLD -> EXPIRED | RELEASED | CONFIRMED
  • payment: PENDING | UNKNOWN -> CONFIRMED | FAILED | RECONCILIATION_REQUIRED
  • late success: COMPENSATING -> REFUNDED | RECONCILIATION_REQUIRED

Expiry and confirmation must compare the expected hold version, never just a wall-clock timestamp.
