Scope and problem framing

Blueprint 16 asks what changes between scales.

This one is the reference behind it: a technique-by-technique catalogue you can read on its own.

  • Each entry answers four questions — what limit does this remove, what does it cost, what does it NOT fix, and what should you have tried before reaching for it.
  • The organising principle is simple: every technique is a trade.

Naming what you gave up separates a design from a technology list.

Requirements

Functional requirements

  • Start from the symptom, never the technology:slow reads, slow writes, a slow dependency, or contention on a single row each have different answers.
  • Limit removed:For each technique, state the limit it removes and the limit it leaves untouched — most production mistakes are a technique applied to the wrong bottleneck.
  • Give the cheaper alternative that should be exhausted first, so the catalogue reads as an order rather than a menu.
  • Name the new failure mode each technique introduces, because that is the ongoing cost you will actually operate.

Quality attributes

  • Measured bottleneck:A technique is only correct if it targets the measured bottleneck; adding replicas to fix write latency is a common and expensive category error.
  • Correctness boundary:Correctness mechanisms and performance mechanisms must never be confused — distributed locks are performance, database constraints are correctness.
  • Async ambiguity:Every asynchronous boundary makes the caller's success ambiguous, so idempotency is not optional once a queue enters the design.
  • Prefer the technique whose failure mode you can detect:a slow system you can see beats a fast one that is silently wrong.

Capacity and constraints

  • Measure before choosing:p99 latency by endpoint, read/write split, cache hit rate, working-set size, and the slowest dependency's timeout budget.
  • Primary write capacity is workload-specific:schema, indexes, transaction shape, durability, contention, hardware, and p99 all matter. Benchmark a production-shaped workload before choosing sharding; the next fix is often a query, data-model, or concurrency change, but never assume it.
  • Working-set fit:Cache effectiveness is set by working-set size versus memory, not by request rate; a 99 percent hit rate and a 90 percent hit rate differ tenfold in origin load.
  • Queue recovery:Queue sizing is about burst absorption and drain rate, not throughput: the useful number is how long the backlog takes to clear after an incident.
  • Give every technique in this catalogue a tier verdict before adopting it, in the four words the rest of the site uses.
    • Read replicas are not needed at T1, worth it at T2, mandatory at T3; a shared cache is not needed at T1 and mandatory at T3; a broker is worth it at T2 and needs its own scaling story at T4; sharding is not needed until T4 and needs its own scaling story when it arrives.
    • A technique with no verdict is one nobody has justified.
  • Anchor every judgement to a tier so the catalogue is a decision aid rather than a menu: T1 is 10k req/day (~2.5 rps peak), T2 100k (~25 rps), T3 1M (~250 rps) and T4 100M (~25,000 rps), with 10M/day as the waypoint inside T4 where a system stops growing and changes shape.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Idempotency key

the precondition for every retry, queue and at-least-once consumer in the catalogue; without it, none of the async techniques are safe.

02Version or sequence column

optimistic concurrency, and the correctness alternative to a distributed lock for contended rows.

03Outbox table

the only sound way to publish an event and commit a transaction together; dual writes lose messages exactly when it matters.

04Denormalized read model

the artefact that makes caching and replicas effective, because it removes the joins that made reads expensive.

05Partition or shard key

the one field that determines whether future transactions stay local; decide it before it becomes load-bearing.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01Read replicas

removes read throughput limits.

  • Does not help writes, and introduces replication lag, so read-your-own-writes must be pinned to the primary.
  • Try index and query tuning first; a missing index is cheaper than a new server.

02Redis

a data-structure server, not just a cache.

  • Buys sub-millisecond reads, counters, sorted sets for leaderboards, token buckets for rate limiting, streams for lightweight queues.
  • Costs an extra failure domain and a stale-data policy.
  • Prefer it over Memcached unless you truly want only an LRU cache, because you will eventually want the other structures.

03Memcached

a pure multithreaded LRU cache.

  • Marginally faster per node for plain key-value and simpler to reason about because it has no persistence and no semantics.
  • Choose it when the cache is genuinely disposable and you want no temptation to store state in it.

04Local in-process cache

removes the network round trip that Redis still costs, and absorbs hot keys before they concentrate on one Redis node. Costs a second staleness window; keep TTLs short rather than attempting precise invalidation across instances.

05Distributed lock (Redis SETNX with token and TTL)

mutual exclusion for efficiency: run one cron, avoid duplicated work.

  • Not safe for correctness, because a GC pause or partition allows two holders; Redlock does not close this.
  • For inventory and money use a unique constraint, SELECT FOR UPDATE, or an optimistic version.

06RabbitMQ

a task broker: per-message ack, requeue, dead-letter, priorities and rich routing.

  • Right when each message is a unit of work consumed once and low latency dispatch matters.
  • Wrong when several independent consumers need the same event, or when replay after a bug is required.

07Kafka

a partitioned, replayable log with ordering per key and independent consumer groups.

  • Right for event backbones, CDC, fan-out to several concerns, and reprocessing history.
  • Costs partition-count planning, consumer lag as a permanent operational metric, and at-least-once semantics you must absorb with idempotency.

08Circuit breakers, bulkheads and backpressure

the controls that keep one slow dependency from consuming every thread.

  • A breaker fails fast when a dependency is unhealthy, a bulkhead caps concurrency per dependency so it cannot starve the rest, and bounded queues with load shedding keep latency finite under overload.
  • These are the cheapest reliability wins in the catalogue and are almost always missing.
Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

Backpressure with a bounded worker queue

Reject before the queue consumes unbounded memory; the caller gets a retryable signal instead of hidden overload.

typescript
const queue: Job[] = [];
const MAX_QUEUE = 500;

export function enqueue(job: Job) {
  if (queue.length >= MAX_QUEUE) {
    throw new Error('OVERLOADED_RETRY_LATER');
  }
  queue.push(job);
}

setInterval(async () => {
  const job = queue.shift();
  if (job) await handle(job);
}, 10);

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
The order is the point

index and query tuning, then connection pooling, then replicas, then caching, then async offload, then read models, then partitioning, then sharding, then cells. Each is cheaper and more reversible than the next, and skipping ahead buys permanent complexity to solve a temporary problem.

02
Caching versus replicas

a cache removes load from the database entirely, a replica moves it.

  • Caching is higher leverage and higher risk; replicas are boring and predictable.
  • Prefer replicas when reads must be fresh, caching when they may be slightly stale.
03
Kafka versus RabbitMQ is a data-shape…

Kafka versus RabbitMQ is a data-shape question, not a performance one.

  • Ask whether the message is work to be done once or an event several parties care about.
  • Choosing Kafka for simple job dispatch adds partition planning you did not need; choosing RabbitMQ for an event backbone means the second consumer forces a redesign.
04
Distributed locks are the most commonly misused item here. They look like correctness and are not. If losing the lock would corrupt data rather than merely duplicate work, the answer is a database constraint

every time.

05
Async offload trades a clear synchronous…

Async offload trades a clear synchronous failure for an ambiguous asynchronous one.

  • The user gets a fast pending response, and you inherit retries, duplicates, dead letters, ordering questions and a backlog that must be monitored.
  • Only cross that boundary when the work genuinely does not belong in the request.
06
Every technique here adds a component that can fail independently. The honest accounting is not throughput gained but on-call surface added

each one is a dashboard, an alert, a runbook and a failure mode someone must understand at three in the morning.

Failure review — answers for this design
01

Which invariant can break?

Every technique here trades a guarantee for capacity, so the invariant at risk is whichever one the technique quietly gave up — a replica gives up read-after-write, a cache gives up freshness, a queue gives up synchronous failure reporting. The failure is adopting the technique without naming what was traded.

02

Which metric detects it first?

The one the technique introduced, not the one you already had. Replication lag, cache hit ratio, queue oldest-age and bulkhead rejection are each invisible on a dashboard built before the technique existed, which is why adding the component and adding its signal are one task.

03

How is the blast radius contained?

By adopting one technique at a time with a measurement either side of it. Two changes shipped together cannot be attributed, and a technique that cannot be attributed cannot be rolled back with confidence when it turns out to be the wrong one.

04

Can retry duplicate or reorder work?

Every asynchronous technique in this catalogue makes both possible where they were not before. A queue converts a synchronous call into at-least-once delivery, and a replica converts a read into a possibly-stale one — so idempotency and staleness tolerance are prerequisites for adoption, not follow-up work.

05

How do we repair and prove recovery?

Each technique needs a stated way to run without it: serve from the primary, bypass the cache, drain the queue synchronously. Recovery is proven when the metric the technique introduced returns to its own baseline and the system’s behaviour without it is still the documented degraded mode rather than an outage.

Engineering deep dives

Evolution without premature distribution

Scale by measured bottleneck and preserve a reversible path; every new datastore creates consistency and on-call obligations.

Use the cheapest lever first

  • Fix query shape and indexes, bound connection pools, add replicas/caches, then asynchronous read models before partitioning or sharding the source of truth.
  • Record the metric and threshold that justify each step. A component without a removal criterion tends to become permanent architecture.

Separate models only when needed

  • CQRS can share one store first. Split physical stores only when read/write load, model or security boundaries demand independent scaling.
  • Treat every derived model as rebuildable: version transformations, retain a replay source, compare counts/checksums and rehearse backfill under live load.

Partition around invariants

  • Choose a key that keeps the common transaction local and spreads writes; quantify skew before rollout and define how hot tenants/entities are isolated.
  • Use expand-migrate-contract for schema and dual-read verification for data moves. Avoid unbounded dual writes; give migration a completion SLI and rollback point.

Observability and security review

Instrumentation should explain user impact and the responsible dependency without leaking identity or creating unbounded telemetry cost.

Start from user SLIs

  • Define success, latency, freshness and correctness SLIs at the system boundary; alert on error-budget burn, then use dependency metrics for diagnosis.
  • Correlate traces, metrics and structured logs with trace/span IDs. Preserve request, policy and schema versions but redact secrets and sensitive payloads.

Keep telemetry bounded

  • Never use user ID, object ID or raw URL as a metric label. Use logs/traces for high-cardinality detail and explicitly monitor cardinality overflow.
  • Sample by value: retain errors, slow paths and rare business failures at higher rates while keeping predictable storage and query cost.

Review the trust boundary

  • Authorize the object and action on every request, use least-privilege service identities and short-lived credentials, encrypt in transit/at rest and audit privileged changes.
  • Threat-model abuse, replay, enumeration, tenant crossover and data retention. Security controls need degraded behavior and recovery drills like every other dependency.

An API has worsening p99 latency for both reads and writes. A proposal says to add read replicas, Redis, and distributed locks immediately. How do you diagnose the actual bottleneck, choose the cheapest effective technique, and distinguish a performance mechanism from a correctness mechanism?11-system-design-cases.the-big-prompts.q17

Diagnose before naming tools: Break p99 down by endpoint into application time, connection wait, query time, lock wait, cache hit rate, and dependency timeouts. Read replicas cannot cure primary write latency, and a Redis cache cannot repair an unindexed or lock-contended transaction.

Use the narrowest fix: Improve the query, index, transaction scope, and pool first. Use replicas for read capacity with a stated replication-lag contract; use caching only when the response may be stale, with single-flight fills and jittered TTLs.

Move genuinely non-request work behind an outbox and queue, returning a durable pending state.

Keep correctness local: A distributed lock may reduce duplicate work, but losing it must not decide whether data is valid. Protect money, inventory, and uniqueness with database constraints or conditional writes. Alert on the measured bottleneck and on the new failure mode each added tier creates.

Case metadata:

  • Workload: read/write mix, payload, dependency fan-out, resource contention and tenant skew
  • Freshness: telemetry and replica/cache observations carry timestamps or lag
  • Duplicate tolerance: diagnostic replay is harmless, business remediation still needs an idempotent command
  • Recovery owner: endpoint owner and SRE/on-call

Canonical boundary: Put pool, retry, cache, overload and observability mechanics in (25-microservice.04-messaging-event-driven-at-scale.q1) and the relevant Topic 25 owner; this case chooses the cheapest measured fix and states what would falsify it.

Checkout needs one fulfilment job, while payment, notification, search indexing, and analytics all need to observe state changes; catalogue reads also need a freshness contract. Choose between RabbitMQ and Kafka, and between cache and replicas. What durability, ordering, replay, and failure behavior must the design state explicitly?11-system-design-cases.the-big-prompts.q18

Shape the messages first: A fulfilment command has one logical worker, so a work queue such as RabbitMQ can fit; it still needs idempotent handling because redelivery is normal.

State changes that several consumers must replay suit Kafka, partitioned by the aggregate key when per-entity order matters. Neither choice makes a database commit and publish atomic: write an outbox with the transaction.

Choose the read contract: Replicas are predictable when reads require near-fresh data, but lag must be visible. Cache removes origin load when bounded staleness is acceptable; it needs invalidation/TTL rules, request coalescing, and cold-start protection. It is never the source of truth.

Operate the boundary: Record stable event IDs, schema versions, consumer offsets, retry policy, DLQ owner, and oldest-message age. A fast pending response is only honest if users and operators can see progress and recover ambiguity.

Case metadata:

  • Workload: command/event rate, consumer count, replay window, catalogue read ratio and payload/retention
  • Freshness: catalogue projection and replica lag are explicit read contracts
  • Duplicate tolerance: command ID, event ID, consumer effect key and offset replay
  • Recovery owner: fulfilment consumer plus each projection owner

Provider/version boundary: Kafka EOS is a scoped transaction/consumer guarantee for the configured Kafka client and broker boundary; RabbitMQ publisher confirms and consumer ACKs cover different boundaries and do not mean customer delivery.

Name the selected versions, retention, retry/DLQ and database inbox/outbox contract before comparing them.
