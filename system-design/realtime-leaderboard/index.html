Scope and problem framing

Ingest trusted score changes, show global or scoped leaderboards, return a player's rank and nearby competitors, handle seasons and rebuild indexes after corruption or rule changes.

Requirements

Functional requirements

  • Apply a score update — absolute or delta — and make it visible on the board within the freshness budget the product promises.
  • Return the top N for a board, and the window around a given player, both with a deterministic rank for equal scores.
  • Scope boards by season, region and cohort, and close a season into an immutable snapshot that can still be read after the live board is reset.
  • Rebuild a board from the durable score history without replaying application logic, because the serving structure is derived state.

Quality attributes

  • A rank must be reproducible:two players with the same score must always order the same way, or the board flickers between reads and users report it as cheating.
  • The serving structure is a cache of a durable log, never the record of truth. Losing it must cost a rebuild, not a season.
  • Top-N reads dominate and must stay cheap; around-me reads are rarer and are allowed to cost more, which is what makes an approximate rank acceptable below the head.
  • Season rollover must be atomic from the reader's point of view — a board that is half reset is worse than one that is briefly frozen.

Capacity and constraints

  • Size the write path by score-update peak with the daily volume beside it: ~25 rps peak (100k updates/day) at T2, ~250 rps peak (1M/day) at T3, ~25,000 rps peak (100M/day) at T4. Game and campaign traffic concentrates hard around an event start, so plan 10–20× the average rather than 3–5×.
  • Reads and writes diverge sharply:a player updates a score occasionally and refreshes the board constantly, so a 10:1 or 50:1 read:write ratio is normal and the top-N result is the single hottest key in the system.
  • Board size, not update rate, is what decides the algorithm. A sorted set holding 10k members is trivial at any tier; the same structure at 50M members changes the memory profile, the rebuild time and the cost of an exact rank query.
  • Judge an exact around-me rank per tier:worth it at T1 and T2, where the board fits comfortably and a rank query is a cheap index operation; mandatory for the top of the board at every tier because that is what users screenshot; not needed below the head at T3 and above, where a bucketed percentile is indistinguishable to the user and far cheaper; needs its own scaling story at T4, where a single board no longer fits one node and rank becomes a merge across shards.
  • Budget the rebuild explicitly:how long a full board takes to reconstruct from the score log is the real recovery time objective, and it grows with member count rather than with traffic.
  • Season rollover is a scheduled traffic spike, not a quiet maintenance window. Snapshot, archive and reset all land at once, usually while players are watching, so size for it as a peak event.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Score event

event id, player, board and season, delta or absolute score, the rule version that produced it and the server time. This is the durable log everything else is derived from.

02Rank member

a composite board and player key with the ranking value. The value must encode the tie-break, not just the score, so that equality never depends on insertion order.

03Board definition

scope, season window, scoring rule version, visibility and the reset policy, stored so that a closed season can still be interpreted with the rules it ran under.

04Season snapshot

the closed board, its winners, the rule version, a checksum and the archive location. Immutable, because a leaderboard result that can be edited after the fact is not a result.

05Rank bucket

for very large boards, the count of members per score band, which is what makes an approximate rank a single lookup instead of a scan.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01A sorted set

Redis ZSET or an equivalent skip-list structure — is the serving primitive: insert and rank are logarithmic, and top-N is a contiguous range read. It is the right structure and it is not the source of truth.

02Durable append-only score log behind it,…

Durable append-only score log behind it, in a relational store or a partitioned topic, so that the sorted set can always be rebuilt and a disputed result can always be explained.

03Encode score and tie-break into one…

Encode score and tie-break into one sortable value rather than sorting on two fields. A score scaled into the high bits with an inverted timestamp in the low bits gives a total order in a structure that only sorts on one key.

04Read replicas or a short-TTL cache…

Read replicas or a short-TTL cache for top-N, because the head of the board is read far more than it changes and it is the same result for every reader.

05Sharding by board rather than by player

a board is the unit of query, so splitting it across nodes turns every rank into a scatter-gather and should be delayed until a single board genuinely stops fitting.

06Observability

update-to-visible lag, top-N read latency, rank query latency split by head and tail, sorted-set memory per board, rebuild duration, and skew — the ratio of the largest board to the median.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

One sortable value carries score and tie-break

Abridged. Sorting on two fields is not available in a sorted set, so the tie-break is packed into the low bits — earlier submissions win, deterministically.

java
long rankingValue(long score, Instant achievedAt) {
    // score in the high bits, inverted time in the low bits: a later time lowers
    // the value, so an equal score is broken in favour of whoever got there first
    long invertedTime = MAX_EPOCH_SECONDS - achievedAt.getEpochSecond();
    return (score << TIME_BITS) | (invertedTime & TIME_MASK);
}

void submit(String board, long playerId, long score, Instant at) {
    // absolute score, not a delta: replaying this event twice is a no-op
    redis.zadd(board, rankingValue(score, at), String.valueOf(playerId));
}

Around-me without an exact rank for everyone

The head is exact because it is what users compare; below the head the bucket count answers "roughly where am I" for a fraction of the cost.

bash
# top of the board: exact, contiguous, one range read
ZREVRANGE board:s7 0 99 WITHSCORES

# a player near the head: exact rank is still cheap
ZREVRANK board:s7 player:42

# deep in the tail: do not pay for an exact rank, read the precomputed bands
HGET board:s7:buckets 1200-1299     # -> members in this score band
# rank ≈ sum of counts in all bands above, which is a fixed number of lookups

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
Absolute scores make updates idempotent and…

Absolute scores make updates idempotent and make replay safe; deltas are natural for gameplay and make every retry a potential double count. If deltas are required, they need an event id and a deduplication table, which is most of the cost of absolute scores anyway.

02
An exact rank for every player…

An exact rank for every player is a logarithmic operation per query and a merge across shards once a board is split. A bucketed percentile below the top N is a single lookup and is invisible to a user sitting 41,000 places down.

03
Keeping the sorted set in memory…

Keeping the sorted set in memory is what makes this design fast and what makes a node loss a rebuild. Persistence options reduce the rebuild window and cost write latency, which is the actual trade rather than durability itself.

04
One board per scope multiplies structures…

One board per scope multiplies structures and keeps each one small; a single global board is simpler and becomes the thing that stops fitting. Choose the scoping early, because resharding a leaderboard means rewriting every rank.

05
Real-time push of rank changes is a lovely feature and a fan-out problem

every score update potentially changes the rank of everyone below it, so push the top of the board and let the rest poll.

06
Anti-cheat belongs on the write path…

Anti-cheat belongs on the write path and slows it down. Validating a score against the rule version before it enters the log is far cheaper than removing it from a published board afterwards.

Failure review — answers for this design
01

Which invariant can break?

A player's displayed rank must follow from the score log and must be stable between two reads with no intervening update. It breaks when a delta is applied twice, and when two equal scores are ordered by insertion rather than by an encoded tie-break.

02

Which metric detects it first?

Update-to-visible lag together with board skew. Aggregate write latency stays flat while one oversized board slows down, so the ratio of the largest board to the median is the number that moves before anything user-visible does.

03

How is the blast radius contained?

Boards are independent structures, so one oversized or hot board cannot slow the others if they are not colocated. The score log is separate from the serving structure, so losing the sorted set costs a rebuild and losing a replica costs nothing.

04

Can retry duplicate or reorder work?

Absolute score submissions are idempotent and safe to retry in any order, because the last valid value wins. Deltas are neither: they need an event id and a deduplication check, and out-of-order deltas produce a correct total but a wrong intermediate board.

05

How do we repair and prove recovery?

Replay the score log into a fresh sorted set and swap it in, which is why rebuild duration is a tracked number rather than a surprise. Recovery is proven when a recomputed board matches the live one for a sampled set of players at both head and tail, and update-to-visible lag is back inside the freshness budget.

Engineering deep dives

Indexes, ranking and freshness

Fast ranking comes from a bounded candidate set and a versioned derived index, not from querying the source of truth on every keystroke or feed read.

Separate retrieval from ranking

  • Retrieve a bounded candidate set using prefix, graph, time or score indexes; rank it with a versioned rule/model and keep a deterministic fallback.
  • Store the ranking/model version and stable tie-break key so pagination, audits and experiments can reproduce an ordering.

Control index freshness

  • Measure event-to-searchable lag by percentile and entity class. Rebuild into a new version, validate counts/checksums, then atomically switch readers.
  • Re-check authorization, deletion and hard availability constraints at read time; an eventually consistent candidate index must not bypass current policy.

Bound cost and abuse

  • Debounce typeahead, cap prefix/fuzzy expansion and cache popular anonymous prefixes. Personalization reduces cacheability and increases privacy review.
  • Track empty-result rate, candidate count, ranking latency, index size, stale-result complaints and quality metrics separately from availability.

Caching as a bounded copy

A cache is a disposable, stale copy with a failure mode. Its key, TTL and origin-protection plan are part of correctness.

Choose what may be stale

  • Include tenant, authorization dimension and schema version in keys. Never cache a security or monetary decision unless the product defines acceptable staleness.
  • Use cache-aside for simple reads, versioned keys for safe rollout and randomized TTLs to avoid synchronized expiry; cap negative-cache lifetime.

Protect the origin

  • Coalesce concurrent misses, refresh hot values ahead of expiry and bound rebuild concurrency. A cache outage must not instantly multiply origin load by the hit ratio.
  • Monitor hit ratio by key class, eviction, memory fragmentation, hot keys, fill latency and origin amplification—not only cache latency.

Compare tiers

  • L1 removes a network hop but multiplies stale copies; shared L2 centralizes data and invalidation but adds a network dependency and hotspot risk.
  • Choose LRU/LFU/TTL from access distribution and object value. If eviction loses authoritative state, the component is a database wearing a cache label.

▸ DEEP DIVE · SENIOR
  • a Redis sorted set is useful for one leaderboard shard: rank and top-N are efficient locally. Define ties explicitly. Equal scores have lexicographic member ordering in Redis; use a stable member/tie key if that is the intended product rule.
  • do not pack score and inverted timestamp into one floating-point score unless the full integer range and precision are proven below the safe limit. Otherwise ties and large scores can silently corrupt rank.
  • make score-event ingestion idempotent, preserve a durable source or event log, and support replay/rebuild after cache loss. Snapshots help recovery speed but are not a sufficient source of truth alone.
  • a global sharded top-N can merge bounded top candidates from shards. Exact global rank for every tail user needs an authoritative aggregate or scatter/gather work; otherwise state that the displayed global rank is approximate or eventually consistent.
  • define season boundaries, resets, anti-cheat review, correction events, and rank freshness before optimizing the sorted-set commands.
