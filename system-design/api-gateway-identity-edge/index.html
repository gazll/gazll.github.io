Scope and problem framing

Every request needs a defensible authentication and authorization boundary before it reaches the system, but putting every control at one gateway creates a new choke point.

The design must separate north-south routing from east-west calls, keep domain authorization with the resource owner, and size identity, rate limiting and connection state against a declared peak workload. It must also say what remains available when the IdP, JWKS, policy engine, Redis or one gateway cell is unhealthy.

The thesis is simple: the edge should make cheap, coarse decisions early, while services retain the authority to protect their own invariants.

Requirements

Functional requirements

  • Routing:match host, path and method, then apply ordered filters without allowing client headers to change the destination.
  • Authentication:verify the bearer token or a narrowly scoped internal assertion before protected north-south traffic reaches a service.
  • Authorization:enforce coarse scope, audience, tenant and product policy at the edge, then leave object and state authorization to the owner service.
  • Admission:apply per-route, tenant and identity rate limits plus bounded concurrency before scarce downstream capacity is consumed.
  • Resilience:enforce deadlines, retry budgets, circuit breaking and an explicit 429, 503 or 504 contract for each route.
  • Identity propagation:forward a verified original token or a signed internal assertion while stripping client-supplied identity headers.
  • Operations:emit route-level RED metrics, W3C traces, a bounded correlation id and audit-safe policy decisions for diagnosis and review.

Quality attributes

  • Latency budget:target no more than 5 ms p99 for a warm local route, then measure JWT, Redis and PDP costs separately; this is an SLO target, not a vendor guarantee.
  • Availability:the edge is not a single point of failure; gateway capacity, configuration, keys and policy must survive one instance, zone or cell loss.
  • Identity outage:cached JWKS may verify an unexpired JWT, but money movement and privilege changes fail closed when the IdP, introspection or policy source is unavailable.
  • Isolation:one route, tenant, backend, IdP or PDP failure cannot exhaust the connection pool, event loop, limiter state or retry budget of unrelated routes.
  • Trust boundary:client-provided user, tenant, role, forwarding and routing headers are stripped and rebuilt only from verified context.
  • Rotation:issuer, key, policy and route changes have overlap, versioning, canary and rollback paths that do not depend on the failing control plane.
  • Degraded contract:every route declares whether it rejects, serves a bounded stale result, becomes read-only or returns pending when a dependency is unhealthy.

Capacity and constraints

  • T1 — 2.5 rps peak (10k req/day):
    • one or two gateway instances, a local or managed limiter and one regional identity path are usually sufficient
    • measure the added hop rather than guessing.
  • T2 — 25 rps peak (100k req/day):
    • keep a small multi-instance fleet, warm connection pools and route-level budgets
    • a shared Redis limiter is useful when tenant or abuse isolation needs it.
  • T3 — 250 rps peak (1M req/day): size gateway replicas by p99 concurrency and downstream budgets, then add zonal HA, Redis HA, JWKS cache protection, retry budgets and dependency-specific breakers.
  • Waypoint — 2,500 rps peak (10M req/day):
    • test whether one regional fleet can still upgrade, warm and recover as a unit
    • this is often where cells or regional policy distribution become worthwhile.
  • T4 — 25,000 rps peak (100M req/day):
    • model roughly ten T3-to-waypoint cells plus routing, with per-cell gateway instances, local key/cache paths and regional isolation
    • the fleet-wide number is not a single process target.
  • JWT and JWKS:benchmark RS256 and ES256 verification at the target p99 with warm and cold key caches, token sizes and realistic concurrency; record cache-hit rate and unknown-kid refresh rate instead of inventing a constant.
  • Rate limiting:count one Redis atomic check, its retries and policy refresh operations per request, then reserve headroom for hot tenants and failover; measure Redis ops and latency under the actual key distribution.
  • Boundary trigger:move tier when connection acquisition, event-loop delay, 429/504 rate, retry amplification, JWKS/PDP latency or blast radius breaches the budget even if average CPU is below a target.
  • Judge each edge concern per tier rather than deploying the whole gateway feature set:
    • rate limiting is worth it at T1 and mandatory at T3
    • centralized token validation is worth it at T2 and mandatory at T3 once more than a couple of services would otherwise each implement it
    • a policy decision point is not needed at T1 and T2, worth it at T3, and needs its own scaling story at T4 alongside cell routing and per-cell key material.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Route configuration

route id, match predicates, destination, ordered filters, timeout, retry budget, auth mode, policy version and rollback owner; publish it as a validated immutable snapshot.

02Rate-limit counter

Redis key, policy version, refill rate, burst, weighted cost, expiry and decision timestamp; counters are disposable control state, not business truth.

03JWKS and token cache

issuer, key id, public key, algorithm, fetched_at, expires_at and refresh status; cache public verification material and never private keys or bearer tokens.

04Policy and rule store

tenant, principal, action, resource class, policy version, bundle checksum and activation window; a PDP decision is reproducible only when its input and version are known.

05Identity assertion

subject, tenant, audience, scopes, issue time, expiry, key id and route context; services verify the assertion before using it and reject a client-created equivalent.

06Audit log

decision id, principal pseudonym, tenant, action, route, policy/key version, outcome, reason code and trace id; exclude tokens, secrets and unnecessary payload data.

07Capacity and health budget

route, cell, instance, connection limits, queue age, dependency state, warm-up phase and last-known-good config; it drives admission and safe scale-in.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01CDN and L4 boundary

terminate or pass through transport concerns, cache safe public bytes and shed obvious abuse before the application gateway; do not put object authorization here.

02Spring Cloud Gateway 5.0.4

use the selected Server WebFlux or Server Web MVC starter from the 2025.1.4 release train, and keep route predicates, ordered filters and effective configuration under test.

03Runtime baseline

use a supported Java LTS and verify vendor patch support against the selected Boot/Cloud train; JDK 25 is the current LTS reference at review time, not a throughput assumption.

04Resilience4j 2.4.0

use CircuitBreaker, TimeLimiter and RateLimiter concepts for local protection, but choose one retry/breaker owner per hop and avoid hiding distributed state behind an in-process default. 2.4.0 is the release that adds Spring Boot 4 support via the separate resilience4j-spring-boot4 starter.

05Redis rate limiter and cache

use atomic token-bucket checks, short-lived policy/JWKS metadata and bounded decision cache; isolate limiter state by region or cell when a global store becomes a failure amplifier.

06Identity provider and keys

use OAuth/OIDC discovery, short-lived access tokens, overlapping signing keys and regional JWKS availability; validate issuer, audience, algorithm and time at the consumer boundary.

07PDP

use OPA/Rego, Cedar or a service-local policy module only for decisions that need dynamic context; version bundles, cache with a stated staleness bound and keep the service invariant local.

08Internal protocols

keep public REST at the north-south contract, use gRPC when a measured east-west need justifies it, and use a durable message broker for work that does not belong on the request path.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

Nginx route guard + leaky-bucket limit

Use the gateway for coarse admission; the downstream service still owns resource authorization.

nginx
http {
    limit_req_zone $binary_remote_addr zone=api_per_ip:10m rate=10r/s;

    server {
        location /api/ {
            auth_request /_verify;
            limit_req zone=api_per_ip burst=20 nodelay;
            proxy_set_header X-Request-Id $request_id;
            proxy_pass http://checkout_pool;
        }

        location = /_verify {
            internal;
            proxy_pass http://identity_verifier;
            proxy_pass_request_body off;
            proxy_set_header Content-Length "";
            proxy_set_header X-Original-URI $request_uri;
        }
    }
}

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
Gateway verification vs service verification

verify at both boundaries for defense in depth, but give the gateway coarse rejection and the service final resource authorization; measure the duplicated crypto cost.

02
JWT vs opaque introspection

JWT keeps the hot path local and survives a bounded IdP outage, while opaque tokens give fresher revocation at the price of an IdP dependency and a cache-staleness contract.

03
Roles in token vs PDP

token roles are cheap and portable but stale; a PDP handles dynamic resource context but needs availability, policy rollout, decision caching and audit ownership.

04
Sync vs async hop

synchronous calls preserve an immediate answer but multiply tail latency and retry work; queues smooth load and isolate failure but owe idempotency, ordering, DLQ, lag and a pending contract.

05
Smart gateway vs thin gateway

domain-aware routing can reduce client hops, but fetching business data at the edge duplicates service ownership, increases blast radius and makes policy evolution harder.

06
Global state vs cells

one limiter, IdP cache or PDP is simple to reason about initially, while regional or per-cell state limits blast radius but adds quota transfer, key distribution and reconciliation work.

07
Central config vs local autonomy

a central snapshot gives consistent policy and rollback, while local cached data keeps the data plane alive during control-plane failure; both require version, expiry and last-known-good behavior.

Failure review — answers for this design
01

Which invariant can break when the gateway or IdP is unhealthy?

A valid identity must never become a valid domain action by itself.

  • The service remains the authority for tenant, object and state invariants
  • gateway and IdP failures may reject or degrade a request, but they cannot authorize a client-supplied header or bypass the service check.
02

Which metric detects the edge boundary before users see an outage?

Start with route-level p99, pending connection acquisition, event-loop delay, 429/504 rate, retry amplification, JWKS/PDP latency and usable downstream pool. The first saturated dependency—not aggregate gateway CPU—sets the next action and the blast radius.

03

How is the blast radius contained when one route, cell or identity dependency fails?

Scope breakers, limits, pools, caches and policy bundles by route, tenant, region or cell. Fail closed for high-risk actions, serve only explicitly bounded stale reads, and keep last-known-good route and key material so one control-plane failure cannot erase every data-plane decision.

04

Can retry duplicate or reorder an external effect?

Yes: a gateway timeout does not prove that the service or provider did nothing. Retry only safe operations or carry an idempotency key, keep one retry owner per hop, and use an explicit pending/unknown state with reconciliation for payment or other irreversible effects.

05

What evidence proves recovery after key, Redis, PDP or gateway-cell loss?

Restore the last-known-good configuration, refresh keys with overlap, rebuild disposable counters and replay policy safely, then verify route error budget, queue age, key refresh, decision consistency and reconciliation debt. Recovery is proven only when the degraded contract ends without an unexplained authorization or business-state transition.

Engineering deep dives

Reliability, overload and recovery

Reliability is a user-visible contract. Capacity, retries and failover must be designed as bounded control loops rather than emergency switches.

Prevent positive feedback

  • Give every call an end-to-end deadline; derive shorter per-hop timeouts from the remaining budget and cancel work the caller no longer needs.
  • Retry only classified transient failures, cap attempts, add exponential backoff with jitter and enforce a retry budget so recovery traffic cannot become the outage.

Degrade deliberately

  • Use admission control, bounded queues, concurrency limits and load shedding before saturation; queue depth without oldest-age is not enough to see stalled work.
  • Define which features fail closed, fail open, serve stale data or become read-only. Test the degraded contract with dependency latency, partial-region loss and bad configuration.

Prove recovery

  • Set RTO and RPO per journey, automate restore/failover where safe, and regularly restore production-shaped backups into an isolated environment.
  • Roll out by canary or cell, compare user SLIs, and keep rollback independent of the failing control plane. A failover plan that has never been exercised is an assumption.

Policy and distributed enforcement

A limiter protects a scarce resource; its key, cost model and failure mode matter more than the counter algorithm.

Model the budget

  • Scope by authenticated tenant/user/API key before IP where possible. Charge weighted cost for expensive queries instead of pretending every request costs one token.
  • Separate sustained rate, burst capacity and concurrency. Version policy and shadow new rules before enforcement to measure false positives.

Bound distributed error

  • Use atomic server-side updates for a precise shared bucket; use local token leases only when bounded overshoot is acceptable and measurable.
  • Choose fail-open or fail-closed per endpoint. Authentication, checkout and public reads have different abuse risk and availability cost.

Operate the control

  • Track allowed, rejected and shadow decisions by policy version plus limiter latency, hot keys and degraded-mode duration—without putting user IDs in metric labels.
  • Return a stable error contract and Retry-After where meaningful; combine rate limits with quotas, bot controls and origin concurrency protection.

Identity controls at the gateway boundary

Authentication, authorization and key distribution are separate decisions. The edge can reject cheap failures early, but a service must still own its resource invariant and trust boundary.

Verify the token, then verify the context

  • Validate issuer, signature algorithm, key id, audience and time claims before using a JWT. A cached JWKS is verification material, not proof that a user may access a particular object.
  • Use the gateway for coarse route policy and let the resource service verify the original token or a signed internal assertion. Strip client identity headers before adding trusted context.

Treat keys and policy as dependencies

  • Refresh an unknown key id once with backoff, overlap old and new signing keys during rotation, and keep the last valid key set only for the documented degraded window.
  • Cache policy decisions with a key that includes principal, tenant, action, resource class and policy version. A stale allow is a security decision, not an ordinary cache hit.

Choose degraded behavior per risk

  • Short-lived JWTs can keep low-risk reads available during a bounded IdP outage; high-risk writes should fail closed when introspection or policy evidence is unavailable.
  • Measure verification p99, JWKS miss and refresh rates, PDP latency, deny/allow changes and key-id distribution. These signals reveal an identity bottleneck before a global gateway outage.

How do you turn 10k, 100k, 1M and 100M requests a day into the peak rate the edge is sized for, and what does one extra hop cost at each tier?27-api-gateway-identity-edge.the-edge-in-four-sizes.q1

Start with average traffic: requests per day divided by 86,400. For a consumer or campaign workload, use roughly a 20× peak heuristic and state that it is an assumption, not a capacity guarantee.

  • T1: 10k req/day is 0.12 average rps, so plan around 2.5 peak rps. One gateway hop is mostly a routing and connection-management choice; a second proxy is usually more operational cost than capacity benefit.
  • T2: 100k req/day is 1.2 average rps, so plan around 25 peak rps. A shared gateway can add authentication, rate limiting and metrics, but measure p99 latency with the real payload and TLS path.
  • T3: 1M req/day is 11.6 average rps, so plan around 250 peak rps. Replicas, connection pools, distributed limits and dependency budgets matter; a hop also consumes sockets and retry budget.
  • T4: 100M req/day is 1,157 average rps, so plan around 25,000 peak rps. Treat it as cells or regional slices, not one giant gateway cluster; each cell should be a T3-to-waypoint system plus routing.

The 10M/day waypoint is about 116 average rps and 2,500 peak rps. It is often where a single regional fleet becomes a cell design. The same 1M/day anchor appears in (→ A travel marketplace receives 1M requests/day, a 100:1…); keep the arithmetic consistent.

An extra hop costs more than its median processing time: it adds queueing, a connection pool, health state, tracing spans, timeout accounting and another failure boundary. Set a per-hop latency budget, then load-test p99 and saturation.

For internal or B2B traffic with a measured 3–5× concentration, do not blindly apply 20×. Recompute from the arrival trace and keep the peak assumption beside the decision.

Sizing card — declare these inputs before choosing a tier:

  • Arrival: measured peak rps, burst duration, open-loop model, and tenant/route skew.
  • Request shape: payload size, compression, streaming ratio, and HTTP version.
  • Connections: new TLS rate, keep-alive reuse, upstream pool and connection-acquisition p99.
  • Identity/dependencies: JWT or opaque-token mix, JWKS/introspection hit rate, PDP calls, and downstream concurrency.
  • Contract: end-to-end p99/p999 deadline, accepted overage, retry budget, and failure mode.

The T1–T4 labels are scenario names, not hard capacity breakpoints. Keep the measured inputs and the 20× multiplier beside the sizing decision.

Edge contract:

For each route, record the owner, trusted ingress, identity source, authorization owner, per-hop deadline, retry budget, error contract, and rollback owner.

What would change this answer — state these before defending the design; each is an assumption the interviewer can ask you to justify, and a measurement that would falsify it:

  • The gateway implementation and release train in scope — Spring Cloud Gateway WebFlux, Envoy, a managed edge, a Kubernetes Gateway API implementation, or a combination.
  • Whether it is public, private, mesh-local or all three, with the paths that can bypass it and the owner of each trust boundary.
  • The p99 and p999 end-to-end deadline, connection reuse, payload, token mix and downstream concurrency targets at each tier.
  • Which routes carry mutations where a 504 can mean "committed but unknown", and the idempotency-key or status-lookup contract behind them.
  • The maximum JWT, JWKS, PDP or policy-cache staleness after a revocation or emergency deny.
  • Whether IdP, introspection or PDP failure fails closed, serves a bounded cached read, or enters an explicit degraded mode per route class; the policy runtime, bundle delivery, decision cache and version, and who can roll it back.
  • What falsifies the edge boundary: gateway p99 eating more than its hop budget, a shared pool failure taking down unrelated routes, or an internal identity header accepted from direct service ingress, batch workers or cross-region calls that were never tested.
At each traffic tier, which edge capability is not needed, worth it, mandatory, or needs its own scaling story?27-api-gateway-identity-edge.the-edge-in-four-sizes.q2

Use the same four verdicts for every control: not needed means the operating cost dominates, worth it is cheap insurance, mandatory prevents a predictable incident, and needs its own scaling story means a config line is no longer enough.

  • T1 — 10k/day: CDN for public static assets is worth it; a managed gateway can route and authenticate. A distributed Redis limiter, PDP and multi-region identity plane are usually not needed.
  • T2 — 100k/day: rate limiting, timeout budgets, circuit breaking and route-level RED metrics are worth it. Keep identity verification local to the gateway and services; a separate policy service is not mandatory unless policy churn or audit requires it.
  • T3 — 1M/day: gateway replicas across zones, bounded connection pools, a shared limiter, JWKS cache, trace propagation and dependency isolation are mandatory. IdP failover, policy decision caching and asynchronous audit may need their own scaling story.
  • T4 — 100M/day: cells, regional routing, independent gateway fleets, regional identity/key distribution, policy bundles and blast-radius controls need their own scaling story. A single global Redis limiter or one global PDP is a hidden critical path.

The verdict is about the failure model as well as rps. A low-volume payment API may require stronger isolation than a high-volume anonymous read. State the protected resource, its abuse cost and the owner before selecting the control.

Which signals say a tier boundary has been crossed before the incident does?27-api-gateway-identity-edge.the-edge-in-four-sizes.q3

A tier boundary is crossed when the current shape cannot meet its SLO with ordinary headroom, not when a dashboard has a round number. Look for several signals moving together:

  • Queueing: gateway event-loop delay, upstream connection acquisition, pending requests and p99 latency rise while average CPU still looks healthy.
  • Dependency pressure: usable connection pools, Redis operations, JWKS refreshes, PDP latency and downstream concurrency approach a hard budget.
  • Failure feedback: 429, 5xx, 504, retry/original ratio, circuit-open time and client cancellation increase; adding replicas no longer lowers the tail.
  • Blast radius: one tenant, route, region or identity provider incident consumes shared pools or makes unrelated routes fail.

At the 10M/day waypoint, ask whether a single fleet can still be upgraded and recovered as one unit.

Near T4, ask whether a cell can fail without taking the region with it.

Define the next action before the threshold: increase capacity, split a pool, introduce admission control, move to cells or isolate a dependency.

Benchmark with production-shaped payloads, token mix, cache hit rate and retry behavior. A synthetic open-loop rps number that omits connection churn can postpone the boundary until the incident.

In Spring Cloud Gateway, what does a request pass through in route, predicate and filter order, and where should authentication sit?27-api-gateway-identity-edge.gateway-configuration-that-matters.q1

A route is a destination plus an ordered filter chain.

Predicates decide whether the route matches; filters transform the request or response, enforce policy, and forward or short-circuit it.

The exact ordering is part of the contract, so inspect the effective route rather than relying on the order in a YAML file.

Authentication belongs before the request reaches a protected service, but it does not have to be the first operation.

Reject malformed or oversized input early, establish correlation and trace context, then authenticate before route-specific authorization and forwarding.

Do not let a rewrite or a client-controlled header change the identity that is verified.

Spring Cloud Gateway 5.0.4 documents distinct Server WebFlux and Server Web MVC starters: spring-cloud-starter-gateway-server-webflux and spring-cloud-starter-gateway-server-webmvc.

The WebFlux server is built on WebFlux, Reactor and Netty; choose the server flavor deliberately instead of copying the older spring-cloud-starter-gateway artifact into a new build.

Record the chosen release train in the build and test the actual filter order.

Use a supported Java LTS runtime; at this review JDK 25 is the current LTS reference. Verify vendor patch support against the selected Spring Boot/Cloud train before rollout.

The gateway may make a coarse decision such as scope=orders:read and route ownership. The service still authenticates the caller at its own trust boundary and performs object-level authorization. This is the edge-specific application of (13-security-oauth2.designing-the-auth-system.q1).

Effective-chain regression: pin the gateway server flavor and release, then render or inspect the effective chain.

Assert the expected order for a normal request, an authentication rejection, an oversized body, and a rewrite. The YAML order is configuration input, not a portable proof of runtime order.

How should gateway, downstream and client timeouts relate, and why is the edge the fastest place to build a retry storm?27-api-gateway-identity-edge.gateway-configuration-that-matters.q2

Give the client an end-to-end deadline, then spend it from the outside in.

The gateway deadline must leave time for response handling, while each downstream deadline is shorter than the gateway budget and includes connection acquisition.

A client retry deadline must not cause a fresh request after the server has already committed an effect.

A retry budget limits retries as a fraction of original traffic over a window.

Retry only errors that are classified transient, only when the operation is safe or idempotent, and add exponential backoff with jitter.

A gateway retry multiplies every downstream hop, so a 2× retry at two layers can approach 4× work before the client is counted.

Keep retries at one deliberate owner for a hop.

The gateway should normally retry a new connection failure or a bounded 502 before bytes reach the service; it should not blindly replay a timed-out POST.

Carry an idempotency key when replay is part of the contract.

The mechanism and storm failure modes belong to (25-microservice.01-cascading-failure-retry-storm.q5); this edge question is about the budget and filter placement.

Return a stable timeout/overload contract. 504 means the gateway did not receive a usable upstream response inside its deadline; it does not prove that the service did nothing.

Spring Cloud Gateway 5.0.4 timeout shape (values are illustrative):

spring:
  cloud:
    gateway:
      server:
        webflux:
          httpclient:
            connect-timeout: 500   # milliseconds
            response-timeout: 2s   # global Duration
          routes:
          - id: orders
            uri: http://orders.internal:8080
            predicates:
            - Path=/api/orders/**
            metadata:
              connect-timeout: 300 # per-route milliseconds
              response-timeout: 1500

Load-test a slow upstream and verify the gateway stops near its 1.5-second route budget while the external client deadline leaves response margin.

  • Benefit: bounded pool occupancy and a predictable tail.
  • Cost: a tight value creates false timeouts and retries; cancellation does not undo a committed downstream effect.
  • Replay rule: do not retry this POST route unless its idempotency contract supports replay.

How do CircuitBreaker and RequestRateLimiter filters change gateway behaviour, and what is the per-tier verdict?27-api-gateway-identity-edge.gateway-configuration-that-matters.q3

A CircuitBreaker filter must be scoped to a route or a deliberately grouped dependency.

Its failure predicate, sliding window, minimum calls, failure/slow-call thresholds, open wait and half-open probe count decide when traffic stops; a shared breaker for unrelated routes turns one bad backend into a larger outage.

Open should return a documented 503 or a safe fallback, with a metric that names the route and cause.

RequestRateLimiter needs a stable KeyResolver, a cost model and a burst policy.

With the Redis token-bucket implementation, replenishRate is sustained tokens per second, burstCapacity is the bucket, and requestedTokens lets an expensive operation spend more than one token.

The Redis check is a distributed dependency, not magic capacity.

Return 429 and Retry-After only when the delay is meaningful and derived from policy; make the client contract explicit.

  • T1: local or managed rate limiting is worth it; a shared Redis limiter is not needed unless abuse risk demands it.
  • T2: route-level limits and a breaker are worth it; keep policies few and inspectable.
  • T3: per-tenant or weighted limits, Redis HA, breaker isolation and retry budgets are mandatory.
  • T4: limiter state, policy distribution and breaker ownership need their own scaling story, usually per cell or region.

Resilience4j 2.4.0 exposes the same conceptual controls in-process, but a gateway filter still has to choose route scope and distributed state.

2.4.0 is also the release that adds Spring Boot 4 support, through a separate resilience4j-spring-boot4 starter. Confirm the BOM actually resolves that artifact for the Spring Cloud train you pinned rather than assuming the umbrella dependency covers it.

The breaker state machine and its parameter set are owned by (25-microservice.01-cascading-failure-retry-storm.q3); what the edge adds is route scope and a distributed limiter.

Do not paste service-level defaults into the edge; compare the edge decision with (→ Which limits belong at the edge, gateway, service, and…).

What connection-pool and request-hygiene settings matter at the edge, and what must the gateway strip or never trust?27-api-gateway-identity-edge.gateway-configuration-that-matters.q4

Netty connection pools trade sockets and memory for reuse.

Size pending acquisition, max connections, keep-alive and idle eviction from measured upstream concurrency and service limits, not from gateway replica count.

A pool that is too small queues at the edge; one that is too large moves the queue into the database or partner.

Set an explicit maximum body and header size, reject malformed framing, and choose buffering only when a filter actually needs the body.

A large upload or response held in memory can turn one request into a heap incident.

CORS is a browser contract, not an authorization control; allow only the origins and methods the product owns.

Strip inbound identity and routing headers before adding trusted values. X-Forwarded-*, user, tenant, role, internal route and correlation headers are untrusted when supplied by the client.

Rebuild them from the verified connection, token and gateway trace context.

Preserve only the headers the downstream contract needs.

Keep-alive and idle eviction must match load balancers and services.

After scale-out, a fleet of cold instances can create a connection storm; warm pools gradually and watch connect rate, pending acquisition, event-loop delay and upstream resets.

Configuration defaults change across Spring Cloud Gateway and Netty versions, so verify the selected 5.0.4 line and benchmark the deployment.

Who verifies the token: gateway only, service only, or both? What does each choice cost and leave open?27-api-gateway-identity-edge.identity-at-the-edge.q1

Gateway-only verification is cheap for the service path and centralizes rejection, but it makes the gateway a trusted security oracle. A bypass, misroute or internal caller that reaches the service can skip the check unless the service has another boundary.

Service-only verification keeps the resource owner authoritative and supports calls that do not traverse the edge, but every service pays verification cost and must implement consistent issuer, audience, key and time validation. It also lets bad traffic consume more downstream work before rejection.

The practical default is both, with different jobs.

The gateway verifies the bearer token and applies coarse route policy; the service verifies the original token or a signed internal assertion, then performs tenant and object authorization.

Cache public keys, not an unbounded authorization decision.

If a service trusts a gateway-issued identity, bind it to audience, expiry, route and a key the service validates; never trust a conventionally forwarded header.

This is defense in depth, not permission to configure two independent policy engines that disagree. Define one owner for each decision and measure the added p99 verification cost. The identity provider and token contract are covered in (13-security-oauth2.designing-the-auth-system.q1).

How should the edge verify a JWT, including JWKS fetch, kid rotation, clock skew, iss, aud and exp?27-api-gateway-identity-edge.identity-at-the-edge.q2

Treat a JWT as untrusted bytes until all relevant checks pass.

Decode only to select a candidate key; verify the signature with an allowed algorithm, then validate iss, aud, exp, nbf and the token type/scope required by the route. kid selects a key inside the issuer's JWKS; it is not an authorization decision.

Cache the issuer metadata and JWKS with bounded freshness.

On an unknown kid, refresh once with backoff and protect the refresh path from a key-id spray.

Keep old and new signing keys available during a rotation overlap.

If the JWKS endpoint is unavailable, continue only with a still-valid cached key under a documented risk policy; do not accept an unverified token because the IdP is down.

Allow only measured clock skew.

A generous skew extends token lifetime and weakens revocation, while zero skew rejects legitimate requests near a boundary.

Reject issuer confusion and algorithm substitution; RFC 8725 is the normative JWT guidance.

OpenID Connect Discovery defines the issuer and jwks_uri relationship, and Spring Security's resource-server reference describes the validation sequence.

Signature verification is not a fixed number of microseconds. RS256 versus ES256, token size, JIT state, key cache hit, CPU generation and concurrency change it. Benchmark accepted and rejected tokens at the target p99, then budget the result per tier.

Minimal reactive resource-server boundary with issuer, audience and route scope:

# application.yml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://idp.example.test/realms/prod
          audiences: api://edge
@Bean
SecurityWebFilterChain security(ServerHttpSecurity http) {
  return http.authorizeExchange(auth -> auth
          .pathMatchers("/actuator/health").permitAll()
          .pathMatchers(HttpMethod.GET, "/api/orders/**")
            .hasAuthority("SCOPE_orders.read")
          .anyExchange().authenticated())
      .oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()))
      .build();
}

Test three paths: no token → 401; valid signature but wrong issuer/audience → 401; valid token without orders.read → 403.

  • Benefit: signature and cached-JWKS verification stay local while key rotation remains discoverable.
  • Cost: local JWT acceptance lasts until expiry; logout/revocation needs short TTL or another mechanism.
  • Boundary: the service still owns object-level authorization.
When does opaque-token introspection make sense, and how should identity be passed inward without trusting a client header?27-api-gateway-identity-edge.identity-at-the-edge.q3

Opaque tokens give the authorization server a live revocation point, but every cache miss creates an IdP dependency and a latency tail.

Cache introspection only with a TTL shorter than the token's accepted lifetime and an explicit fail-open or fail-closed rule.

JWT verification pays local crypto cost but can remain valid after logout until expiry or another revocation mechanism acts.

Token relay is simple: the service receives the original bearer token and verifies it.

It preserves the original issuer/audience semantics but spreads token handling and sends a user credential across more hops.

A signed internal claim is narrower: the gateway signs sub, tenant, scopes, route audience, issue time and expiry for the service.

The service verifies that assertion and rejects a token made for another service.

Never accept X-User, X-Tenant or X-Roles from the public request.

Strip them at the edge, add trusted identity only after verification, and use mTLS or a workload identity between gateway and service so an arbitrary internal process cannot forge the channel.

A header is a transport representation; the signature and trust path are the boundary.

Choose per route. High-risk money actions may prefer live introspection or service-local verification; high-volume reads may use short-lived JWTs and cached keys. The trade-off is the subject of (13-security-oauth2.jwt-tokens.q2), not a reason to duplicate its token taxonomy here.

JWTLocal verification after a warm key cacheExpiry, issuer/audience checks, and service-side resource authorization
Opaque introspectionCentral freshness or revocation decisionIntrospection deadline, outage mode, and cache staleness bound
mTLS/SPIFFEWorkload-to-workload identityCredential rotation and end-user/application authorization

Accept forwarded identity only from a configured trusted proxy chain. Test public, private, direct-service, batch-worker and cross-region ingress separately.

Send forged X-User/X-Tenant/X-Roles headers and expect strip-or-reject behaviour. Rotate keys and verify that tokens, authorization headers and sensitive policy input are absent from logs and metric labels.

How should revocation, logout and IdP failure work at the edge, and what changes at each tier?27-api-gateway-identity-edge.identity-at-the-edge.q4

Short access-token TTL is the baseline revocation bound, not a logout guarantee.

A deny-list gives immediate invalidation but adds a read and an eviction/retention problem.

A BFF or edge session can hide tokens from a browser and centralize logout, but it creates session state and a high-availability edge store.

Choose from the risk of a stolen token, not from a generic security checklist.

When the IdP is unavailable, already cached JWKS can still verify an unexpired JWT; an introspection-only path cannot safely invent a positive answer.

Fail closed for money movement, privilege changes and sensitive reads.

A low-risk public or previously authorized read may serve a bounded stale session if the product explicitly accepts that risk.

Never fail open merely because the gateway wants availability.

Rotate keys with overlap: publish the new key before signing with it, accept both during the maximum token lifetime plus propagation margin, then retire the old key after observing zero legitimate use. Refresh unknown kid values once, rate-limit misses and alert on a sudden key-id distribution.

  • T1/T2: short JWT TTL plus cached JWKS is often worth it; a global deny-list is usually not needed for low-risk routes.
  • T3: regional IdP/JWKS redundancy, refresh protection and route-specific fail-closed policy are mandatory.
  • T4: identity, key distribution, revocation and session state need their own scaling story per region or cell.

RFC 9700 recommends modern OAuth security practices, but it does not choose the product's availability mode. That decision remains a route risk and business contract.

What may the gateway authorize coarsely, what must stay in the service, and where does tenant resolution belong?27-api-gateway-identity-edge.authorization-without-a-bottleneck.q1

The gateway can authorize decisions that are visible from the request contract: token is valid, route is in the audience, scope allows orders:read, method is permitted, and the caller is inside a coarse tenant or product boundary. These checks are useful before spending downstream capacity.

The service owns domain decisions: whether this user may read this order, whether the tenant owns the object, whether the account is suspended, and whether the requested state transition is legal.

The gateway should not fetch domain rows just to decide a policy; that turns it into a second application with a wider blast radius.

Resolve tenant from a verified claim, mTLS/workload context or an explicitly mapped host, then let the service confirm membership and object ownership.

A client-supplied tenant_id is only a request hint until it matches the authenticated subject's allowed tenancy.

Never use a URL path alone as proof of tenant identity.

Keep the same rule for gateway bypasses and east-west calls. The owner service must be able to enforce its invariant without assuming that a particular proxy was in the path. This is the gateway-specific application of (13-security-oauth2.designing-the-auth-system.q6).

Should roles live in the token or in a policy decision point such as OPA or Cedar, and what can decision caching safely accept?27-api-gateway-identity-edge.authorization-without-a-bottleneck.q2

Roles in a token are fast and available during an IdP outage, but they become stale until the token expires and are a poor fit for resource attributes or rapidly changing entitlements.

A PDP call can evaluate tenant, resource, action and context centrally, but it adds latency, availability coupling and a policy deployment path.

Use the token for stable coarse facts such as subject, tenant, audience and broad scopes.

Use a service-local check or PDP for dynamic roles, ownership, time, geography and resource state.

OPA/Rego or Cedar is a policy choice, not a replacement for a service's invariant; the service still supplies trustworthy input and owns the final state transition.

Cache a decision only with a key containing subject or principal, tenant, action, resource class, policy version and relevant context.

Set a TTL from the harm of stale allow, not from cache convenience.

Invalidate on role removal for high-risk actions, or choose a short fail-closed cache.

A stale deny usually costs availability; a stale allow can be a security incident.

Audit the decision without logging bearer tokens or sensitive payloads: principal pseudonym, tenant, action, resource class, policy version, decision, reason code, trace id and timestamp are usually enough. Record policy changes separately so an auditor can explain which rule produced an allow.

Roll out policy with a version/hash, shadow or compare decisions where safe, and alert when the active version differs across gateway replicas. A stale deny is normally an availability problem; a stale allow is a security problem, so the route owner must choose the failure mode per action.

What belongs at the CDN, L4 load balancer, gateway, mesh and service, and what happens when the same control is configured twice?27-api-gateway-identity-edge.introducing-a-gateway-into-a-running-system.q1

Give each layer a narrow owner:

  • CDN: cacheable public bytes, edge TLS and coarse abuse protection. It should not decide a private order's ownership.
  • L4 load balancer: anycast/health-based transport distribution and connection termination where appropriate.
  • Gateway: L7 route matching, external authentication, coarse authorization, public rate limits, request normalization and edge observability.
  • Mesh: east-west mTLS, service identity, traffic policy and transport-level telemetry when the organization can operate the control plane.
  • Service: domain authorization, invariants, idempotency and state transitions.

Duplicate controls do not automatically add safety.

Two retries multiply work, two timeouts create ambiguous ownership, two rate limiters make capacity unpredictable, and two identity transforms can disagree about the principal.

Put one owner and one contract in the design, then make other layers enforce only a compatible guardrail.

A CDN can reject obvious abuse before the gateway, and a service can reverify a token at its trust boundary. Those are complementary because they protect different resources. Cross-ref the general layered trade-off in (12-architecture-patterns.patterns-principles.q5).

How do you keep the gateway from becoming a single point of failure while migrating a running system?27-api-gateway-identity-edge.introducing-a-gateway-into-a-running-system.q2

Run at least N+1 healthy gateway capacity across failure domains, with no route depending on one instance, zone, configuration store or identity endpoint.

Health checks must test the gateway's ability to accept traffic, not synchronously fail every pod because a shared dependency is slow.

Keep a last-known-good route snapshot so a control-plane outage does not erase the data plane.

Treat routes, filters, policies and limits as code.

Validate them in CI, render the effective configuration, canary it on a small route/tenant/cell, compare RED metrics and keep a rollback that does not require the failing control plane.

Never roll out a gateway change and a backend contract change as one irreversible switch.

Migrate route by route: shadow or mirror safe reads, then send a small percentage of real traffic, expand by zone, and only remove the old path after logs and authorization decisions agree. Preserve the original correlation id and error contract during the transition.

At T1/T2 a pair across zones may be enough; at T3 multi-zone fleet and config validation are mandatory; at T4 each cell needs independent gateway capacity, policy distribution and rollback. The exact N comes from failure tests and warm-up time, not a universal replica count.

Shadow/cutover contract: every route has a named owner and configuration hash. Shadow traffic is read-only or side-effect isolated; it never sends a second mutation to a real provider.

During canary, compare route, authorization, status, latency, retry and error outcomes by route/tenant/cell. Roll back to the last-known-good hash before removing the old path, then keep a measured rollback window.

How do you operate the edge: trace propagation, correlation ids, RED metrics, 504 interpretation, warm-up and connection storms?27-api-gateway-identity-edge.introducing-a-gateway-into-a-running-system.q3

Propagate W3C trace context across HTTP and gRPC, create one gateway span per route, and preserve a bounded correlation id for logs.

Do not use raw user, tenant or URL values as metric labels.

Emit RED metrics—request rate, error rate and duration—by route, status class, outcome and region; keep high-cardinality detail in sampled logs and traces.

A gateway 504 says the gateway's deadline expired without a usable upstream response.

The service may still be running, may have committed an effect, or may have been rejected before execution.

Pair the metric with upstream connect time, response headers received, cancellation, retry count and an idempotency/reconciliation signal.

Treat it as a symptom, not proof of rollback.

After scale-out, cold JVMs, empty DNS/connection pools, JWKS refreshes and synchronized health checks can create a warm-up storm.

Pre-warm instances, gradually open connection limits, stagger refreshes, and gate readiness on measured local warm-up without making liveness depend on the entire dependency graph.

The operational owner must see route-level saturation before aggregate CPU. Use the autoscaling and gateway signals described in (25-microservice.08-operational-concerns.q3), then rehearse a 504, IdP outage and config rollback.

What decision rule chooses synchronous or asynchronous work per hop, and when is REST or gRPC worth the change?27-api-gateway-identity-edge.internal-calls-sync-async-or-neither.q1

Ask one question for every hop: does the caller need this answer to produce its own response or commit its next local decision? If yes, keep the hop synchronous, bound it with a deadline and make the failure visible.

If no, persist a command or event and return a durable pending state; the consumer now owes delivery, deduplication and observability.

REST is usually the cheaper boundary for public APIs, browser clients, heterogeneous teams and independently evolved contracts. gRPC is useful for controlled east-west calls where Protobuf contracts, generated clients, HTTP/2 multiplexing or streaming solve a measured problem.

It does not remove timeout, authorization, compatibility or load-shedding work.

Do not put an internal call through the external gateway merely to reuse a route. That adds public auth, edge limits, extra hops and a larger blast radius. Use service discovery or a mesh for east-west transport, and keep the service's authorization boundary intact.

The protocol comparison is owned by (04-rest-grpc-webflux.protocols.q2). This item applies that choice to a gateway topology and preserves the one-decision-per-hop rule.

What do you gain and owe when moving a hop onto a queue, and why must east-west traffic bypass the edge gateway?27-api-gateway-identity-edge.internal-calls-sync-async-or-neither.q2

A queue removes the producer from the consumer's immediate latency and failure path, smooths a burst and lets each side scale from its own signal. It also changes the user contract from a response to accepted/pending, and creates obligations:

  • durable command identity and idempotent consumers;
  • ordering only within the entity that needs it;
  • bounded retries, expiry and a visible DLQ;
  • backpressure, oldest-message age and consumer capacity;
  • schema compatibility, audit and reconciliation for external effects.

For a three-hop synchronous chain, approximate p99 as gateway overhead plus each hop's queueing, service and network tail.

If each service has 40 ms p99 and there are 2 ms of gateway/transport overhead, the optimistic serial budget is about 122 ms before retries; independent tail correlation and connection waits can make it worse.

Use a measured budget, not the sum of averages.

East-west calls should use mesh or service discovery because the external gateway is optimized for north-south policy: public auth, tenant quotas, route exposure and edge protection.

Sending service A through it to reach service B duplicates controls, consumes public capacity and lets an edge outage take down internal recovery.

The sync/async failure semantics are expanded in (25-microservice.10-system-design-putting-it-all-together.q2); here the decisive boundary is the caller's need for an immediate answer.

How should an edge route large uploads and asynchronous jobs without hiding failure?27-api-gateway-identity-edge.internal-calls-sync-async-or-neither.q3

The edge should enforce cheap, uniform controls: authenticated ownership, size and decompression limits, deadlines, rate/concurrency budgets, and clear 413 or 429 responses.

For a large body, stream or redirect to an authorized upload session. Do not buffer and replay it through every gateway replica.

For an asynchronous command, the edge must not return 202 merely because a downstream call was started.

Before 202, the service must durably record the command or upload completion, return a stable operation identity, and expose a status or inquiry path. A gateway timeout after forwarding bytes is UNKNOWN until that path is checked.

Do not add broad automatic retries around a non-replayable body or a mutation.

The API resource owns completion, idempotency and reconciliation. The gateway owns hop budgets, observability, request hygiene and traffic protection. Internal workers should use service discovery or a private mesh, not route back through the public edge.
