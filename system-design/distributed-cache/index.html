Scope and problem framing

Provide low-latency get/set/delete with TTL across a changing cluster. Decide consistency, replication and eviction semantics and protect the origin during node loss, rebalance and cold start.

Requirements

Functional requirements

  • Serve a get, set and delete for an opaque key across a cluster, routing a key to its owning node without a central lookup on the hot path.
  • Expire entries by TTL and evict under memory pressure by an explicit policy, rather than letting the process decide by failing.
  • Rebalance ownership when a node joins or leaves, moving the minimum number of keys and continuing to serve during the move.
  • Expose enough per-key and per-node telemetry that a hot key, a mass expiry and a rebalance are distinguishable from each other in an incident.

Quality attributes

  • A cache miss must be slower, never wrong. Serving a stale value after an explicit delete is the failure mode that turns a cache into a correctness problem.
  • The cache is an optimization and the system must have a defined behaviour without it — degraded, slower, rate-limited, but defined.
  • Node loss costs the keys that node owned and nothing else. A design where losing one node invalidates the cluster has traded the whole benefit away.
  • Tail latency matters more than average:the point of the cache is the p99 of the path behind it, so a cache with a good mean and a bad tail has not done its job.

Capacity and constraints

  • Size the cluster by operation peak with the daily volume beside it: ~250 rps peak (1M ops/day) at T3 and ~25,000 rps peak (100M ops/day) at T4. Cache traffic follows the application it fronts, so its peak factor is the application's — 10–20× for consumer traffic, 3–5× for internal services.
  • Memory is sized from unique active keys and the value size distribution, not from the total key space. The working set is almost always a small fraction of the corpus, and measuring it is cheaper than guessing generously.
  • Size for replication, fragmentation, headroom and rebalance rather than the payload sum. A cluster planned at its payload size has no room to move a partition and will evict at exactly the moment a node is being replaced.
  • Judge client-side local caching per tier:not needed at T1 and T2, where a network round trip to the cache is already fast enough; worth it at T3 for a small set of very hot keys; mandatory at T4 for the hottest keys, because a single key's traffic can exceed what one node can serve regardless of cluster size; needs its own scaling story wherever local copies need invalidating, since that is a fan-out problem of its own.
  • Model the cold start separately:after a full restart every request is a miss, so the origin briefly takes the traffic the cache normally absorbs. If the origin cannot survive its own uncached load, the cache is load-bearing and must be warmed before it takes traffic.
  • Budget mass expiry. A batch of entries written together expires together, so a nightly job that populates a million keys with the same TTL has scheduled a stampede — jitter the TTL rather than discovering this in production.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Entry

binary key and value, a version or CAS token, creation and expiry metadata. The version is what makes a compare-and-set possible and what lets a client detect that it lost a race.

02Cluster map

node identity, token or slot ownership, health, generation and replica placement. Clients cache it and refresh on a redirect, which is what keeps routing off the hot path.

03Key namespace convention

the entity, its id and a version segment. A version in the key turns invalidation into a write of a new key rather than a delete that has to reach every replica.

04Eviction telemetry

policy, memory class, key and value size bucket and a bounded reason code. Bounded, because per-key eviction metrics are how a cache melts the metrics system instead.

05Hot key registry

the small set of keys currently exceeding a per-key threshold, which is the input to local caching and to replica promotion.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01Consistent hashing or a slot map for ownership

both move a minimal share of keys when membership changes, which is the entire reason not to use a plain modulo over node count.

02Client-side routing with a cached cluster map and redirect handling, so a get is one network hop. A proxy tier is simpler to operate and adds a hop to every operation

pick it for operational reasons, not for performance ones.

03Cache-aside as the default pattern with…

Cache-aside as the default pattern with a versioned key, so an update writes a new key and readers move to it. Write-through couples the cache to the write path and makes a cache outage a write outage.

04Single-flight or probabilistic early expiry in front of the origin

without it a hot key expiring means every concurrent reader misses at once and the origin takes the full fan-in.

05An admission policy, not just an…

An admission policy, not just an eviction policy. Plain LRU admits everything and lets a large scan evict the working set; a frequency-aware admission filter keeps a one-off scan from displacing keys that are actually hot.

06Observability

hit ratio by namespace, evictions by reason, p99 split by hit and miss, per-node memory and key count, rebalance progress, and the age of the oldest key in each namespace.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

Cache-aside with a versioned key

Write the origin first and version the key so stale values cannot overwrite a newer product snapshot.

bash
key=product:42:v17
value=$(redis-cli --raw GET "$key")

if [ -z "$value" ]; then
  value=$(psql -At catalog.sql -c "SELECT jsonb_build_object('id', id, 'price', price) FROM product WHERE id = 42")
  redis-cli SET "$key" "$value" EX 30 NX
fi

printf '%s\n' "$value"

Runbash cache-aside.sh

Collapse the stampede on a hot key

Abridged. Without the single-flight, a hot key expiring sends every concurrent reader to the origin at the same instant — the miss is cheap, the fan-in is not.

java
Value get(String key) {
    Value hit = cache.get(key);
    if (hit != null && !hit.nearExpiry()) return hit;

    // probabilistic early refresh: one reader renews slightly before expiry so the
    // key is never simultaneously missing for everyone
    if (hit != null && !shouldEarlyRefresh(hit)) return hit;

    // one loader per key per process; the rest wait on the same future rather
    // than each issuing their own origin call
    return inFlight.computeIfAbsent(key, k -> CompletableFuture.supplyAsync(() -> {
        Value fresh = origin.load(k);
        cache.put(k, fresh, ttlWithJitter());   // jitter: batch writes must not expire together
        return fresh;
    })).whenComplete((v, e) -> inFlight.remove(key)).join();
}

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
Delete-on-update is immediate and racy

a reader that missed just before the delete can write a stale value back afterwards. A versioned key sidesteps the race entirely and costs key-space growth plus a way to reclaim the old versions.

02
A short TTL bounds staleness and…

A short TTL bounds staleness and raises the miss rate; a long TTL protects the origin and extends the window in which a delete has not taken effect everywhere. TTL is the staleness contract, so state it in the design rather than tuning it later.

03
Replicating a hot key spreads its…

Replicating a hot key spreads its read load and multiplies the invalidation problem by the replica count. It is the right answer for a genuinely hot key and the wrong default for all of them.

04
LRU is simple and is the…

LRU is simple and is the wrong policy under a scan; LFU keeps the hot set through a scan and reacts slowly when the hot set legitimately changes. The admission filter is usually a better lever than swapping the eviction policy.

05
Making the cache durable removes the…

Making the cache durable removes the cold-start problem and makes the cache a database with a different failure model, including a recovery time you must now care about. Warming is usually the cheaper answer.

06
A cache that the system cannot…

A cache that the system cannot run without is not a cache, it is an in-memory database with no durability story. Deciding which one you have is a design decision, and pretending it is the former while operating the latter is how a cache outage becomes a full outage.

Failure review — answers for this design
01

Which invariant can break?

A value served from the cache must be one the origin actually produced, and an explicit invalidation must not be undone by a slower reader. The second is the real hazard: a reader that missed before a delete can populate the cache with the pre-delete value after it.

02

Which metric detects it first?

Hit ratio by namespace and evictions by reason, read together. A scan that is displacing the working set shows as a hit-ratio drop with a spike in size-based evictions long before latency on the origin path becomes visible.

03

How is the blast radius contained?

Ownership is per key, so a node loss costs its own share and triggers a bounded rebalance. The origin is protected by single-flight and by TTL jitter, and the application has a defined degraded behaviour without the cache at all.

04

Can retry duplicate or reorder work?

Reordering is the entire risk.

  • A retried set can land after a newer set and silently roll the value back, which is what compare-and-set tokens and versioned keys exist to prevent.
  • A retried get is harmless.
05

How do we repair and prove recovery?

Flush the affected namespace and let it refill, warming the known-hot keys first so the origin is not asked to serve a cold cluster at peak. Recovery is proven when hit ratio returns to its namespace baseline, eviction reasons are back to TTL rather than memory pressure, and a sampled set of keys matches the origin value.

Engineering deep dives

Caching as a bounded copy

A cache is a disposable, stale copy with a failure mode. Its key, TTL and origin-protection plan are part of correctness.

Choose what may be stale

  • Include tenant, authorization dimension and schema version in keys. Never cache a security or monetary decision unless the product defines acceptable staleness.
  • Use cache-aside for simple reads, versioned keys for safe rollout and randomized TTLs to avoid synchronized expiry; cap negative-cache lifetime.

Protect the origin

  • Coalesce concurrent misses, refresh hot values ahead of expiry and bound rebuild concurrency. A cache outage must not instantly multiply origin load by the hit ratio.
  • Monitor hit ratio by key class, eviction, memory fragmentation, hot keys, fill latency and origin amplification—not only cache latency.

Compare tiers

  • L1 removes a network hop but multiplies stale copies; shared L2 centralizes data and invalidation but adds a network dependency and hotspot risk.
  • Choose LRU/LFU/TTL from access distribution and object value. If eviction loses authoritative state, the component is a database wearing a cache label.

Reliability, overload and recovery

Reliability is a user-visible contract. Capacity, retries and failover must be designed as bounded control loops rather than emergency switches.

Prevent positive feedback

  • Give every call an end-to-end deadline; derive shorter per-hop timeouts from the remaining budget and cancel work the caller no longer needs.
  • Retry only classified transient failures, cap attempts, add exponential backoff with jitter and enforce a retry budget so recovery traffic cannot become the outage.

Degrade deliberately

  • Use admission control, bounded queues, concurrency limits and load shedding before saturation; queue depth without oldest-age is not enough to see stalled work.
  • Define which features fail closed, fail open, serve stale data or become read-only. Test the degraded contract with dependency latency, partial-region loss and bad configuration.

Prove recovery

  • Set RTO and RPO per journey, automate restore/failover where safe, and regularly restore production-shaped backups into an isolated environment.
  • Roll out by canary or cell, compare user SLIs, and keep rollback independent of the failing control plane. A failover plan that has never been exercised is an assumption.

A distributed cache is a bounded, disposable acceleration layer. The origin remains authoritative, and the system must still be correct during a cold start, eviction storm, or total cache loss.

▸ DEEP DIVE · SENIOR
  • define source ownership and key schema: include tenant, authorization boundary, locale or schema version when they affect the result. Apply tenant quotas and eviction isolation so one tenant cannot evict another tenant's working set.
  • use cache-aside for derived reads; after an origin commit, publish an invalidation or version event through a durable outbox path. TTL limits stale damage but is not a correctness proof.
  • Redis Cluster uses hash slots and cluster-aware clients following redirects; it is not inherently a proxy-based cache. Multi-key operations need deliberate same-slot placement.
  • replicate a hot key only with explicit replica routing and write/invalidation fan-out to every copy. Random key suffixes without that contract reduce hit rate and create inconsistent reads.
  • protect the origin with TTL jitter, single-flight rebuilds, admission limits, warm critical keys, degraded responses, and bounded concurrency when cache capacity or availability disappears.

Case metadata:

  • Workload: hit/miss rate, working-set size, tenant skew and fill burst
  • Freshness: TTL/invalidation and origin revalidation define the permitted staleness
  • Duplicate tolerance: cache fill/single-flight key, not a business command key
  • Recovery owner: origin data owner and cache platform
