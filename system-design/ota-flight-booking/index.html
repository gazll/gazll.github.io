Scope and problem framing

Let travellers search changing fares, hold scarce inventory, pay and receive a ticket or PNR through one or more GDS/airline integrations. Keep the money-and-seat path correct while search remains fast, cached and explicitly stale.

Requirements

Functional requirements

  • Search itineraries and quote a fare with a clear expiry, source and baggage or rule snapshot.
  • Create an idempotent seat hold, complete payment and issue the ticket through a recoverable booking workflow.
  • Release expired holds, reconcile ambiguous PSP/GDS results and publish booking status changes to clients.
  • Support a bounded, policy-driven overbooking allocation separately from accidental double-selling.

Quality attributes

  • No two confirmed bookings consume the same physical seat unless an explicit overbooking pool permits it.
  • Search can degrade to cached availability, but confirmation never treats a cached result as authoritative.
  • External outcomes:Every external call is timed out and idempotent where possible; unknown outcomes enter reconciliation rather than being guessed.
  • The workflow exposes pending states and survives service, queue or orchestrator restarts.
  • A timeout is an unknown outcome, not a failure — the saga must resolve it by querying the provider with the same client reference before it retries or compensates.

Capacity and constraints

  • Estimate search-to-book ratio, peak search QPS, concurrent holds, conversion rate and route/date skew.
  • Model GDS latency and quota, fare/availability freshness, hold TTL and reconnect or retry storms.
  • Size the booking path for peak purchases while isolating it from the much larger search workload.
  • Budget event retention, reconciliation backlog, payment/ticket issue timeout windows and provider failover.
  • Put the numbers on the two paths separately, because they differ by two orders of magnitude: at a 100:1 search-to-book ratio a T3 booking volume of 10k bookings/day sits behind ~1M searches/day, which is ~250 rps peak on search against ~2.5 rps peak on the booking path. Travel traffic is consumer traffic and concentrates 10–20× around a fare drop or a holiday window.
  • Judge the seat-hold mechanism per tier:worth it at T1 and T2, where contention is rare and a failed booking is an apology; mandatory at T3, because two customers reaching the last seat within the GDS round trip is a routine event rather than an edge case; needs its own scaling story at T4, where holds, their expiry and the reconciliation of abandoned ones become a component with an owner rather than a TTL on a row.
  • The GDS quota is an external hard limit and usually binds before your own capacity does. Size the search cache from that quota backwards: if the provider allows N calls per second, the cache hit ratio is what determines the search rate you can offer, not your instance count.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Offer snapshot

itinerary, provider, fare/rules, availability observation, currency, version and expiry.

02Seat hold

flight/seat or inventory bucket, customer, quantity, status, fencing version and expires_at.

03Booking saga

booking id, current step, provider references, idempotency keys, attempts and next action.

04Payment ledger

immutable debit/credit postings, PSP reference and reconciliation state.

05Ticket/PNR

provider locator, passengers, segments, issue status and latest verified provider state.

06Saga instance

saga_id, booking_id, saga_version, state, current_step and deadline_at; the process truth, kept separate from the booking row that is the domain truth.

07Saga step

(saga_id, step_name) with attempt, a stable idempotency_key that is unique across the table, the external_ref the provider returned, and compensation_status.

08Outbox event

event_id, aggregate_type/id, a monotonic aggregate_version, event_type, schema_version and payload; unique on (aggregate, version, type) so a retried write cannot emit the same fact twice.

09Inbox message

(consumer_name, event_id) as a primary key; the row exists only to make a redelivered event a no-op inside the consumer transaction.

10API idempotency

(scope, idempotency_key) holding request_hash plus the stored response, so a client retry returns the first booking instead of creating a second.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01Stateless search/pricing services with Redis cache…

Stateless search/pricing services with Redis cache and provider-specific circuit breakers or quota controls.

02PostgreSQL/MySQL for atomic holds, booking saga…

PostgreSQL/MySQL for atomic holds, booking saga and payment ledger; conditional updates or row locks at the inventory boundary.

03Kafka-compatible event bus with Outbox for…

Kafka-compatible event bus with Outbox for notifications, analytics and availability projections.

04Durable workflow/orchestrator for hold → authorize/capture…

Durable workflow/orchestrator for hold → authorize/capture → issue, plus scheduled expiry and reconciliation workers.

05WebSocket or SSE for bounded realtime…

WebSocket or SSE for bounded realtime updates; GDS/airline and PSP adapters behind anti-corruption layers.

06Transactional outbox with CDC

the service commits state and event in one local transaction and never calls the broker directly; Debezium reads committed rows from the WAL and routes them, which closes the dual-write window in both directions.

07Durable workflow engine for the orchestrator

the booking waits on supplier callbacks, payment challenges and ticketing far longer than one process lifetime, so workflow state and timers must survive a crash rather than live in memory.

08Schema registry with a CI compatibility gate

a booking event has many independent consumers, so a renamed or deleted field is an incident that spreads; additive changes pass, breaking ones fail the build.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Saga, outbox and the three idempotency boundaries

Client-to-API, saga-to-provider and broker-to-consumer each need their own key; one table cannot serve all three.

sql
-- Saga progress, outbox and the three idempotency boundaries.
-- Domain state and the event intent commit in ONE local transaction.

CREATE TABLE saga_instance (
    saga_id       UUID PRIMARY KEY,
    booking_id    UUID NOT NULL,
    saga_version  INTEGER NOT NULL,     -- code version that started it
    state         TEXT NOT NULL,
    current_step  TEXT,
    deadline_at   TIMESTAMPTZ,
    version       BIGINT NOT NULL DEFAULT 0,

    CHECK (state IN ('RUNNING', 'CONFIRMED', 'FAILED',
                     'COMPENSATING', 'COMPENSATED',
                     'MANUAL_REVIEW', 'EXPIRED'))
);

CREATE TABLE saga_step (
    saga_id             UUID NOT NULL,
    step_name           TEXT NOT NULL,
    attempt             INTEGER NOT NULL DEFAULT 0,
    status              TEXT NOT NULL,
    idempotency_key     TEXT NOT NULL,   -- stable across every retry
    external_ref        TEXT,            -- PNR, authorization_ref, hold_ref
    compensation_status TEXT,

    PRIMARY KEY (saga_id, step_name),
    UNIQUE (idempotency_key)
);

CREATE TABLE outbox_event (
    event_id          UUID PRIMARY KEY,
    aggregate_type    TEXT NOT NULL,
    aggregate_id      UUID NOT NULL,
    aggregate_version BIGINT NOT NULL,   -- monotonic per aggregate
    event_type        TEXT NOT NULL,
    schema_version    INTEGER NOT NULL,
    payload           JSONB NOT NULL,
    occurred_at       TIMESTAMPTZ NOT NULL DEFAULT now(),

    UNIQUE (aggregate_type, aggregate_id, aggregate_version, event_type)
);

CREATE TABLE inbox_message (
    consumer_name TEXT NOT NULL,
    event_id      UUID NOT NULL,
    processed_at  TIMESTAMPTZ NOT NULL DEFAULT now(),

    PRIMARY KEY (consumer_name, event_id)
);

CREATE TABLE api_idempotency (
    scope           TEXT NOT NULL,
    idempotency_key TEXT NOT NULL,
    request_hash    TEXT NOT NULL,   -- same key + different body = conflict
    resource_id     UUID,
    response_code   INTEGER,
    response_body   JSONB,

    PRIMARY KEY (scope, idempotency_key)
);

Outbox producer — state and event in one commit

No publish call in the request path. CDC observes committed rows, so "committed but never published" cannot happen.

python
# Booking creation: domain row + event intent in one transaction.
# There is no producer.send() here - CDC reads committed rows only.

def create_booking(cmd, idempotency_key, db):
    with db.transaction() as tx:
        prior = tx.query_one(
            """SELECT request_hash, response_code, response_body
                 FROM api_idempotency
                WHERE scope = 'create-booking' AND idempotency_key = %s
                  FOR UPDATE""",
            [idempotency_key])

        request_hash = canonical_hash(cmd)

        if prior:
            # Same key, different body is a client bug, not a retry.
            if prior.request_hash != request_hash:
                raise IdempotencyConflict()
            return prior.response_code, prior.response_body

        booking_id, saga_id = uuid4(), uuid4()

        tx.execute(
            """INSERT INTO booking (booking_id, saga_id, customer_id,
                                     status, currency, total_amount_minor)
               VALUES (%s, %s, %s, 'PENDING', %s, %s)""",
            [booking_id, saga_id, cmd.customer_id,
             cmd.currency, cmd.amount_minor])

        tx.execute(
            """INSERT INTO outbox_event (event_id, aggregate_type,
                    aggregate_id, aggregate_version, event_type,
                    schema_version, payload)
               VALUES (%s, 'booking', %s, 1, 'booking.created', 1, %s)""",
            [uuid4(), booking_id,
             json.dumps({'booking_id': str(booking_id),
                         'saga_id': str(saga_id), 'status': 'PENDING'})])

        response = {'booking_id': str(booking_id), 'status': 'PENDING'}

        tx.execute(
            """INSERT INTO api_idempotency (scope, idempotency_key,
                    request_hash, resource_id, response_code, response_body)
               VALUES ('create-booking', %s, %s, %s, 202, %s)""",
            [idempotency_key, request_hash, booking_id,
             json.dumps(response)])

    # Commit happened. Debezium will observe the outbox row from the WAL.
    return 202, response

Inbox consumer — duplicates become no-ops

Insert the event id first, ACK only after the local commit, and guard the aggregate version so a replay cannot regress state.

python
# The consumer side of at-least-once: duplicates must be no-ops.

def consume_booking_event(message, db):
    event = decode_and_validate(message)

    with db.transaction() as tx:
        inserted = tx.execute(
            """INSERT INTO inbox_message (consumer_name, event_id)
               VALUES (%s, %s) ON CONFLICT DO NOTHING""",
            ['payment-service', event.event_id])

        if inserted.rowcount == 0:
            return ACK          # already applied in an earlier delivery

        current = tx.query_one(
            """SELECT version FROM payment_booking_view
                WHERE booking_id = %s FOR UPDATE""",
            [event.aggregate_id])

        if current:
            # Version guard: ordering is per-partition, not global.
            if event.aggregate_version <= current.version:
                return ACK                        # stale replay
            if event.aggregate_version > current.version + 1:
                raise SequenceGap(event.aggregate_id)   # park, do not apply

        apply_business_transition(tx, event)

        # A downstream event goes into THIS transaction's outbox, not a
        # separate publish - the same dual-write rule applies here.

    return ACK   # ACK only after the local commit succeeded

Orchestrated saga with compensation

Compensation runs in business order and stops at the first irreversible step rather than pretending it can be undone.

python
# Orchestrated booking saga. The durable workflow runtime owns retries,
# timers and resumption; every step below must still be idempotent.

async def run_booking_saga(ctx, booking):
    completed = []
    try:
        quote = await execute_step(ctx, name='REPRICE',
            action=lambda key: pricing.reprice(booking.quote_id,
                                               idempotency_key=key))
        completed.append(('REPRICE', quote))

        hold = await execute_step(ctx, name='HOLD_INVENTORY',
            action=lambda key: supplier.hold(booking.items,
                                             idempotency_key=key))
        completed.append(('HOLD_INVENTORY', hold))

        auth = await execute_step(ctx, name='AUTHORIZE_PAYMENT',
            action=lambda key: payment.authorize(booking.amount,
                                                 idempotency_key=key))
        completed.append(('AUTHORIZE_PAYMENT', auth))

        # Past this point a timeout means UNKNOWN, never "did not happen":
        # the resolver asks the supplier by client reference before any retry.
        confirmed = await execute_step(ctx, name='CONFIRM_SUPPLIER',
            action=lambda key: supplier.confirm(hold.ref,
                                                idempotency_key=key),
            ambiguous_outcome_resolver=supplier.lookup_by_client_ref)
        completed.append(('CONFIRM_SUPPLIER', confirmed))

        capture = await execute_step(ctx, name='CAPTURE_PAYMENT',
            action=lambda key: payment.capture(auth.ref,
                                               idempotency_key=key),
            ambiguous_outcome_resolver=payment.lookup)
        completed.append(('CAPTURE_PAYMENT', capture))

        await booking_service.confirm(booking.id)
        return 'CONFIRMED'

    except RetriableError:
        raise      # runtime backs off with jitter inside the deadline

    except UnrecoverableError as failure:
        return await compensate(ctx, booking, completed, failure)


async def compensate(ctx, booking, completed, failure):
    # Business order, not a blind reverse loop: some steps cannot be undone.
    for step, result in choose_compensation_order(completed):
        if step == 'CAPTURE_PAYMENT':
            await idempotent_retry(payment.refund, result.ref)

        elif step == 'CONFIRM_SUPPLIER':
            outcome = await idempotent_retry(supplier.cancel_if_allowed,
                                             result.ref)
            if outcome == 'NON_REFUNDABLE':
                # Forward recovery beats a rollback that cannot happen.
                return await manual_review(booking.id,
                                           reason='supplier_irreversible')

        elif step == 'AUTHORIZE_PAYMENT':
            await idempotent_retry(payment.void, result.ref)

        elif step == 'HOLD_INVENTORY':
            await idempotent_retry(supplier.release, result.ref)

    await booking_service.mark_compensated(booking.id, failure.code)
    return 'COMPENSATED'

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
One atomic inventory authority prevents accidental…

One atomic inventory authority prevents accidental double-booking but may need partitioning by flight or inventory bucket.

02
A short hold TTL improves utilization…

A short hold TTL improves utilization but punishes slow payment and accessibility flows; extend it only through explicit policy.

03
Orchestration makes the money-and-ticket path observable;…

Orchestration makes the money-and-ticket path observable; choreography reduces coupling but hides one business transaction across events.

04
Issue the hardest-to-reverse step last, yet…

Issue the hardest-to-reverse step last, yet treat every timeout as unknown and query provider status before compensating.

05
Overbooking is a commercial capacity model…

Overbooking is a commercial capacity model with limits and recovery cost, not a race condition disguised as eventual consistency.

06
Chase effectively-once business effect, not exactly-once delivery

a broker guarantee stops at its own boundary, while an airline or PSP sits outside it; idempotency keys, unique constraints, an inbox and reconciliation are what actually prevent a second charge.

07
Compensation is a new valid business state, not a byte-for-byte rollback

once a seat is held, funds are authorized or a ticket is issued, the outside world has moved, and forward recovery or manual review is sometimes the correct answer.

08
Orchestrate the money-and-ticket path, choreograph everything after it

a coordinator gives the core flow explicit timeouts, compensation and an auditable saga_id, while notification, loyalty and analytics stay loosely coupled behind BookingConfirmed.

09
Keep the local transaction short and free of remote calls

holding a database transaction open across an airline or PSP call pushes their tail latency straight into your lock contention.

Failure review — answers for this design
01

Which invariant can break?

A seat may be sold once, and a payment may be captured only for a booking that was actually ticketed. Both break at the same place: an ambiguous outcome from the airline or the PSP, where a timeout means the effect may or may not have happened and treating it as failure is exactly as wrong as treating it as success.

02

Which metric detects it first?

The count of bookings sitting in an unresolved outcome state, and their age. Payment success rate and booking conversion both look normal while these accumulate, because an ambiguous booking has neither failed nor succeeded and therefore appears in neither number.

03

How is the blast radius contained?

The search path and the booking path are separated so that a GDS quota exhaustion degrades search rather than stopping sales, holds expire on their own so an abandoned checkout returns inventory without intervention, and each external provider sits behind its own breaker and budget.

04

Can retry duplicate or reorder work?

Yes at every external boundary, which is why the saga carries an idempotency key per step rather than per booking. A retried ticket issue must return the original ticket, and a retried capture must return the original capture — otherwise a customer is charged twice for one seat.

05

How do we repair and prove recovery?

Resolve the unresolved set by querying each provider for the true outcome, then either complete or compensate — never by guessing from a local record. Recovery is proven when the unresolved-outcome count returns to zero, held inventory matches the airline’s view for a sampled set of flights, and no booking holds a capture without a ticket.

Engineering deep dives

Saga and transactional outbox under at-least-once delivery

A booking crosses pricing, inventory, a supplier, payment and ticketing, so no single ACID transaction spans it. Commit each local step with its event intent, then make every external effect safe to repeat.

Close the dual-write window, then order what you own

  • Writing the database and then publishing to a broker are two independent writes: either order leaves a crash window where one succeeded and the other did not. Commit the domain row and an outbox row in one local transaction and let CDC publish from the log.
  • The outbox is a consistency technique, not a microservice one — a monolith can adopt it before any service is extracted, which is what makes it the safe first step of a strangler migration.
  • Ordering exists per partition, not per cluster. Key booking events by booking_id and carry a monotonic aggregate_version so a consumer can ignore stale replays and park on a gap; never force a global key to buy total ordering, because it turns one partition into the ceiling for the whole topic.

Aim for effectively-once, and treat a timeout as unknown

  • A broker exactly-once guarantee holds inside its own boundary; an airline, GDS or PSP sits outside it and is never covered. Treat delivery as at-least-once and defend each side effect with a stable idempotency key, a unique constraint and an inbox row.
  • Do not mint a new idempotency key on retry — the key is the identity that lets the provider recognise the repeat. Keep personal data out of it, and store the first response so a client retry replays it instead of creating a second booking.
  • If a supplier call times out after the request left the building, the outcome is unknown: retrying under a fresh reference can create a duplicate PNR, and compensating immediately can refund a booking that exists. Route it through an explicit OUTCOME_UNKNOWN state that queries by client reference before it repeats anything.

Compensate by reversibility, alert on age, version the workflow

  • Classify each step: fully reversible (release a hold), reversible but asynchronous (refund), reversible with cost (cancellation fee), conditionally reversible (rate deadline), and irreversible (an issued non-refundable ticket). Compensation is semantic correction, not database rollback, so it need not run in strict reverse order and may itself fail.
  • Prefer oldest-outbox-age and CDC lag over queue length: a large backlog draining fast can be healthy, while a twenty-minute-old outbox row is an incident even on a short queue. Make MANUAL_REVIEW a real terminal state rather than a stuck saga.
  • A saga started under V1 can still be running when V3 deploys, so pin in-flight executions to their own version and drain them. Broker retention plus maximum saga lifetime is what sets how long old event schemas and old workflow code must stay decodable.

Correctness across money and inventory

The database protects local invariants; idempotency, state machines and reconciliation protect the workflow around it.

Make commands repeatable

  • Persist idempotency key, request fingerprint and original response together. Reject key reuse with different parameters and define retention from the maximum retry window.
  • Represent pending and unknown outcomes explicitly. After a timeout, query authoritative provider state before retrying or compensating an irreversible action.

Keep invariants local

  • Put uniqueness, balance and legal state transitions in one transaction and enforce them with constraints, conditional updates or locks—not a cache lock.
  • Choose isolation from the anomaly to prevent. Serializable transactions can abort under contention, so the whole transaction needs a bounded retry path.

Close the distributed gap

  • Write business state and an outbox record atomically; consumers deduplicate effects. Exactly-once inside one platform does not make an external PSP or airline atomic.
  • Reconcile independent statements, retain immutable audit history and repair by compensating entries. Monitor aged pending states and unmatched totals as correctness SLIs.

Reliability, overload and recovery

Reliability is a user-visible contract. Capacity, retries and failover must be designed as bounded control loops rather than emergency switches.

Prevent positive feedback

  • Give every call an end-to-end deadline; derive shorter per-hop timeouts from the remaining budget and cancel work the caller no longer needs.
  • Retry only classified transient failures, cap attempts, add exponential backoff with jitter and enforce a retry budget so recovery traffic cannot become the outage.

Degrade deliberately

  • Use admission control, bounded queues, concurrency limits and load shedding before saturation; queue depth without oldest-age is not enough to see stalled work.
  • Define which features fail closed, fail open, serve stale data or become read-only. Test the degraded contract with dependency latency, partial-region loss and bad configuration.

Prove recovery

  • Set RTO and RPO per journey, automate restore/failover where safe, and regularly restore production-shaped backups into an isolated environment.
  • Roll out by canary or cell, compare user SLIs, and keep rollback independent of the failing control plane. A failover plan that has never been exercised is an assumption.

Given an OTA flight-booking brief, sketch the system for search, hold, payment, and ticketing. Which assumptions, ownership boundaries, and browse-versus-commit consistency rules would you state before drawing?16-project-concurrency-whiteboard.presenting-dissecting-the-ota-project.q1

Present it concisely, layer by layer:

  • Clients (web/mobile/B2B agents) → API Gateway (authentication, rate limiting, routing)
  • bounded-context services: Search/Pricing, Inventory/Seat-Hold, Booking Orchestrator, Payment (+ ledger), Ticketing/PNR, Notification, Loyalty
  • edge integrations: GDS/Airline (Amadeus/Sabre/NDC), PSP/bank (3DS, webhooks)
  • data infrastructure: database per service (Postgres/MySQL), Redis (cache + seat holds), Kafka (event bus + Outbox), reconciliation jobs

When drawing, emphasize consistency boundaries:

  • the seat and money path requires strong consistency (ACID + holds + idempotency)
  • the search/availability path accepts caching + eventual consistency

Primary flow: search → hold a seat (TTL) → payment → issue the ticket (PNR) → on timeout, release the seat and reconcile.

Presentation tip:

Start with one use case—booking a single ticket—and trace it end to end before expanding into scale and edge cases. Do not present a disconnected collection of boxes; tell the story of one request.

▸ DEEP DIVE · SENIOR
  • be prepared to explain why the services are split this way (boundaries follow bounded contexts and consistency boundaries, not technical layers), plus each component's bottlenecks and scaling strategy
  • be ready for follow-ups: 'What if the GDS is slow or unavailable?' (circuit breaker + cache + graceful degradation), 'How do you prevent double-selling a seat?' (atomic conditional update), and 'What about data residency/compliance?' (regional partitioning, PII encryption)

Draw one end-to-end use case first, then expand into scale. Knowing what the system DOES NOT have & why—for example, 'we have not sharded because a single primary is still sufficient'—demonstrates depth & pragmatism.

Name the authorities before naming technologies:

  • search is a projection
  • the quote is a time-bounded commercial contract
  • the local hold store is an admission authority
  • the GDS/airline is the external inventory authority
  • the PSP owns the payment outcome

State the assumptions: the key as a segment/flight/cabin/seat (or SKU) identity, the quote and hold TTL, the peak search-to-book ratio, supplier p99, and whether controlled overbooking is allowed.

For one booking, draw QUOTED -> HELD -> BOOKING -> PAYMENT_PENDING/UNKNOWN -> TICKETED, with EXPIRED, RELEASED, and MANUAL_REVIEW exits. A stale browse result may end in REPRICE or SOLD_OUT; it must never silently allocate inventory.

▸ DEEP DIVE · SENIOR

What would change this answer — state these before defending the design; each is an assumption the interviewer can ask you to justify, and a measurement that would falsify it:

  • Which supplier or GDS contract the example assumes for hold expiry, booking idempotency and late ticketing success — the external authority decides most of the state machine.
  • Whether controlled overbooking is a permitted product policy, and which compensation or re-accommodation authority owns that risk.
  • The target search-to-book ratio, supplier p99, hold duration, connection count and WebSocket offline retention — the numbers behind every pool and queue size.
  • The acceptable limiter failure mode: fail closed, bounded regional overshoot, or a degraded local budget. And the Java target, because it changes the wording on virtual threads, structured concurrency and pinning.
  • What falsifies conditional writes over a long-held lock: a supplier API that requires a lease protocol, or a measured transaction pattern that needs multi-row atomicity.
  • What falsifies "WebSocket plus status cursor": a product contract with no offline or replay requirement and a verified loss-tolerant notification path.
Two users race to reserve the same flight seat. Design the hold state machine, database invariant, expiry behavior, idempotency, payment-after-expiry path, and supplier reconciliation that prevent double booking.16-project-concurrency-whiteboard.presenting-dissecting-the-ota-project.q2

A seat hold is a lease on authoritative inventory, not a promise that a background cleanup job can safely reopen at any time.

Acquire: atomically change one authoritative seat or inventory record from FREE to HELD only when it is still free or its prior lease is expired according to the database clock. Store a generated hold ID, lease version or fencing token, expiry, actor, and idempotency key.

Confirm: require the same hold ID and version, and require the lease to be unexpired. First move HELD to a non-expirable CONFIRMING state with a conditional database update; then durably record the supplier/payment intent and dispatch it outside the database transaction.

▸ DEEP DIVE · SENIOR
  • an expiry worker may release only a HELD lease whose hold ID, version, and expiry still match. It must never reopen CONFIRMING, BOOKED, or CANCELLED inventory.
  • supplier and airline inventory remain authoritative outside the OTA database. Persist an intent/outbox record, call the supplier idempotently, then query/reconcile unknown results rather than assuming a timeout failed.
  • one authoritative seat row is often simplest. If holds are separate, use a database-specific partial unique constraint for active allocation states; do not describe a vague active_hold column as a complete concurrency solution.
  • a payment result arriving after expiry must enter reconciliation: confirm inventory if the supplier can still prove it, otherwise void/refund according to the payment contract. Do not silently re-hold another seat.
  • bucketizing does not reduce contention for the same seat. Use admission control, per-seat serialization, or a product-level random-seat pool when the product permits it.

One atomic PostgreSQL hold claim — run the same statement from two sessions:

CREATE TABLE seat_inventory(
  flight_id bigint, seat_no text, hold_id uuid, hold_until timestamptz,
  version bigint NOT NULL DEFAULT 0,
  PRIMARY KEY(flight_id, seat_no)
);
INSERT INTO seat_inventory(flight_id, seat_no) VALUES (7, '12A');
UPDATE seat_inventory
   SET hold_id='11111111-1111-1111-1111-111111111111',
       hold_until=clock_timestamp()+interval '5 minutes', version=version+1
 WHERE flight_id=7 AND seat_no='12A'
   AND (hold_id IS NULL OR hold_until < clock_timestamp())
RETURNING hold_id, hold_until, version;
-- first contender returns one row; the second waits, rechecks, then returns zero

The row and predicate—not a prior SELECT—decide the winner.

  • Benefit: the database invariant survives two application instances.
  • Cost: a hot seat serializes on one row and expiry needs a durable state/reconciliation rule.
  • Late success rule: transition only the matching unexpired hold; never resurrect whichever hold currently occupies the seat.

The state machine must make expiry and stale workers safe: AVAILABLE -> HELD -> CONFIRMING -> BOOKED, with explicit EXPIRED, RELEASE_PENDING, and UNKNOWN states.

Three rules keep it safe:

  • Accept a transition only when the authoritative record still matches (resource_key, version, hold_id), and increment an integer version on every transition.
  • A TTL lease is a liveness mechanism, not fencing: a paused worker can wake after expiry, so the protected authority must reject its old version/token.
  • Reuse the same command and provider idempotency key after a timeout; keep the result UNKNOWN until inquiry or reconciliation rather than issuing a second hold or charge.
If an airline permits controlled overbooking, how would you model sellable inventory, policy ownership and versioning, concurrent sales, carrier reconciliation, audit, and legal or customer-experience guardrails?16-project-concurrency-whiteboard.presenting-dissecting-the-ota-project.q3

An OTA usually does not own the airline's overbooking policy. It should consume a carrier or supplier's versioned sellable allocation, hold it idempotently, and reconcile against the supplier's authoritative outcome.

▸ DEEP DIVE · SENIOR
  • model sellable limit separately from physical seats. It can reflect cabin, fare class, channel allotment, blocked seats, holds, cancellations, and a supplier-approved overbooking allowance; it is not universally physical seats multiplied by one factor.
  • use an atomic predicate that matches the counter: for example, increment sold only where sold is below sellable_limit, or decrement remaining only where remaining is above zero. Include a version and correlation ID for replay/reconciliation.
  • policy has effective dates, version, channel and legal constraints. Never lower sellable capacity below already sold or protected holds without an explicit exception workflow.
  • if more passengers arrive than physical seats, customer handling is governed by carrier policy and applicable law. The OTA should surface the policy, preserve audit evidence, and avoid inventing a universal bumping rule.
  • treat supplier updates, cancellation releases, and OTA retries as idempotent events; stale availability must not overwrite a newer supplier version.

Treat controlled overbooking as an explicit risk budget, not as permission to read a stale counter. The policy must have an owner, effective time, version, channel/fare scope, protected inventory, and a measured reaccommodation or compensation path.

The admission write is still conditional and idempotent; a policy update cannot silently reduce capacity below sold or protected holds.

Reconciliation must compare supplier sequence/version and distinguish SOLD, CANCELLED, PROTECTED, and UNKNOWN rather than overwriting the newest state with an older event.

Design a browse-to-book flow when price and availability sources are stale or slow. How do cache and freshness contracts, quote binding, final revalidation, customer messaging, and supplier failure handling preserve both speed and correctness?16-project-concurrency-whiteboard.presenting-dissecting-the-ota-project.q4

Browsing data is advisory; the supplier-bound quote and final inventory hold decide whether a booking can proceed.

Browse path: supplier adapters may ingest feeds, webhooks, or polls and normalize them into internal versioned events. Cache and stale-while-revalidate can improve browsing only when the UI labels the result as non-binding.

▸ DEEP DIVE · SENIOR
  • bind a quote to quote ID, itinerary, fare, tax, currency, rules, supplier version, expiry, and user/session where required. At checkout, reprice and request a supplier hold or confirmation using an idempotency key.
  • only promise a price or seat guarantee when the supplier actually supports that hold/guarantee. WebSocket or SSE updates are UX signals, not a correctness mechanism.
  • protect caches from older supplier updates overwriting newer state with versions or monotonic sequence rules. Cache invalidation is an optimization, not a substitute for final revalidation.
  • a supplier timeout after a mutation creates PENDING or UNKNOWN, not an automatic failure. Query status, reconcile using correlation IDs, and show the user an honest pending state instead of blindly retrying a booking.
  • decide the payment authorization/capture order together with supplier rules, hold expiry, and the recovery plan for partial outcomes.

Make freshness a contract, not an implementation detail: expose availability age, quote expiry, supplier version, and the maximum time a result may be shown as non-binding.

Propagate one absolute deadline and a retry budget across search, reprice, hold, and supplier calls. If a mutation times out, return PENDING/UNKNOWN with a status resource and correlation ID; do not retry with a new key.

Supplier events need monotonic sequence/version checks, while the final hold remains the admission decision.

Design the long-running OTA booking saga from hold through payment and ticket issue. Specify durable states and timers, transaction boundaries, idempotency, retries, unknown PSP/GDS outcomes, compensation, and reconciliation.16-project-concurrency-whiteboard.presenting-dissecting-the-ota-project.q5

A booking saga is a durable state machine around inventory, payment, and supplier issuance; it is not a database transaction spanning a PSP or GDS.

Example states: CREATED → HOLDING → HELD → PAYMENT_PENDING → AUTHORIZED → SUPPLIER_PENDING → ISSUED, with FAILED, CANCELLED, EXPIRED, UNKNOWN, and RECONCILIATION_REQUIRED paths. The exact authorization/capture sequence depends on the supplier and payment contracts.

▸ DEEP DIVE · SENIOR
  • persist the business state and an outbox record atomically in the local database. A relay or CDC process publishes the outbox at least once; consumers and external calls must be idempotent. This is not an atomic database-to-Kafka handoff.
  • do not call a PSP or GDS inside an open database transaction. Persist intent, dispatch with an idempotency/correlation key, record the outcome, and query/reconcile when the outcome is unknown.
  • a supplier PNR, ticket issuance, and payment capture can be different pivots.
  • define timers and compensation for each: release hold before expiry, void authorization where possible, refund after capture when issuance cannot be recovered, and preserve the customer-visible pending state while reconciling.
  • every transition needs an owner, retry deadline, terminal condition, audit trail, and duplicate-event behavior. “Compensation” is a new business action, not a true rollback of external systems.

Draw the recovery table beside the Saga:

  • PAYMENT_UNKNOWN: inquire/reconcile with the same provider reference
  • TICKET_UNKNOWN: query the GDS/airline before releasing or refunding
  • late success: apply it only through an allowed versioned transition

Each timer needs an owner, deadline, retry budget, terminal state, and repair queue. Compensation is a new business action that can fail or be partial, so the customer-visible state must remain pending/manual-review until the authority confirms it.
