Scope and problem framing

Use the supplied e-commerce diagram as a logical target for a promotion:

  • CDN and gateway at the edge
  • isolated search and cart paths
  • a durable Checkout Saga coordinating order, inventory and payment
  • and a local outbox beside each authoritative database.

The image says 1M DAU and a 10x campaign, whereas this blueprint's shared yardstick is requests/day. Convert DAU into endpoint traffic before sizing anything, then decide what is one deploy at 1M requests/day, what splits at the 10M waypoint, and what only becomes justified near 100M or under an explicit blast-radius target.

The skill is preserving the same business invariants while refusing distribution that has no measured constraint to remove.

Requirements

Functional requirements

  • Browse and search:Serve product images from the CDN, product details from cache or the catalog, and ranked results from a rebuildable search projection whose stock may be stale.
  • Cart:Persist the cart durably while using Redis only to accelerate active carts; an eviction or Redis outage must not erase a customer's order intent.
  • Checkout:Accept one idempotent checkout command, persist Saga state, create the order, reserve stock, process payment, then confirm or compensate each participant through explicit transitions.
  • After payment:Fan `PaymentCompleted` out to reviews, notification, analytics and search/index updates without placing those consumers on the checkout latency path.
  • Recovery:Expire abandoned reservations, reconcile `UNKNOWN` payments against the provider, replay outboxes, quarantine poison events and redrive the DLQ only after the consumer defect is fixed.

Quality attributes

  • Stock invariant:Available stock never becomes negative, and at most one live reservation may consume the same scarce unit/version; search is not an authority for that decision.
  • Payment invariant:A client, gateway, Saga retry and provider webhook may all duplicate work, but one checkout intent can produce at most one captured amount under one provider idempotency key.
  • Local atomicity:Each service commits its state transition and outbox record in one local transaction; delivery and consumption remain duplicate-tolerant.
  • Failure isolation:Search, cart, payment and after-payment work use separate pools and bounded queues, so a slow PSP or review consumer cannot exhaust checkout or browse capacity.
  • Operability:Alert on aged Saga states, outbox age, consumer lag, DLQ growth, reserve conflicts, payment `UNKNOWN` age and reconciliation mismatches rather than CPU alone.

Capacity and constraints

  • Unit guard:1M DAU is not requests/day. Estimate `requests/day = DAU × journeys/user/day × API calls/journey`, then split by browse, cart and checkout endpoint; report the assumptions beside the result.
  • 1M request scale:1M requests/day is 11.6 rps average and about 250 rps peak under the site's 20x planning factor.
    • One relational primary and one coarse application deployment may still be enough
    • preserve the logical ownership shown in the image without paying for a database and on-call team per box.
  • 10M waypoint:10M requests/day is 116 rps average and about 2,500 rps peak. A 10x promotion is a burst profile, not automatically 10M/day: measure its duration, endpoint mix, cache-hit ratio and hot-SKU skew, then cap accepted checkout work to the inventory and PSP drain rates.
  • Write amplification:One accepted checkout can create order, reservation and payment writes plus several outbox, inbox and derived-index records. Size database IOPS, WAL, broker ingress and consumers from commands and events per checkout, not from the public API count alone.
  • Serialized hot key:Ten stateless inventory replicas do not raise the safe rate for one SKU row or one ordered partition. Benchmark that critical section, reserve headroom, and use per-SKU admission or a waiting room when demand exceeds its drain rate.
  • 100M scale:About 25,000 rps peak is a fleet-sizing number.
    • Introduce shards or cells only for measured write/data volume, restore-time or blast-radius limits
    • model it as roughly ten independently operable T3-to-waypoint cells rather than one giant shared checkout.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Product and search document

Product DB is authoritative for catalog data; Elasticsearch/OpenSearch is a denormalized projection with `source_version` and `indexed_at`, so it can be stale, discarded and rebuilt.

02Cart

Durable cart rows own product, quantity and price-snapshot references; Cart Redis is a TTL acceleration tier for active sessions, never the only copy of checkout intent.

03Checkout request and Saga

`idempotency_key`, canonical request hash, original response, Saga state, step attempts, deadlines and version. Keep request dedupe with the transaction that creates the Saga, not in an eventually consistent global cache.

04Order

One aggregate with legal `CREATED → CONFIRMED | CANCELLED` transitions and a version. Order Service alone changes it; the Saga requests transitions but never writes Order DB directly.

05Inventory reservation

`sku_id`, quantity, order id, expiry, state and fencing version. A conditional update or uniqueness constraint is the final oversell guard; Redis may protect capacity but not replace this invariant.

06Payment attempt

Amount, currency, order id, provider idempotency key/reference and explicit `PENDING | SUCCEEDED | FAILED | UNKNOWN | REFUNDED` states. Timeout means query and reconcile, not retry with a new key.

07Outbox and inbox

Stable event/command id, aggregate id, aggregate version, type, payload and occurred time. Outbox closes the database/broker dual-write gap; inbox or an effect-specific unique key makes at-least-once delivery harmless.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01Image CDN

Problem solved: remove large immutable image and static-file reads from application compute and origin bandwidth.

Flow position: App/Web requests a content-addressed URL such as `products/42/sha256.webp` directly from the nearest edge; business APIs still enter the gateway.

Failure / cost:

  • a bad cache key serves stale content, an expiry wave stampedes the origin, and public caching can leak private responses
  • use versioned URLs, long immutable TTLs, origin shielding and a placeholder when the CDN is unavailable.

Tier verdict:

  • 1M worth it
  • 10M mandatory for image-heavy browse
  • 100M needs its own scaling story across regions and origins.

02API Gateway

Problem solved: give clients one stable edge contract for TLS termination, authentication hand-off, coarse authorization, routing, request-size limits and per-route rate limits.

Flow position: every dynamic `/search`, `/cart` and `/checkout` call enters here, receives a correlation id and is routed to an independently budgeted backend pool.

Failure / cost: it is a high-blast-radius choke point; policy mistakes reject all traffic, retries can amplify overload, and deep business authorization here becomes unmaintainable. Run multiple instances across zones, fail closed for auth, return explicit `429` with backoff, and keep domain checks in services.

Tier verdict:

  • 1M worth it
  • 10M mandatory
  • 100M needs its own scaling story per cell or region.

03Service discovery with Kubernetes Service/DNS

Problem solved: let gateway and services call a stable name while Pods and IPs are replaced.

Flow position:

  • `checkout.default.svc.cluster.local` resolves to a Service whose EndpointSlices track healthy checkout replicas
  • clients still need connection timeouts, load balancing and readiness because DNS only finds an endpoint.

Failure / cost: stale DNS caches, an unhealthy readiness probe or a control-plane outage can route poorly, while a second custom registry duplicates platform state.

Tier verdict:

  • platform discovery is 1M worth it and 10M mandatory once replicas move
  • a custom registry is not needed at either tier
  • 100M cross-cell discovery needs its own scaling story.

04Search Service plus Elasticsearch/OpenSearch

Problem solved: full-text relevance, typo tolerance, filtering, faceting and sorting that a transactional Product DB should not execute on every browse request.

Flow position:

  • product and stock events update a versioned `products-v42` projection
  • Search Service queries it and returns `source_version` or `indexed_at`, while checkout revalidates stock in Inventory.

Failure / cost:

  • refresh and consumer lag make results stale, mappings and shard counts are expensive to change, hot queries exhaust heap, and out-of-order events can overwrite newer documents
  • reject older source versions and keep a rebuild path from Product DB/outbox.

Tier verdict:

  • 1M worth it when product search is real
  • 10M mandatory for the depicted search-heavy lane
  • 100M needs its own scaling story for shards, indexing and relevance.

05Product Redis cache

Problem solved: absorb repeated product-detail reads and protect Product DB connection/IO budgets.

Flow position:

  • Search or Product Service performs cache-aside `GET product:{id}:v{source_version}`, loads the authoritative row on a miss, then `SET`s a bounded TTL
  • writes commit to Product DB first and invalidate or advance the versioned key.

Failure / cost:

  • stale values, eviction and Redis outage are expected
  • simultaneous misses create a stampede and one hot key can saturate a shard, so use single-flight fill, jittered TTL, negative caching with a short TTL and a direct-to-origin concurrency cap.

Tier verdict:

  • 1M worth it
  • 10M mandatory for the hot catalogue path shown
  • 100M needs its own scaling story for memory, hot keys and failover.

06Cart DB plus Cart Redis

Problem solved: Cart DB preserves customer intent across sessions, while Redis reduces latency for repeatedly edited active carts.

Flow position:

  • Cart Service writes the durable cart with an optimistic version and may cache `cart:{customer_id}`
  • checkout always reloads or validates the durable version and current price/stock rules.

Failure / cost: cache eviction must become a miss, never an empty cart; dual writes can diverge, long TTLs expose stale quantity and a hot anonymous campaign can consume memory. Prefer database-first plus invalidate, measure hit rate and cap cart size.

Tier verdict: durable Cart DB is 1M mandatory; Cart Redis is 1M not needed, 10M worth it, and 100M needs its own scaling story.

07Checkout Saga plus Checkout DB

Problem solved: preserve progress across the Order, Inventory and Payment transaction boundaries when no single ACID commit covers them.

Flow position:

  • Checkout persists `RECEIVED → STOCK_HELD → PAYMENT_PENDING → CONFIRMED`, deadlines and step attempts before issuing idempotent participant commands
  • workers can restart from durable state and compensations are explicit new commands.

Failure / cost: the orchestrator couples workflow knowledge, can become a control-plane hotspot, and compensation may fail or be semantically impossible after an external effect. Partition workers by checkout/order id, fence concurrent transitions and reconcile aged non-terminal rows.

Tier verdict:

  • 1M not needed while all participants share one local transaction
  • 10M mandatory only after they become separate authorities
  • 100M needs its own scaling story per cell.

08Idempotency store

Problem solved: make client retries, gateway retries and duplicate submissions return one logical checkout outcome.

Flow position:

  • the transaction that creates the Saga inserts `(tenant, idempotency_key, canonical_request_hash, status, original_response)` under a unique constraint
  • the same key with a different hash is rejected, while an exact replay returns the stored response.

Failure / cost: a remote eventually consistent cache allows races, unbounded retention grows forever, and deleting keys too early reopens duplicate capture risk. Co-locate it with Checkout DB, define retention from the longest retry/webhook window and monitor hot keys.

Tier verdict:

  • 1M mandatory
  • 10M mandatory
  • 100M needs its own scaling story for partitioning and retention.

09Order Service plus relational Order DB

Problem solved: own the legal order lifecycle and audit trail independently of the Saga's opinion.

Flow position:

  • idempotent `Create`, `Confirm` and `Cancel` commands perform conditional transitions such as `CREATED → CONFIRMED | CANCELLED`, then record an outbox event in the same transaction
  • no other service writes Order tables.

Failure / cost: cross-service joins disappear, stale commands conflict by version, and premature service/database separation adds network and on-call cost. Keep indexes around customer/status/time and archive by policy rather than sharding the headline.

Tier verdict: the relational state machine is 1M mandatory; a separate service/database is 1M not needed, 10M worth it for ownership/isolation, and 100M needs its own scaling story.

10Inventory Service plus relational Inventory DB

Problem solved: make stock reservation the single authority that prevents oversell.

Flow position: `Reserve(sku, qty, order)` performs one short conditional update such as `available >= qty AND version = expected`, inserts an expiring reservation and outbox row, then `Confirm` or `Release` transitions that exact reservation idempotently.

Failure / cost: one promotional SKU remains a serialized hot key even with many replicas; lock waits, expired holds and duplicate release commands must be visible. Use a database constraint as the final guard, admission/waiting-room controls for the hot SKU and reconciliation for leaked reservations.

Tier verdict: the invariant is 1M mandatory and 10M mandatory; 100M needs its own scaling story by SKU/warehouse, not random request sharding.

11Payment Service plus relational Payment DB

Problem solved: isolate provider-specific APIs while keeping one authoritative payment-attempt ledger.

Flow position: it stores amount, currency, order id, provider reference and one reused provider idempotency key, calls the PSP outside the database transaction, records webhook/status-query evidence, and emits a local outbox event.

Failure / cost: timeout means `UNKNOWN`, not failed; retrying with a fresh key may double-charge, late success may require refund, and a slow PSP can exhaust checkout workers. Use strict timeouts, a separate concurrency budget, status polling/webhooks and financial reconciliation.

Tier verdict:

  • durable attempts and idempotency are 1M mandatory
  • provider isolation is 10M worth it
  • 100M needs its own scaling story per provider/region.

12Transactional Outbox, relay and consumer Inbox

Problem solved: close the database/broker dual-write gap without a distributed transaction.

Flow position:

  • each Order, Inventory or Payment transaction appends a stable event id and aggregate version locally
  • a relay publishes unprocessed rows, and each consumer records the event id plus its side effect in one local transaction.

Failure / cost: a relay crash after publish causes duplicates, backlog grows the source DB, and out-of-order delivery can apply stale state; therefore publication is at-least-once, not end-to-end exactly-once. Monitor oldest outbox age, batch with `SKIP LOCKED`, deduplicate and reject stale versions.

Tier verdict:

  • 1M not needed while one local transaction has no broker side effect
  • 10M mandatory for the depicted split
  • 100M needs its own scaling story for relay throughput and retention.

13Kafka event log

Problem solved: retain replayable domain events and let checkout, search, analytics and after-payment consumer groups advance independently.

Flow position:

  • outbox relays publish `OrderCreated`, `StockReserved` and `PaymentCompleted` keyed by the aggregate whose order matters
  • one partition preserves order for that key and each group gets its own copy.

Failure / cost: consumers can replay duplicates, rebalances pause work, retention can remove repair history, and adding partitions changes key distribution while one hot key still cannot use several partitions. Size partitions from measured bytes/events, use schemas and compatibility checks, and alert on oldest lag rather than broker CPU alone.

Tier verdict:

  • 1M worth it when replay or multiple groups are required
  • 10M mandatory for the pictured fan-out
  • 100M needs its own scaling story for partitions, storage and cross-cell replication.

14RabbitMQ work queues

Problem solved: route one command or task to one logical worker with broker-side acknowledgements, redelivery and queue-level policies.

Flow position:

  • it can carry fulfilment, email or compensation commands whose consumer acknowledges only after its local effect commits
  • publisher confirms cover broker acceptance, not consumer success.

Failure / cost: redelivery is at-least-once, requeue loops can burn capacity, a queue can become a single ordered bottleneck, and RabbitMQ is not Kafka-style retained replay by default. Set prefetch/concurrency budgets, durable or quorum queues where required, idempotent handlers and policy-managed dead lettering.

Tier verdict:

  • 1M not needed when direct calls or Kafka events suffice
  • 10M worth it for routed work
  • if selected at 100M it needs its own scaling story.

15Bounded retry plus DLQ

Problem solved: recover transient delivery/dependency failures without one poison record blocking a partition or queue forever.

Flow position:

  • the consumer retries only classified transient errors with exponential backoff and jitter, then parks the original payload, headers, schema version and failure reason in quarantine
  • an owner fixes the defect and explicitly redrives it.

Failure / cost: retry amplifies outages, delayed work can violate business deadlines, and a DLQ is not automatic repair or an archive. Cap attempts and elapsed time, preserve ordering requirements, alert on oldest age/growth and reconcile before redrive.

Tier verdict:

  • 1M mandatory for any asynchronous lane
  • 10M mandatory
  • 100M needs its own scaling story for quarantine volume and operator tooling.

16After-payment workers and After Payment DB

Problem solved: keep reviews, notifications, analytics and other non-critical effects off checkout latency while allowing each to lag or replay independently.

Flow position: dedicated consumer groups process `PaymentCompleted`, write their own local state with an inbox/effect unique key and expose completion separately from the order's authoritative payment state.

Failure / cost: users may see delayed email/review eligibility, fan-out multiplies event traffic, and one consumer's schema bug can accumulate a large backlog. Give every effect an SLO, concurrency budget, retention/rebuild plan and owner; never let its outage reject a paid order.

Tier verdict:

  • 1M worth it
  • 10M mandatory for failure isolation
  • 100M needs its own scaling story per consumer domain.

17Observability and reconciliation workers

Problem solved: detect and repair ambiguous distributed state that metrics on HTTP success cannot prove correct.

Flow position: traces carry checkout/order/event ids, dashboards join accepted-to-completed ratio with oldest Saga/outbox/consumer age, and scheduled reconcilers compare Checkout, Order, Inventory, Payment and PSP evidence before issuing explicit confirm/release/cancel/refund repairs.

Failure / cost: high-cardinality telemetry is expensive, sampling can hide rare money errors, and an unsafe repair job can magnify corruption. Keep immutable audit evidence, dry-run repair plans and require idempotent, fenced transitions.

Tier verdict:

  • 1M mandatory
  • 10M mandatory
  • at 100M the telemetry and repair plane needs its own scaling story.

18Shards and cells

Problem solved: bound dataset/restore time, write contention and regional blast radius after simpler tuning is exhausted.

Flow position:

  • a versioned router keeps Checkout, Order and Payment for one order in one cell, while Inventory remains routed by its SKU/warehouse authority
  • migrations copy, stream ordered changes, verify invariants, cut one range over and fence the old writer.

Failure / cost:

  • cross-cell workflows, routing-map mistakes, skew, rebalancing and duplicated platform/on-call estates are permanent complexity
  • independent dual writes are not a migration strategy.

Tier verdict:

  • 1M not needed
  • 10M not needed unless measured restore or blast-radius targets say otherwise
  • at 100M it needs its own scaling story and is mandatory only when those targets require it.
Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

Atomic inventory reservation + outbox

The conditional update is the final oversell guard; the outbox row commits with the reservation.

sql
BEGIN;

INSERT INTO checkout_inbox (idempotency_key, request_hash, state)
VALUES (:key, :request_hash, 'RECEIVED')
ON CONFLICT (idempotency_key) DO NOTHING;

UPDATE inventory
SET available = available - :qty, version = version + 1
WHERE sku_id = :sku_id
  AND available >= :qty
  AND version = :expected_version;
-- Require row_count = 1; otherwise reject or re-read the SKU.

INSERT INTO reservation (order_id, sku_id, quantity, state, expires_at)
VALUES (:order_id, :sku_id, :qty, 'HELD', now() + interval '10 minutes');

INSERT INTO outbox_event (event_id, aggregate_id, type, payload)
VALUES (:event_id, :order_id, 'StockReserved', :payload);
COMMIT;

Runpsql checkout.sql --set sku_id=sku-42 --set qty=1

Inbox de-dup + optimistic Saga fence

At-least-once delivery is expected; the inbox key and version predicate make a replay harmless.

sql
BEGIN;

INSERT INTO event_inbox (event_id, consumer)
VALUES (:event_id, 'checkout')
ON CONFLICT (event_id, consumer) DO NOTHING;

UPDATE checkout_saga
SET state = :next_state, version = version + 1, updated_at = now()
WHERE checkout_id = :checkout_id
  AND version = :expected_version
  AND state = :expected_state;
-- Zero rows means duplicate, stale, or an unexpected transition.

COMMIT;

Runpsql checkout.sql --set event_id=evt-123

Replay the event stream into a new index

Replay is a rebuild tool, not a correctness shortcut: consumers still need idempotent effects and version checks.

bash
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --if-not-exists --topic order.events --partitions 12 --replication-factor 3

kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic order.events --group search-indexer-rebuild \
  --from-beginning --property print.key=true

RunStart Kafka locally, then stop the consumer after the rebuild lag reaches zero.

Find payment attempts that need reconciliation

UNKNOWN is a durable state. Query the provider before deciding whether to capture, refund, or retry.

sql
SELECT payment_id, order_id, provider_ref, idempotency_key
FROM payment_attempt
WHERE state = 'UNKNOWN'
  AND updated_at < now() - interval '5 minutes'
ORDER BY updated_at
FOR UPDATE SKIP LOCKED
LIMIT 100;

Runpsql payment.sql --set statement_timeout=2000

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
Logical architecture versus operational estate

The picture is an excellent ownership map but an expensive day-one deployment.

  • Keeping boxes logical at 1M preserves simple transactions and on-call
  • splitting the measured hot lanes at 10M buys isolation while adding network failure, versioned contracts and more deployments.
02
Orchestration versus choreography

Checkout Saga makes sequence, timeout and compensation visible in one place.

  • It also becomes a control-plane hotspot and coupling point
  • persist state, partition workers and keep participant APIs idempotent so losing the orchestrator process loses no workflow.
03
Asynchronous checkout

Moving payment status and secondary effects behind the broker bounds request latency and isolates dependencies. Users now need a truthful `PENDING` contract, while operators own backlog age, replay, DLQ and workflows that can remain incomplete for hours.

04
Compensation is not rollback

Releasing inventory, cancelling an order or refunding a payment is a new business action that may fail after the original action became externally visible. Every compensation needs its own idempotency, legal precondition, audit record and reconciliation fallback.

05
Outbox guarantee

The local database change and outbox row are atomic, but publication can repeat and consumers can crash after their side effect. Stable event ids, aggregate sequence checks and inbox/effect uniqueness are permanent costs of the reliability gained.

06
Database per service

Ownership and failure isolation improve, but joins, reports and cross-domain consistency become asynchronous products. Do not let the Saga update another service's tables, and build analytics from events/CDC rather than cross-service request-time joins.

07
Adoption order

Tune query/index and pools, isolate browse from checkout, add CDN/cache and asynchronous secondary effects, then partition consumers and only later shard/cell. Each step needs a triggering metric, owner, rollback and failure drill; otherwise the architecture can only grow.

Failure review — answers for this design
01

Which invariant can break?

Oversell, duplicate capture and an order marked confirmed while stock or payment disagrees are the critical failures.

  • Inventory conditional updates, one provider idempotency key and legal versioned transitions in each authoritative service guard them
  • the Saga coordinates but is not the source of truth for participant state.
02

Which metric detects it first?

Watch accepted-to-completed checkout ratio and p99 together with oldest non-terminal Saga age, outbox age, consumer lag, reserve-conflict rate, PSP `UNKNOWN` age and reconciliation mismatches. Queue depth alone hides a stalled partition.

03

How is blast radius contained?

Use separate gateway routes, pools, concurrency budgets and bounded queues for browse, cart, checkout, PSP and after-payment lanes. Partition by order/SKU as required, cap one campaign or hot SKU at admission, and let secondary consumers lag without consuming checkout capacity.

04

Can retry duplicate or reorder work?

Yes by default. Bind the client key to a canonical request hash and original response, reuse the same provider key, assign every command/event a stable id plus aggregate version, and apply each consumer effect in a local transaction with an inbox or unique business key.

05

How do we repair and prove recovery?

Reconcile aged Saga rows against Order, Inventory, Payment and the PSP; replay committed outboxes; repair by explicit confirm, release, cancel or refund transitions; then redrive quarantined events. Prove recovery with zero unmatched captures/reservations, bounded outbox and consumer age, and sampled aggregate sequence checks.

Engineering deep dives

Correctness across money and inventory

The database protects local invariants; idempotency, state machines and reconciliation protect the workflow around it.

Make commands repeatable

  • Persist idempotency key, request fingerprint and original response together. Reject key reuse with different parameters and define retention from the maximum retry window.
  • Represent pending and unknown outcomes explicitly. After a timeout, query authoritative provider state before retrying or compensating an irreversible action.

Keep invariants local

  • Put uniqueness, balance and legal state transitions in one transaction and enforce them with constraints, conditional updates or locks—not a cache lock.
  • Choose isolation from the anomaly to prevent. Serializable transactions can abort under contention, so the whole transaction needs a bounded retry path.

Close the distributed gap

  • Write business state and an outbox record atomically; consumers deduplicate effects. Exactly-once inside one platform does not make an external PSP or airline atomic.
  • Reconcile independent statements, retain immutable audit history and repair by compensating entries. Monitor aged pending states and unmatched totals as correctness SLIs.

Asynchronous delivery and replay

Moving work off the request path trades immediate failure for lag, duplicates, ordering constraints and operational backlog.

Define delivery semantics

  • Assume at-least-once at service boundaries. Give each event a stable ID, partition key, schema version and event time; make every side effect idempotent.
  • Guarantee order only within the business entity that needs it. Global order limits parallelism and usually encodes no useful invariant.

Treat lag as user impact

  • Observe oldest-message age, input/output rate, retry count, poison messages and partition skew. Queue depth alone hides slow old work behind new small messages.
  • Use retry topics or delayed queues with expiry and a DLQ; DLQ is not resolution until it has ownership, alerting and a safe replay tool.

Evolve safely

  • Use backward/forward-compatible schemas and tolerant readers. Deploy consumers before producers when adding fields and preserve raw events for bounded replay.
  • Replay into an isolated output or shadow consumer first; throttle it so historical traffic cannot starve live processing or repeat external effects.

Caching as a bounded copy

A cache is a disposable, stale copy with a failure mode. Its key, TTL and origin-protection plan are part of correctness.

Choose what may be stale

  • Include tenant, authorization dimension and schema version in keys. Never cache a security or monetary decision unless the product defines acceptable staleness.
  • Use cache-aside for simple reads, versioned keys for safe rollout and randomized TTLs to avoid synchronized expiry; cap negative-cache lifetime.

Protect the origin

  • Coalesce concurrent misses, refresh hot values ahead of expiry and bound rebuild concurrency. A cache outage must not instantly multiply origin load by the hit ratio.
  • Monitor hit ratio by key class, eviction, memory fragmentation, hot keys, fill latency and origin amplification—not only cache latency.

Compare tiers

  • L1 removes a network hop but multiplies stale copies; shared L2 centralizes data and invalidation but adds a network dependency and hotspot risk.
  • Choose LRU/LFU/TTL from access distribution and object value. If eviction loses authoritative state, the component is a database wearing a cache label.

Indexes, ranking and freshness

Fast ranking comes from a bounded candidate set and a versioned derived index, not from querying the source of truth on every keystroke or feed read.

Separate retrieval from ranking

  • Retrieve a bounded candidate set using prefix, graph, time or score indexes; rank it with a versioned rule/model and keep a deterministic fallback.
  • Store the ranking/model version and stable tie-break key so pagination, audits and experiments can reproduce an ordering.

Control index freshness

  • Measure event-to-searchable lag by percentile and entity class. Rebuild into a new version, validate counts/checksums, then atomically switch readers.
  • Re-check authorization, deletion and hard availability constraints at read time; an eventually consistent candidate index must not bypass current policy.

Bound cost and abuse

  • Debounce typeahead, cap prefix/fuzzy expansion and cache popular anonymous prefixes. Personalization reduces cacheability and increases privacy review.
  • Track empty-result rate, candidate count, ranking latency, index size, stale-result complaints and quality metrics separately from availability.

Evolution without premature distribution

Scale by measured bottleneck and preserve a reversible path; every new datastore creates consistency and on-call obligations.

Use the cheapest lever first

  • Fix query shape and indexes, bound connection pools, add replicas/caches, then asynchronous read models before partitioning or sharding the source of truth.
  • Record the metric and threshold that justify each step. A component without a removal criterion tends to become permanent architecture.

Separate models only when needed

  • CQRS can share one store first. Split physical stores only when read/write load, model or security boundaries demand independent scaling.
  • Treat every derived model as rebuildable: version transformations, retain a replay source, compare counts/checksums and rehearse backfill under live load.

Partition around invariants

  • Choose a key that keeps the common transaction local and spreads writes; quantify skew before rollout and define how hot tenants/entities are isolated.
  • Use expand-migrate-contract for schema and dual-read verification for data moves. Avoid unbounded dual writes; give migration a completion SLI and rollback point.

Reliability, overload and recovery

Reliability is a user-visible contract. Capacity, retries and failover must be designed as bounded control loops rather than emergency switches.

Prevent positive feedback

  • Give every call an end-to-end deadline; derive shorter per-hop timeouts from the remaining budget and cancel work the caller no longer needs.
  • Retry only classified transient failures, cap attempts, add exponential backoff with jitter and enforce a retry budget so recovery traffic cannot become the outage.

Degrade deliberately

  • Use admission control, bounded queues, concurrency limits and load shedding before saturation; queue depth without oldest-age is not enough to see stalled work.
  • Define which features fail closed, fail open, serve stale data or become read-only. Test the degraded contract with dependency latency, partial-region loss and bad configuration.

Prove recovery

  • Set RTO and RPO per journey, automate restore/failover where safe, and regularly restore production-shaped backups into an isolated environment.
  • Roll out by canary or cell, compare user SLIs, and keep rollback independent of the failing control plane. A failover plan that has never been exercised is an assumption.

A service-local reservation plus outbox transaction:

BEGIN;
--
INSERT INTO command_inbox(command_id, request_hash, status)
VALUES (:command_id, :request_hash, 'PROCESSING')
ON CONFLICT (command_id) DO NOTHING;
-- if row_count = 0: stop and return the stored outcome
--
UPDATE inventory
SET available = available - :qty, version = version + 1
WHERE sku_id = :sku_id
  AND available >= :qty
  AND version = :expected_version;
-- require row_count = 1, otherwise roll back as SOLD_OUT/CONFLICT
--
INSERT INTO reservation(id, sku_id, order_id, qty, state, expires_at)
VALUES (:reservation_id, :sku_id, :order_id, :qty, 'HELD', :expires_at);
--
INSERT INTO outbox_event
  (event_id, aggregate_id, aggregate_version, event_type, payload)
VALUES
  (:event_id, :sku_id, :next_version, 'StockReserved', :payload);
--
UPDATE command_inbox SET status = 'RESERVED'
WHERE command_id = :command_id;
COMMIT;

The relay may publish that outbox row more than once after a crash. Consumers therefore keep an inbox or an effect-specific unique key and reject stale aggregate versions. This closes the database/broker dual-write gap; it does not make checkout exactly-once across the PSP.

An idempotent, version-guarded payment event consumer:

BEGIN;
--
INSERT INTO event_inbox(consumer, event_id, aggregate_id, sequence_no)
VALUES ('checkout-saga', :event_id, :order_id, :sequence_no)
ON CONFLICT (consumer, event_id) DO NOTHING;
-- if row_count = 0: duplicate; commit no business effect
--
UPDATE checkout_saga
SET state = 'PAYMENT_SUCCEEDED', version = version + 1
WHERE saga_id = :saga_id
  AND state IN ('PAYMENT_PENDING', 'PAYMENT_UNKNOWN')
  AND version = :expected_version;
-- require row_count = 1; otherwise ROLLBACK and park/reconcile the event
--
COMMIT;

The inbox and Saga transition share one local transaction, so a crash cannot record only one of them. Aggregate sequence/version detects stale or out-of-order delivery; it does not repair it automatically, so the consumer parks the record rather than silently acknowledging an impossible transition.

Operations and proof: A cell outage should create scoped PENDING or stale behavior, never hidden global inconsistency.
