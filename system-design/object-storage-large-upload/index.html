Scope and problem framing

Upload, resume, finalize, version and download large immutable objects. Metadata coordinates ownership and lifecycle while clients transfer chunks directly to storage nodes or a managed object store.

Requirements

Functional requirements

  • Initiate a multipart upload, hand the client a way to send parts directly to storage, and complete the upload into a single addressable object.
  • Resume an interrupted upload by listing the parts already stored, so a dropped connection costs one part rather than the whole file.
  • Verify integrity per part and for the assembled object, and reject a completion whose parts do not match what the client claims.
  • Expire incomplete uploads on a lifecycle policy, because abandoned parts are billed storage that nothing references.

Quality attributes

  • The application must not be in the data path. Bytes flow from client to storage directly; the service issues credentials and records metadata, and its capacity is therefore unrelated to file size.
  • An upload that the client believes succeeded must be readable, complete and byte-identical. Integrity is verified, not assumed, because a truncated part is silent.
  • Failure granularity is one part. Any design where a network drop at 90% costs the whole transfer has chosen the wrong unit.
  • Metadata operations and bulk transfer are different workloads with different limits, and conflating them is how a listing API becomes the bottleneck on a storage system.

Capacity and constraints

  • Size the control plane by upload-initiation peak and the data plane by bytes, and never mix the two: ~25 rps peak (100k uploads/day) at T2 and ~250 rps peak (1M/day) at T3 for the metadata API, while the byte volume at the same tier is a network and storage question with completely different units.
  • Part count is the number that drives the control plane. A 5 GB file at a 16 MB part size is over 300 parts, so one upload is one initiate, 300-plus part registrations and one complete — the metadata API sees two orders of magnitude more traffic than the upload count suggests.
  • Part size is a real trade with a floor and a ceiling:too small multiplies request overhead and metadata rows, too large makes a failed part expensive to retry. Between 8 and 64 MB suits most networks, and it should be chosen from measured client conditions rather than from a default.
  • Judge presigned direct-to-storage upload per tier:worth it at T1 and T2, where it mostly saves bandwidth cost and complexity; mandatory at T3 and above, because proxying bytes through the application means scaling the application with file size rather than with request count; needs its own scaling story wherever uploads must be scanned or transformed, since that reintroduces a data path the presigned URL removed.
  • Budget replication or erasure-coding overhead explicitly.
    • Three-way replication is 3× the raw bytes
    • erasure coding is closer to 1.5× and costs CPU on read repair, so the storage bill follows the durability choice more than the data volume.
  • Model the read side separately:incomplete uploads, repair traffic and CDN hit ratio all consume capacity that the upload path never sees, and abandoned parts accumulate silently until a lifecycle rule removes them.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Upload session

upload id, target object key, owner, part size, initiation time and state. This is what makes resumption possible and what a lifecycle rule expires.

02Part record

upload id, part number, size, checksum and storage location. The part number gives the assembly order, so parts may arrive in any order and even in parallel.

03Object

final key, size, content type, checksum, storage class and version. Versioned, because overwriting is the one operation that cannot be undone without it.

04Multipart completion manifest

the ordered part list and checksums the client asserts, checked against the part records before the object is materialized.

05Lifecycle rule

the age at which incomplete uploads are abandoned and the transition schedule between storage classes, stored as configuration rather than encoded in a job.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01Presigned URLs or short-lived scoped credentials…

Presigned URLs or short-lived scoped credentials issued by the control plane, so the client uploads directly to storage. This single decision is what decouples service capacity from file size.

02Multipart upload with per-part checksums

the part is the unit of retry, the unit of parallelism and the unit of verification, all at once.

03Object store with erasure coding or…

Object store with erasure coding or replication chosen from the durability target, and a storage class transition for data that is written once and read rarely.

04A completion step that validates the…

A completion step that validates the manifest against the recorded parts before publishing the object key. Publishing first and validating later is how a half-assembled object becomes readable.

05CDN in front of reads with…

CDN in front of reads with a versioned object key, so a new version is a new URL rather than an invalidation that has to reach every edge.

06Observability

initiate-to-complete duration, part retry rate, part size distribution, incomplete-upload count and age, integrity failures at completion, and storage overhead ratio against raw bytes.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

The control plane never touches the bytes

Abridged. Three calls and no data path: the service issues credentials, the client transfers, the service validates. Capacity here is a function of part count, not of gigabytes.

java
UploadSession initiate(String key, long size, UserId owner) {
    int partSize = choosePartSize(size);        // measured, not a constant
    return sessions.create(key, owner, partSize, storage.initiateMultipart(key));
}

URI urlForPart(String uploadId, int partNumber) {
    UploadSession s = sessions.require(uploadId);
    // short-lived and scoped to exactly one part of one object: a leaked URL
    // cannot be replayed against another key or after the window
    return storage.presignPart(s.storageKey(), s.storageUploadId(), partNumber, PART_URL_TTL);
}

ObjectRef complete(String uploadId, List<PartAssertion> claimed) {
    UploadSession s = sessions.require(uploadId);
    List<PartRecord> recorded = parts.listFor(uploadId);

    // validate BEFORE publishing the key: a half-assembled object must never be readable
    if (!manifestMatches(claimed, recorded)) throw new IntegrityMismatch(uploadId);

    return storage.completeMultipart(s.storageKey(), s.storageUploadId(), recorded);
}

Resume costs one part, not the file

The client asks what the store already has and sends only the gap. Without this listing, a drop at 90% restarts at zero.

bash
# what does the store already hold for this upload?
aws s3api list-parts --bucket media --key video/42.mp4 --upload-id "$UPLOAD_ID"

# send only the missing part numbers, in bounded parallel
aws s3api upload-part --bucket media --key video/42.mp4 \
  --upload-id "$UPLOAD_ID" --part-number 217 --body part-217.bin

# abandoned uploads are billed storage nothing references — expire them by policy
aws s3api put-bucket-lifecycle-configuration --bucket media \
  --lifecycle-configuration file://abort-incomplete-after-7-days.json

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
Direct-to-storage upload removes the application from…

Direct-to-storage upload removes the application from the data path and removes its ability to scan, transform or watermark the bytes. If content must be inspected, it happens after completion on an event, which means the object exists before it has been approved.

02
Small parts give fine-grained retry and…

Small parts give fine-grained retry and multiply request count and metadata rows; large parts are cheaper to track and more expensive to lose. The right size depends on the client network, so measure it rather than inheriting a default.

03
Erasure coding cuts storage cost substantially and adds CPU and latency on degraded reads. Replication is more expensive and simpler to reason about under failure

for a small cluster the simplicity often wins.

04
Client-side parallelism makes uploads fast and…

Client-side parallelism makes uploads fast and makes the client the thing that saturates the network, which is exactly what a mobile user on a shared connection does not want. Bound the concurrency rather than maximizing it.

05
Keeping every version is safe and…

Keeping every version is safe and grows the bill forever. A lifecycle policy is the answer, and it must be written when versioning is enabled rather than when the invoice arrives.

06
Verifying the whole-object checksum at completion costs a read of everything just uploaded. Per-part checksums plus a composite check is the usual compromise, and it verifies less than people assume

state which guarantee you actually have.

Failure review — answers for this design
01

Which invariant can break?

A published object key must resolve to a complete, verified object; a key must never become readable while parts are missing. It breaks when completion publishes before validating the manifest, and when a retried part overwrites a different part number.

02

Which metric detects it first?

Integrity failures at completion and part retry rate, watched together. A network or client-side bug shows as retries climbing well before any object is corrupted, and a completion-time mismatch is the last chance to catch it before a reader does.

03

How is the blast radius contained?

The application is not in the data path, so an application outage stops new uploads from starting but does not interrupt transfers already in flight. Failure granularity is one part, and presigned URLs are scoped to a single part of a single object with a short expiry.

04

Can retry duplicate or reorder work?

Parts are addressed by number, so a retried part overwrites itself idempotently and arrival order does not matter — assembly follows the manifest, not the sequence of writes. A retried complete must be idempotent too, or a second call assembles an object that has already been published.

05

How do we repair and prove recovery?

Abort the affected upload sessions and let clients resume from the part list; nothing needs reconstructing because parts are immutable and independently addressed. Recovery is proven when integrity failures return to zero, the incomplete-upload backlog drains under the lifecycle policy, and a sampled set of completed objects matches their asserted checksums.

Engineering deep dives

Object integrity and lifecycle

Separate strongly consistent metadata from bulk bytes and make upload completion a verified state transition.

Secure direct upload

  • Issue short-lived, narrowly scoped presigned operations for one object/session; bind expected size, content type, checksum and tenant ownership in metadata.
  • Treat a presigned URL as a bearer capability. Restrict signature age, prevent key overwrite unless intended and never trust a client-declared MIME type alone.

Verify and finalize

  • Record every part and checksum idempotently, require consecutive parts, then verify full size/checksum before changing the object from uploading to available.
  • Do not treat multipart ETag as the full-object MD5. Persist the selected checksum algorithm/value and verify it again during repair or critical download.

Operate the lifecycle

  • Expire abandoned sessions and orphan parts, quarantine malware scans, version metadata changes and make retention/legal hold override ordinary deletion.
  • Measure incomplete bytes, finalize latency, checksum failures, replication/repair backlog and restore sampling; durability claims require periodic verification.

Observability and security review

Instrumentation should explain user impact and the responsible dependency without leaking identity or creating unbounded telemetry cost.

Start from user SLIs

  • Define success, latency, freshness and correctness SLIs at the system boundary; alert on error-budget burn, then use dependency metrics for diagnosis.
  • Correlate traces, metrics and structured logs with trace/span IDs. Preserve request, policy and schema versions but redact secrets and sensitive payloads.

Keep telemetry bounded

  • Never use user ID, object ID or raw URL as a metric label. Use logs/traces for high-cardinality detail and explicitly monitor cardinality overflow.
  • Sample by value: retain errors, slow paths and rare business failures at higher rates while keeping predictable storage and query cost.

Review the trust boundary

  • Authorize the object and action on every request, use least-privilege service identities and short-lived credentials, encrypt in transit/at rest and audit privileged changes.
  • Threat-model abuse, replay, enumeration, tenant crossover and data retention. Security controls need degraded behavior and recovery drills like every other dependency.

Treat uploads as a control-plane state machine, not merely a signed URL: UPLOADING → PENDING_SCAN → AVAILABLE or QUARANTINED, with FAILED and EXPIRED paths.

▸ DEEP DIVE · SENIOR
  • create an upload session only after authorization and quota reservation. Bind each presigned URL to tenant, object or part, key prefix, method, expected content length/type/checksum, and short expiry; it is a narrowly scoped capability, not broad storage access.
  • a presigned URL or resumable session URI is a bearer capability: anyone who obtains it can use it within scope until expiry. Keep it out of logs and analytics, give it one purpose and a short TTL, and assume the storage provider may not offer immediate revocation.
  • complete multipart upload only after the server verifies expected parts, ownership, idempotency key, and checksum policy. A multipart or encrypted object ETag is not generally an MD5 integrity proof.
  • persist the part manifest and final checksum so completion is idempotent and only one control-plane transition publishes the object.
  • do not expose the object through CDN or read URLs until validation and malware scanning complete. Store metadata and access policy separately from opaque object-store keys.
  • deduplicate only inside a tenant or an explicitly authorized boundary; cross-tenant hashes can leak that another customer uploaded the same file.
  • abort abandoned multipart uploads, release or reconcile quota reservations, expire orphan metadata, and apply lifecycle, retention, legal-hold, audit, and deletion policies deliberately.

Case metadata:

  • Workload: bytes per object, multipart concurrency, tenant quota and upload burst
  • Freshness: scan/finalization/publication status is durable while progress is approximate
  • Duplicate tolerance: upload session, part number/checksum and finalize key
  • Recovery owner: upload/security owner and object-store lifecycle job

Provider/version boundary: S3 multipart uploads and GCS resumable sessions have different session, checksum, completion and cleanup contracts.

An S3 multipart ETag is not generally a complete content hash; use the documented checksum algorithm and finalization response for the selected provider/version.

A presigned URL or session URI is a time-limited capability, not a harmless API token.

Security and failure tests: Bind capability to tenant/object/method/expiry and do not put it in ordinary logs. Test checksum mismatch, replayed part, wrong offset, URL leakage, scan timeout/quarantine, finalize replay, quota race, abandoned-part cleanup and publication only after policy approval.
