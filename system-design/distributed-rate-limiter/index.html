Distributed rate limiter as a shared service

Protect shared APIs across many gateway and service instances. Limits may apply to a user, tenant, credential, IP, endpoint or weighted cost, and must behave predictably under concurrency and Redis failure.

Scope and problem framing

Protect shared APIs across many gateway and service instances. Limits may apply to a user, tenant, credential, IP, endpoint or weighted cost, and must behave predictably under concurrency and Redis failure.

Requirements

Functional requirements

  • Decide allow or deny for a request against a key — user, tenant, API key, IP — within a latency budget small enough to sit in front of everything.
  • Enforce the same budget across every instance of the service, so that adding a node does not multiply the effective limit.
  • Return a refusal the caller can act on:the standard status, the remaining allowance and when to retry, rather than a bare error.
  • Support several limits at once — per second, per minute, per day, per tenant and per endpoint — and apply the most restrictive one that matches.

Quality attributes

  • The limiter must cost less than the work it protects. A limiter that adds a network round trip to every request has moved the bottleneck rather than removed it.
  • The failure mode must be a deliberate decision, stated in the design: fail open and lose enforcement when the store is down, or fail closed and lose the service. Neither is universally right and leaving it undecided means it will be discovered during an incident.
  • The limit must be enforced closely enough to be meaningful and loosely enough to be affordable. Exact global counting at every request is possible and is almost never worth what it costs.
  • A refusal must be cheap. If rejecting a request costs the same as serving it, the limiter provides no protection under exactly the load it exists for.

Capacity and constraints

  • Size the limiter by the traffic it fronts, not by the traffic it allows: at T3 a service admitting ~250 rps peak (1M req/day) may be evaluating several times that during an abuse burst, and at T4 a ~25,000 rps peak service is asking the limiter for a decision on every one of them.
  • The key space, not the request rate, decides the storage shape.
    • Per-user limits at ten million users is a large but bounded key set with a short TTL
    • per-IP limits over the open internet is an unbounded one, and that difference is what makes the second design need eviction.
  • A single hot key is the failure case, not the aggregate. One tenant hammering one endpoint concentrates every decision on one shard, so the per-key hot spot is what to size against rather than the average spread.
  • Judge a centralized counter store per tier:not needed at T1, where one instance can count in memory and be correct by construction; worth it at T2 with a handful of instances, where drift is small and tolerable; mandatory at T3, because per-instance counting multiplies the effective limit by the instance count; needs its own scaling story at T4, where the counter store is sharded, replicated and itself needs a hot-key strategy.
  • Budget the limiter's own store as a hard dependency on the request path: its p99 becomes part of every request's p99, which is why the decision usually has to be one round trip or none.
  • Model the burst allowance explicitly. A limit of 1,000 per minute with no burst rule permits all 1,000 in the first second, so the shape of the allowance matters as much as its size.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Limit policy

key pattern, window, allowance, burst capacity and scope. Configuration rather than code, because a limit that requires a deploy to change is a limit nobody adjusts during an incident.

02Counter state

the key, the current count or token level and the last refill time. Small, hot and short-lived, which is what makes an in-memory store the natural home for it.

03Decision record

for audit and for the caller: whether the request was allowed, which policy matched, the remaining allowance and the retry-after value.

04Hot key registry

keys currently exceeding a per-key rate threshold, used to promote them to a local decision or to a dedicated shard.

05Override list

keys with a raised or suspended limit and an expiry, so that an incident response is a data change rather than a deploy.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01Token bucket is the default

it expresses a sustained rate and a burst in two numbers, refills lazily on read, and does not need a background job. Fixed windows are simpler and allow twice the limit across a boundary; sliding-window log is exact and stores every timestamp.

02A single-round-trip atomic decision

a Lua script or an equivalent server-side operation — because read-then-write from the application makes the limiter itself a race under precisely the concurrency it exists to control.

03A local pre-filter in front of the shared store for keys that are obviously over budget

once a key is refused, the next refusal for the same key does not need a network call.

04Approximate distributed counting for high tiers

each instance holds a local allowance and syncs periodically, trading exactness for a decision that never leaves the process.

05Standard refusal semantics

429 with Retry-After and the rate-limit headers — so that a well-behaved client backs off rather than retrying immediately and amplifying the burst it just caused.

06Observability

decisions per second split by allow and deny, limiter store p99 as a share of request p99, top keys by refusal count, hot-shard skew, and the rate of fail-open events.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

Atomic fixed-window fallback

A short Redis script keeps increment and expiry together; choose fail-open or fail-closed per route.

lua
local count = redis.call('INCRBY', KEYS[1], ARGV[1])
if count == tonumber(ARGV[1]) then
  redis.call('PEXPIRE', KEYS[1], ARGV[2])
end
return count <= tonumber(ARGV[3])

Runredis-cli --eval limiter.lua limit:user:42 , 1 1000 10

Token bucket in one round trip

Lazy refill means no background job: the bucket is brought up to date from the elapsed time on read. Doing this as read-then-write from the application is a race under the exact concurrency the limiter exists to control.

lua
-- KEYS[1] bucket   ARGV: rate_per_sec, burst, now_ms, cost
local state   = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local rate    = tonumber(ARGV[1])
local burst   = tonumber(ARGV[2])
local now     = tonumber(ARGV[3])
local cost    = tonumber(ARGV[4])

local tokens  = tonumber(state[1]) or burst
local last    = tonumber(state[2]) or now

-- refill for the elapsed time, capped at the burst size
tokens = math.min(burst, tokens + (now - last) / 1000 * rate)

if tokens < cost then
  -- tell the caller when it is worth trying again, do not just refuse
  return { 0, math.ceil((cost - tokens) / rate * 1000) }
end

redis.call('HMSET', KEYS[1], 'tokens', tokens - cost, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(burst / rate * 1000) + 1000)
return { 1, 0 }

A refusal the caller can act on

A bare 429 makes a well-behaved client retry immediately and amplify the burst. The headers are what turn a refusal into backpressure.

bash
HTTP/1.1 429 Too Many Requests
Retry-After: 3
RateLimit-Limit: 1000
RateLimit-Remaining: 0
RateLimit-Reset: 3
Content-Type: application/problem+json

{"type":"https://example.com/probs/rate-limit","title":"Rate limit exceeded",
 "detail":"1000 requests per minute for this API key","status":429}

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
A fixed window is one counter and one expiry, and it allows twice the limit across a boundary

the last second of one window plus the first of the next. Sliding window fixes that and costs either a stored log or a weighted approximation.

02
Exact global limits require coordination on…

Exact global limits require coordination on every decision and put the counter store on the critical path; approximate per-instance limits with periodic sync remove the round trip and let the effective limit drift by roughly the sync interval. Above T3 the second is usually the only affordable answer.

03
Fail open keeps the service available and removes the protection at the exact moment an outage might be caused by the traffic being limited. Fail closed protects the backend and turns a limiter outage into a total outage. Choose per limit

abuse protection and quota enforcement do not deserve the same answer.

04
Per-IP limiting catches naive abuse and…

Per-IP limiting catches naive abuse and punishes shared connections and mobile carriers; per-account limiting is fair and requires the request to be authenticated before it can be limited, which is exactly what an unauthenticated flood is not.

05
Rejecting early at the edge is…

Rejecting early at the edge is cheapest and knows the least about the request; rejecting in the application knows the most and has already paid for parsing, authentication and a connection. Most systems need both, at different granularities.

06
A generous burst allowance improves the…

A generous burst allowance improves the experience for legitimate bursty clients and widens the window in which an abusive client does damage. The burst is a product decision, not a tuning constant.

Failure review — answers for this design
01

Which invariant can break?

The sum of what every instance admits for one key must stay within that key's policy. It breaks the moment counting is per instance without coordination, because the effective limit silently becomes the policy multiplied by the instance count.

02

Which metric detects it first?

Limiter store p99 as a share of request p99, together with the fail-open rate.

  • A limiter degrading shows there first
  • a limiter that has stopped enforcing shows as the deny rate falling to zero while upstream traffic is unchanged, which reads as good news and is not.
03

How is the blast radius contained?

Hot keys are promoted to a local decision so one abusive tenant cannot saturate a shard for everyone, the local pre-filter absorbs repeat refusals without a network call, and the fail-open or fail-closed behaviour is chosen per limit rather than globally.

04

Can retry duplicate or reorder work?

A retried decision consumes allowance twice, which is why the decision must be made once per request rather than once per attempt at an internal hop. Reordering is harmless — the bucket is a level, not a sequence — but a clock that moves backwards refills it incorrectly, so the refill must use a monotonic source.

05

How do we repair and prove recovery?

Counters are short-lived, so recovery is mostly waiting: restore the store and the buckets refill within one window. Recovery is proven when the deny rate returns to its baseline shape for the top keys, fail-open events are back to zero, and limiter p99 is a small and stable share of request p99.

Engineering deep dives

Policy and distributed enforcement

A limiter protects a scarce resource; its key, cost model and failure mode matter more than the counter algorithm.

Model the budget

  • Scope by authenticated tenant/user/API key before IP where possible. Charge weighted cost for expensive queries instead of pretending every request costs one token.
  • Separate sustained rate, burst capacity and concurrency. Version policy and shadow new rules before enforcement to measure false positives.

Bound distributed error

  • Use atomic server-side updates for a precise shared bucket; use local token leases only when bounded overshoot is acceptable and measurable.
  • Choose fail-open or fail-closed per endpoint. Authentication, checkout and public reads have different abuse risk and availability cost.

Operate the control

  • Track allowed, rejected and shadow decisions by policy version plus limiter latency, hot keys and degraded-mode duration—without putting user IDs in metric labels.
  • Return a stable error contract and Retry-After where meaningful; combine rate limits with quotas, bot controls and origin concurrency protection.

Observability and security review

Instrumentation should explain user impact and the responsible dependency without leaking identity or creating unbounded telemetry cost.

Start from user SLIs

  • Define success, latency, freshness and correctness SLIs at the system boundary; alert on error-budget burn, then use dependency metrics for diagnosis.
  • Correlate traces, metrics and structured logs with trace/span IDs. Preserve request, policy and schema versions but redact secrets and sensitive payloads.

Keep telemetry bounded

  • Never use user ID, object ID or raw URL as a metric label. Use logs/traces for high-cardinality detail and explicitly monitor cardinality overflow.
  • Sample by value: retain errors, slow paths and rare business failures at higher rates while keeping predictable storage and query cost.

Review the trust boundary

  • Authorize the object and action on every request, use least-privilege service identities and short-lived credentials, encrypt in transit/at rest and audit privileged changes.
  • Threat-model abuse, replay, enumeration, tenant crossover and data retention. Security controls need degraded behavior and recovery drills like every other dependency.

Design a token-bucket limit for a named API: what is the key, refill rate, burst allowance, client response contract, and atomic state in single-node and distributed deployments?10-system-design-rate-limit.rate-limiting-in-depth.q1

The bucket holds up to B tokens, refilling at r tokens/second.

  • each request consumes 1 token; out of tokens → reject/wait
  • allows burst up to B (flexible), average rate limited to r
  • the most common choice for APIs
# pseudo
now = time()
tokens = min(B, tokens + (now-last)*r)
last = now
if tokens >= 1: tokens -= 1; allow()
else: reject()
▸ DEEP DIVE · SENIOR
  • token bucket allows bursts (good for APIs with spikes); leaky bucket smooths output (protects a weak downstream)
  • distributed needs atomicity: store (tokens, last_refill) + compute lazy refill inside a single Redis Lua script (atomic read-compute-write) — don't split into a GET then SET (race condition)
  • calling Redis on every request adds latency → you can use a local per-instance token bucket with a quota = total/N (less accurate under uneven load)

Return a documented machine-readable rejection. Use 429 for a caller-facing rate rejection.

Retry-After is an API policy choice, and emit X-RateLimit-Remaining only when its value and reset semantics are truthful; do not promise these headers at every internal layer. The whiteboard version of this question is (→ Whiteboard exercise: a gateway must enforce per-tenant and…).

  • The full token bucket implementation, including synchronization when multiple threads grab tokens concurrently, is in the LLD round (22-low-level-design-ood.the-lld-framework-classic-problems.q3).

▸ DEEP DIVE · SENIOR
  • fixed window double burst: 100/minute can allow ~200 within the 2 seconds straddling the boundary

How would you implement a Redis-backed shared rate limiter so refill and consumption are atomic, keys expire safely, Cluster key placement and time source are explicit, and outage behavior is deliberate?10-system-design-rate-limit.rate-limiting-in-depth.q4

Shared state in Redis can coordinate stateless instances, but the design must say exactly what is atomic, where the key lives, and what happens when the limiter is unavailable.

  • for a fixed window, increment and expiry must be installed as one operation; a crash between separate INCR and EXPIRE calls can leave an unbounded counter.
  • for token or sliding-window algorithms, one short Redis Lua script can read state, calculate refill or window weight, decide, update state, and set expiry atomically on the serving primary.
  • atomicity is per script execution, not a global guarantee across regions, caches, or a failed primary. Keep scripts short because they block other work on that Redis shard.
Bottom line:

The critical operation is check plus consume plus expiry as one state transition. A separate GET followed by SET is a race, but a Lua script is only correct when its key, time, and failure policy are also explicit.

▸ DEEP DIVE · SENIOR
  • use a stable key such as policy plus tenant plus subject plus route. In Redis Cluster, every key touched by one script must be in the same hash slot; a per-subject bucket is simplest, and multi-key designs need deliberate hash tags.
  • choose one time authority. Redis server time avoids disagreement among application clocks, while a local fallback needs a documented bounded overshoot. Do not silently mix both.
  • choose fail-open, fail-closed, or a smaller emergency local limit from the threat and business invariant; a login endpoint may need brute-force protection even while a broad public read API prefers availability.
  • record the maximum tolerated overage and the reconciliation path, and measure and alert on every fallback.
  • return 429 and a documented retry delay when the policy denies a request. Emit limit or remaining headers only when they describe the actual policy and are safe to expose.
  • apply coarse edge limits, gateway policy limits, service business limits, and downstream concurrency guards for different purposes rather than treating Redis as the only protective layer.

Runnable Redis Lua token bucket — save as token_bucket.lua:

local rate = tonumber(ARGV[1])
local capacity = tonumber(ARGV[2])
local cost = tonumber(ARGV[3])
local t = redis.call('TIME')
local now = t[1] * 1000 + math.floor(t[2] / 1000)
local state = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(state[1]) or capacity
local previous = tonumber(state[2]) or now
tokens = math.min(capacity, tokens + math.max(0, now-previous) * rate / 1000)
local allowed = 0
if tokens >= cost then tokens = tokens - cost; allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', KEYS[1], math.ceil(capacity / rate * 2))
return {allowed, math.floor(tokens), now}

Run one key with rate 10/s, capacity 20, cost 1:

redis-cli --eval token_bucket.lua 'rl:{tenant-42}:checkout' , 10 20 1
# first result: 1 (allowed), 19 (tokens left), server time

TIME avoids client-clock skew, one script makes refill/consume/expiry atomic, and {tenant-42} makes Cluster slot ownership explicit.

  • Benefit: every gateway sees shared state.
  • Cost: Redis latency joins admission; a long script blocks server work; and a hot tenant serializes decisions on one shard. Measure script p99, key skew, and fallback/error rates before increasing concurrency.
  • Failure boundary: define fail-open/closed per resource; at cell scale prefer per-cell allocation over a global Redis round trip.

Durability and expiry boundary:

  • Redis replication is asynchronous by default. A primary can acknowledge a consume before the replica has it; failover may forget accepted tokens. Treat this as bounded overage, not exact quota accounting.
  • math.ceil(capacity / rate * 2) is a cleanup heuristic, not a safety proof. Test idle expiry, refill precision, clock skew, failover, and resharding.
  • On MOVED, ASK, timeout, or an unknown script outcome, retry only a decision that is safe to repeat; otherwise record UNKNOWN and reconcile before repeating the business command.
Which limits belong at the edge, gateway, service, and downstream boundary, and how do rate limit, quota, concurrency limit, and overload shedding differ in keying, response, and policy?10-system-design-rate-limit.rate-limiting-in-depth.q5

Multiple layers:

  • edge/CDN: blocks coarse DDoS (by IP)
  • API gateway: per API key/IP, plan quotas
  • service: per user/endpoint, business rules
  • downstream guard: protects DB/PSP/GDS

Return a documented machine-readable error shape. A caller-facing rate decision commonly uses 429; include retry guidance only when the request is safe to retry and the delay is meaningful.

▸ DEEP DIVE · SENIOR

Distinguish:

  • rate limit (abuse prevention) vs quota (plan/billing limit) vs throttling/backpressure (protects the system under overload) vs concurrency limit (semaphore/bulkhead)

OTA: per-key rate limiting on search fights price-scraping bots; quota for B2B partners per contract; leaky bucket protects the GDS; a concurrency limit (semaphore) to the PSP. Set limits at multiple layers for different purposes, not just one place.

  • The further out you block, the cheaper it is: blocking at the CDN costs almost nothing, whereas by the time a request reaches the service it has already passed the gateway and occupied a connection in the pool.
  • The trade-off is that the further out you go, the less business context you have — the edge doesn't know which plan this user is on.
  • Define one machine-readable error shape, but do not force every layer to emit identical headers. 429 is the usual caller-facing rate rejection; RFC 6585 permits Retry-After, so send it when the retry delay is known and retry is safe.
  • A dependency timeout or overload may instead surface as 503/504, and clients must not retry those blindly.
  • X-RateLimit-* or newer RateLimit fields are compatibility choices: document their units and reset semantics, and omit a value you cannot calculate truthfully. The gateway can map internal rejection reasons to the public contract.

When the shared limiter is unavailable or partitioned, how do you choose fail-open, fail-closed, or local fallback?10-system-design-rate-limit.rate-limiting-in-depth.q6

Classify the endpoint by the invariant it protects before choosing an outage mode.

  • Authentication, password reset, expensive partner calls, money-moving commands, and abuse-sensitive operations usually need fail-closed or a small, explicit local emergency budget.
  • Public browsing or a cacheable read may prefer fail-open for a short window, but record the exception and cap it with a local limiter so an outage does not become unlimited traffic.
  • A local fallback is not equivalent to a global quota: each instance can overshoot, and a network partition can make the aggregate error large. Allocate per-cell budgets when the business can tolerate bounded overshoot.

The decision belongs to the policy owner, not to a generic Redis client default. Emit metrics for limiter latency, errors, fallback decisions, denied requests, estimated overshoot and recovery.

Reconcile billing or quota state from authoritative usage records; a rate limiter is an admission control, not a correctness ledger.

▸ DEEP DIVE · SENIOR

Document the mode per route and failure reason, test failover and clock/region partitions, and alert before the emergency budget is exhausted. The shared Lua transition and Cluster key rules remain the mechanism; this item owns the failure policy.

Design a shared rate-limiting service for stateless gateways across regions. Which limits require an exact global decision, which may be approximate, and how do allocation, Redis Cluster, latency, and outage behavior affect the answer?11-system-design-cases.the-big-prompts.q5

A shared limiter needs an explicit policy contract: trusted code chooses policy ID, authenticated subject, scope, route, and validated cost. The caller must not freely choose its own limit or identity key.

▸ DEEP DIVE · SENIOR
  • for one subject bucket, a short Redis Lua script can atomically read state, refill, decide, consume, and set its idle expiry. A GET followed by SET is a race.
  • Redis Cluster is slot-based: all keys used by one script must share a hash slot through a deliberate hash tag. Cluster replication and failover do not make it an exact global, multi-region authority.
  • distinguish strict global quotas from approximate protection.
  • a contractual supplier quota, paid quota, or security lockout may need a home region, strong coordinator, or non-overlapping expiring leases.
  • regional token leases can improve availability, but must declare bounded overshoot or under-use; total divided by N plus periodic sync is not a correctness guarantee.
  • choose time authority, endpoint-specific fallback, and no-result retry behavior. Do not blindly repeat an uncertain consume request, because the first execution may already have deducted a token.
  • return a documented denial and retry delay only when they represent the actual policy; edge, gateway, service, and downstream concurrency limits protect different resources.

Case metadata:

  • Workload: requests per second, key cardinality, burst, cost per request and region skew
  • Freshness: the limiter decision has a declared exactness/overshoot bound while telemetry may lag
  • Duplicate tolerance: uncertain consume requests need a request key or safe retry contract
  • Recovery owner: limiter service and the protected domain

Provider and failure boundary: For the chosen Redis version and Redis Cluster topology, document hash tags, Lua/function atomicity, replication and failover behavior, clock/TTL assumptions and hot-key limits.

Async replication or WAIT does not by itself create a strongly consistent global quota. A partition must select fail-open, fail-closed or bounded leases per policy.

Answer framework:

  1. Clarify: what is the limit keyed by (user/IP/API key)? Per second or per minute? Are bursts allowed? Is this single-node or distributed?
  2. Choose an algorithm: token bucket is common and allows bursts; a sliding-window counter is more precise and smooths window boundaries
  3. Single node: store (tokens, last_refill) in a map and refill lazily
