Scope and problem framing

Start with the user journeys, invariants and non-goals. The output is not one perfect diagram; it is a defensible chain from workload and failure model to decisions, consequences and the evidence that would make the team revisit them.

Requirements

Functional requirements

  • Name the actors, critical journeys and API contracts before drawing services.
  • Identify the source of truth and the state transition each write is allowed to perform.
  • End with migration, rollback and an explicit list of unresolved questions.
  • Produce a decision record per choice — context, options, consequence, review trigger — so that a future reader can tell a decision from an accident.

Quality attributes

  • State latency, availability, durability, consistency and recovery targets per journey.
  • Separate a correctness invariant from a freshness or performance preference.
  • Review operability:ownership, observability, capacity triggers and failure drills.
  • Every number in the design must have a derivation. An estimate whose origin nobody remembers cannot be revisited when the workload changes, which is the only reason to have written it down.

Capacity and constraints

  • Lead every capacity line with the peak rate and put the daily volume in parentheses, because requests per day is the number a team actually knows about its own system: 250 rps peak (1M req/day) is a T3 service, and the four tiers — 10k, 100k, 1M and 100M per day — are the yardstick every decision on this site is judged against.
  • Derive the peak rather than guessing it:peak is roughly 20× the average, and the shape is the assumption to state out loud. Consumer and campaign traffic concentrates 10–20×; steady internal and B2B traffic concentrates 3–5×.
  • Judge each proposed component per tier in four words — not needed, worth it, mandatory, needs its own scaling story — and make the reviewer say which one applies. A component with no tier verdict is a component nobody has justified.
  • Treat 10M/day as the documented waypoint inside T4 rather than a fifth tier: T1 to T3 is 10× per step, T3 to T4 is 100×, and that last jump is where a system stops growing and changes shape into cells, shards and regional isolation.
  • Carry units through every estimate and include indexes, replicas, logs, backups and growth. A storage number that counts only the rows is wrong by a factor that depends entirely on what was left out.
  • Turn the estimate into a benchmark or a scaling trigger. Arithmetic is an input, not proof: the review's output is a number to measure against, plus the threshold at which the decision gets revisited.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Decision record

context, options considered, the choice, its consequences and the trigger that would make the team revisit it. The trigger is the field most often left blank and the one that makes the record useful a year later.

02Workload envelope

average, peak, burst duration, skew and growth assumptions, with the tier the design is being built for stated explicitly.

03Risk register

invariant, failure mode, detection signal, mitigation, owner and residual risk. A risk with no detection signal is a risk nobody will notice arriving.

04Non-goals

what the design deliberately does not do, written down, because an unstated non-goal reappears as a requirement halfway through implementation.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01Diagram

Mermaid source in version control so an architecture change is reviewable as text, with a diff, rather than as two images someone has to compare by eye.

02Decision log

ADRs or RFCs linked to rollout metrics and operational runbooks, so the reason for a choice and the evidence about it live in the same place.

03Validation

load tests, failure injection, schema and contract tests, and restore drills — each one chosen from a specific risk in the register rather than from a general sense of diligence.

04A capacity model that is a spreadsheet or a script, not a paragraph

the point is that changing one assumption changes every number that depends on it.

05A written degradation plan naming which…

A written degradation plan naming which journeys survive, which features are shed and in what order, so that the shed order is a decision rather than whatever the code happens to do.

06Review checkpoints tied to thresholds rather than to the calendar

a design is revisited when the workload, the regulation, the cost of an outage or the team's capability crosses a recorded line.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

A decision record with a review trigger

The trigger is the field that makes this useful a year later. Without it the record explains a past choice; with it, the record tells you when the choice expires.

bash
# ADR-014: single Postgres primary for the ledger
#
# Context     1M postings/day -> 250 rps peak (20x the 11.6 rps average,
#             consumer payment traffic, so 10-20x was the assumed shape)
# Tier        T3, designed to the T4 waypoint (10M/day) without resharding
#
# Options     (a) single primary + read replicas   <- chosen
#             (b) shard by account range           - real option, rejected on
#                 operational cost: cross-account transfers become distributed
#             (c) ledger in the app database       - rejected: no retention
#                 boundary, and reconciliation competes with product queries
#
# Consequence one primary is the write ceiling; balance reads move to replicas
#             and are therefore allowed to lag by up to 2s (stated, not implied)
#
# TRIGGER     revisit when sustained write rate exceeds 40% of measured primary
#             capacity, OR when a single account exceeds 5M entries, whichever
#             comes first. Both are on the capacity dashboard.

The tier verdict, applied

Four words, used the same way every time. A component with no verdict is one nobody has justified — that is the whole point of forcing the column.

bash
# component            T1           T2         T3          T4
# ------------------------------------------------------------------------
# CDN                   worth it     worth it   mandatory   mandatory
# shared cache (L2)     not needed   worth it   mandatory   needs its own
#                                                           scaling story
# read replicas         not needed   worth it   mandatory   mandatory

#                                                           scaling story
# sharding              not needed   not needed not needed  needs its own
#                                                           scaling story
# multi-region          not needed   not needed worth it    mandatory
#
# not needed                  = the operational cost exceeds the benefit here
# worth it                    = cheap insurance, not yet required
# mandatory                   = its absence is an incident waiting
# needs its own scaling story = one config line will not do it; it needs a
#                               component and an owner

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
A detailed diagram with unstated assumptions…

A detailed diagram with unstated assumptions is weaker than a small design with explicit boundaries. The diagram shows what exists; the assumptions are what determine whether it will keep working.

02
Do not add sharding, multi-region or…

Do not add sharding, multi-region or a broker without naming the measured constraint it solves. Each one is a permanent operational cost paid for a benefit that must be stated in the same sentence.

03
Every rejected option needs a real…

Every rejected option needs a real advantage. A strawman used only to justify the preferred stack makes the record worthless, because the next reader cannot tell which options were genuinely considered.

04
Designing for the next tier costs…

Designing for the next tier costs complexity now against a load that may not arrive; designing only for the current one risks a rewrite. Naming the tier and the trigger is what turns this from a debate into a decision.

05
A long review finds more problems…

A long review finds more problems and delays the work; a short one ships and discovers the problems in production. The useful compromise is to review deeply along the invariants and lightly everywhere else.

06
Recording a decision costs an hour and pays back only when someone questions it later

which is exactly when the person who made it has left. This is the cheapest documentation in engineering and the first to be skipped.

Failure review — answers for this design
01

Which invariant can break?

The design under review must state its correctness invariants separately from its preferences, and every number must have a derivation. When those blur, a freshness preference gets defended like a correctness rule and a guessed number gets treated as a measurement.

02

Which signal detects a weak design before it is built?

A component with no tier verdict and a number with no derivation. Both are answerable in one sentence by whoever proposed them, and an inability to answer is the signal — long before a load test could tell you the same thing at far greater cost.

03

How is the blast radius of a wrong decision contained?

By the review trigger and the non-goals. A decision recorded with the threshold at which it expires is a decision that can be unwound on schedule rather than discovered during an incident, and a written non-goal stops scope from arriving as an emergency.

04

Can a review duplicate or reorder work?

Yes — two teams solving the same constraint separately is the organizational version of duplicated mechanism, and it is found by the decision log rather than by the diagram. Reviewing the log before the design is what prevents the second copy.

05

How do we prove the design was right?

By the benchmark the estimate turned into and the threshold it named. The design is validated when measured behaviour lands inside the stated envelope, the risk register's detection signals are actually emitting, and every decision record has an owner and a trigger that someone is watching.

Engineering deep dives

Reliability, overload and recovery

Reliability is a user-visible contract. Capacity, retries and failover must be designed as bounded control loops rather than emergency switches.

Prevent positive feedback

  • Give every call an end-to-end deadline; derive shorter per-hop timeouts from the remaining budget and cancel work the caller no longer needs.
  • Retry only classified transient failures, cap attempts, add exponential backoff with jitter and enforce a retry budget so recovery traffic cannot become the outage.

Degrade deliberately

  • Use admission control, bounded queues, concurrency limits and load shedding before saturation; queue depth without oldest-age is not enough to see stalled work.
  • Define which features fail closed, fail open, serve stale data or become read-only. Test the degraded contract with dependency latency, partial-region loss and bad configuration.

Prove recovery

  • Set RTO and RPO per journey, automate restore/failover where safe, and regularly restore production-shaped backups into an isolated environment.
  • Roll out by canary or cell, compare user SLIs, and keep rollback independent of the failing control plane. A failover plan that has never been exercised is an assumption.

Observability and security review

Instrumentation should explain user impact and the responsible dependency without leaking identity or creating unbounded telemetry cost.

Start from user SLIs

  • Define success, latency, freshness and correctness SLIs at the system boundary; alert on error-budget burn, then use dependency metrics for diagnosis.
  • Correlate traces, metrics and structured logs with trace/span IDs. Preserve request, policy and schema versions but redact secrets and sensitive payloads.

Keep telemetry bounded

  • Never use user ID, object ID or raw URL as a metric label. Use logs/traces for high-cardinality detail and explicitly monitor cardinality overflow.
  • Sample by value: retain errors, slow paths and rare business failures at higher rates while keeping predictable storage and query cost.

Review the trust boundary

  • Authorize the object and action on every request, use least-privilege service identities and short-lived credentials, encrypt in transit/at rest and audit privileged changes.
  • Threat-model abuse, replay, enumeration, tenant crossover and data retention. Security controls need degraded behavior and recovery drills like every other dependency.

How would you lead a 45-minute system-design interview from requirements to a defensible design, and decide which assumptions, capacities, risks, and trade-offs deserve a deep dive?10-system-design-rate-limit.framework-building-blocks.q1

7 steps:

  1. Clarify requirements: functional + non-functional (scale, p99 latency, availability, consistency)
  2. Capacity estimation: read/write QPS, storage, bandwidth
  3. API design: a few core endpoints
  4. Data model: tables/collections, indexes, SQL vs NoSQL
  5. High-level diagram: client → LB → service → cache/DB/queue
  6. Deep dive into 1-2 critical components
  7. Bottleneck & trade-off: pain points, how to scale, what you're trading off
Bottom line:

lead the conversation, keep surfacing trade-offs and confirming assumptions. What's judged is the thinking and reasoning, not a perfect diagram.

▸ DEEP DIVE · SENIOR
  • start by clarifying functional + non-functional requirements (QPS, p99 latency, availability, consistency, read/write ratio) — don't dive straight into drawing boxes
  • keep stating trade-offs & confirming assumptions ('assume 10M bookings/day, p99 < 200ms, strong ledger consistency — correct?')
  • deep-dive into 1-2 core components

The interviewer grades your thought process (decomposition, trade-offs, bottlenecks), not a pretty diagram. Close with 'where's the bottleneck, how would it scale, what's the trade-off' — that's what sets senior apart.

▸ DEEP DIVE · SENIOR

What would change this answer — state these before defending the design; each is an assumption the interviewer can ask you to justify, and a measurement that would falsify it:

  • Which limiter authority and failure policy the application needs: local best-effort, Redis with bounded overage, a gateway service, or strongly consistent — and the maximum overage the business can reconcile after a failover.
  • Whether the guarded commands are idempotent. If not, say what stops a retry after a timeout from performing the business action twice.
  • The trusted proxy chain behind an IP-based key, and how NAT and shared-IP users are treated.
  • The Redis version, client and cluster topology the code targets — script and function behaviour is version-sensitive.
  • The measurements that would falsify the design: p99 decision latency above the endpoint budget, key skew making one shard hot, a failover losing more than the agreed overage.
  • If the authoritative resource cannot enforce fencing or version checks, downgrade every "the limiter preserves correctness" claim to "it reduces load".
Given daily volume, peak-to-average ratio, payload size, replication, and retention, how do you estimate read/write QPS, storage, bandwidth, and the first capacity threshold that changes the architecture?10-system-design-rate-limit.framework-building-blocks.q2

Use 86,400 seconds as the arithmetic constant; the other values are assumptions until measured.

Assumption table (illustrative, not a benchmark):

InputIllustrative assumptionMeasure before sizing
Volume10M/day → 115.7 average QPSpeak/average, p95/p99 burst, retry attempts
Payload500 B logical recordwire bytes, headers, compression
Storage1.8 TB/year rawindex, metadata, replicas, retention
Capacityno portable QPS numbercode path, hardware, runtime, DB, p99 target
  • Average QPS = daily volume / 86,400; peak QPS = average × the stated peak-to-average factor.
  • Bytes/s = peak QPS × measured request/response bytes. Storage = records × logical size × index/metadata/replica/retention factors.
  • reads ≫ writes can justify cache/replicas only when freshness and authorization boundaries allow it.

Measurement exercise:

  1. Replay a representative read/write mix and payload distribution against one candidate instance and database.
  2. Sweep arrival rate and concurrency until p99, errors, queue age, connection wait, CPU/memory, or I/O crosses its budget.
  3. Repeat with retry amplification and dependency-failure injection; record the safe operating point, burst duration, and rollback threshold.
Bottom line:

Use the arithmetic to find the first bounded resource; treat every capacity number as a workload-specific result.

▸ DEEP DIVE · SENIOR
  • Keep R_sustained, R_peak, payload, retries, replication, and retention as explicit inputs; include headers and compression in byte estimates.
  • A statement such as “one instance handles a few thousand QPS” is not portable without the code path, hardware, runtime, dependency shape, and tail-latency target.
  • The architecture changes when a bounded resource reaches its safe limit: bytes, file descriptors, connections, CPU, memory, queue age, DB locks/I/O, or provider quota.
How should a capacity estimate include bytes, concurrency, retries, and the first architectural threshold?10-system-design-rate-limit.framework-building-blocks.q7

Start with a workload table, not a single QPS number:

  • average request rate = daily volume / 86,400; peak rate = average × the stated peak-to-average factor;
  • ingress or egress bytes/second = peak requests/second × the measured payload distribution, including headers and compression assumptions;
  • retained storage = records × logical size × index, replica, metadata, and retention factors;
  • in-flight work is approximately arrival rate × latency (Little's law), then split it across connection, thread, worker, database, and downstream pools;
  • retry amplification = original work plus every retry attempt, multiplied again when several layers retry the same failure.

The first architecture threshold is whichever bounded resource reaches its safe operating limit first: network bytes, file descriptors, connection acquisition, CPU, memory, queue age, database I/O/locks, or a downstream quota.

State the limit, target utilization, burst duration, and what happens at saturation. A fixed claim such as “one instance handles X QPS” is not portable without payload, code path, latency target and failure assumptions.

Interview contract:

Show one optimistic, one peak, and one retry-amplified scenario. The point is to expose the threshold that changes the design, not to pretend a rough estimate is a benchmark.

Given a proposed system design, how would you review scope, workload, contracts, state ownership, critical paths, failure behavior, operations, and trade-offs—and turn each gap into a concrete follow-up question?11-system-design-cases.the-big-prompts.q12

A strong design is a chain of explicit decisions. Use the same scorecard for a payment system, feed, cache, chat, or URL shortener so visual complexity does not hide missing correctness.

DimensionEvidence expected
Scope and successactors, top journeys, out-of-scope features, SLI/SLO, compliance and business invariants
Workloadread/write/event rates with units, payload and retention ranges, peak/average ratio, growth and skew assumptions
ContractsAPI/event examples, idempotency, ordering, pagination, compatibility, authentication and authorization boundaries
State ownershipdata model, source of truth, indexes/partitions, consistency, transaction boundary, lifecycle and deletion
Critical pathone end-to-end write and read, sync/async boundaries, queues, caches and external dependencies
Failure behaviortimeouts, retry eligibility/budget, duplicates, partial failure, overload/backpressure, recovery and reconciliation
OperationsSLIs, alerts, tracing/audit, rollout/rollback, capacity headroom, disaster recovery and cost drivers
Trade-offwhy this option fits the stated constraints, what was rejected, and which measurement would change the choice
Interview flow:

Clarify and rank requirements, estimate only the quantities that affect architecture, draw a minimal baseline, walk one critical path, then deepen the highest-risk bottleneck or invariant.

End by testing the design against a traffic spike, dependency outage, duplicate request, zone loss, and schema/version rollout. Adapt the time split to the interview instead of reciting a fixed minute-by-minute script.

▸ DEEP DIVE · SENIOR

Use ranges and sensitivity analysis rather than precision theatre: peak writes/s × bytes/event × retention is useful when every term has a unit and source. Label assumptions and revisit them. A diagram earns credit only when ownership, protocol, and failure semantics are explainable.

Correctness and availability must be separated. Some domains tolerate stale reads; a ledger cannot tolerate an unbalanced entry.

Likewise, adding Kafka, Redis, or multiple regions is not “scale” by itself—it introduces state, failure modes, and an operating cost that must answer a stated requirement.

Case metadata:

  • Workload: read/write/event rates, payload, retention, peak ratio, tenant skew and dependency quota
  • Freshness: each projection and measurement has a stated observation time
  • Duplicate tolerance: repeated review evidence is harmless but business effects still need owners
  • Recovery owner: design reviewer plus the owner of each invariant

Invariant assertion: For every critical scenario, write a property such as “no two active holds for one version” or “one idempotency key maps to one effect.”

The test must inject timeout, crash, replay and stale projection, then assert the property at the authority—not only that an HTTP response looks correct.

▸ DEEP DIVE · SENIOR
  • Bank/fintech payment may require ledger authority, exact idempotency, reconciliation and strong local consistency.
  • OTA search can tolerate stale projections, while the booking/hold write still needs an authoritative state machine.
  • A notification system may accept at-least-once delivery with deduplication; an OTP may need a tighter expiry and abuse budget.
  • Do not reward a design for saying Kafka, Redis, Saga or distributed lock. Ask which invariant the mechanism protects, what it cannot protect, and what evidence would change the choice.
  • Keep the mechanism explanation in its canonical topic: Topic 08 for broker semantics, Topic 09 for workflow correctness, Topic 17 for API contracts, Topic 25 for service/cache behavior, Topic 28 for leases/fencing. Cases should show their different authority and failure model.
  • A complete answer includes a negative path and an operational proof: what is measured, who is paged, how to replay/reconcile, and how rollback works when the schema or provider version changes.

Case metadata:

  • Workload: review time, evidence volume, peak/average assumptions, tenant/data sensitivity and dependency limits
  • Freshness: claims and measurements carry a reviewed-at date and scope
  • Duplicate tolerance: repeated mechanisms are linked to one owner instead of copied
  • Recovery owner: design reviewer and the canonical mechanism owner
