Scope and problem framing

Return a small ranked suggestion list after each keystroke using query, catalog or entity data. Protect users from unsafe suggestions and keep serving when the model-building pipeline is delayed.

Requirements

Functional requirements

  • Return ranked completions for a prefix within a latency budget that is short enough for the suggestion to arrive before the next keystroke.
  • Rebuild the suggestion index from query logs and catalogue data on a schedule, and roll a new version out without a gap in service.
  • Apply locale, personalization signals and policy filtering — blocked terms, unsafe suggestions, and anything the catalogue no longer sells.
  • Serve a degraded but useful result when the ranking model or the personalization store is unavailable.

Quality attributes

  • The latency budget is the feature. A suggestion that arrives after the user has typed the next character has already lost, which puts the target under about 100 ms end to end including the network.
  • Suggestions are read-mostly and rebuilt in bulk, so the serving path can be optimized for reads to a degree that would be reckless in a transactional system.
  • A policy filter must apply at serve time, not only at build time: a term blocked at noon cannot wait for tonight's rebuild to disappear.
  • Index rollout must be atomic from the reader's point of view. Half-old, half-new suggestions for adjacent prefixes read as a bug, not as a deploy.

Capacity and constraints

  • Size the service by keystroke peak, not by search peak, with the daily volume beside it: a search box averaging 4 typed characters turns 1M searches/day into roughly 4M lookups/day, so a T3 product places a T3-to-waypoint load on this one component — ~1,000 rps peak against ~250 rps of actual searches.
  • Debouncing on the client is a capacity decision, not a UI detail. A 120 ms debounce removes most intermediate keystrokes and can halve the request rate before a single server is added.
  • Prefix popularity is extremely skewed and short prefixes are the hottest: one and two character prefixes are a tiny key space serving a large share of traffic, which is exactly why they cache almost perfectly.
  • Judge an edge cache per tier:worth it at T1 and T2, where it is a few lines of configuration for a real win; mandatory at T3, because the keystroke multiplier has already made this the highest-QPS endpoint in the product; needs its own scaling story at T4, where the cache is regional, has its own invalidation on index rollout and must be warmed before a new version takes traffic.
  • Size the index by term count and the fan-out per prefix, not by document count. Ten million suggestions with the top 10 completions per prefix is a small in-memory structure, which is why this workload usually wants memory rather than a search cluster.
  • Budget the rebuild separately:build duration, the memory needed to hold two versions at once during rollout, and the lag between a term becoming popular and it appearing. That lag is a product property and should be stated, not discovered.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Suggestion

normalized term, display value, target reference, locale, score features and policy state. Normalization is the thing that must be identical at build and at query time, or the lookup misses for reasons nobody can see.

02Prefix index

prefix as the key, the ordered top-N suggestion ids with scores, model version and build time. Storing the top N per prefix rather than the full list is what makes a lookup a single read instead of a scan plus a sort.

03Aggregate signal

bounded query and entity counts over a freshness window, with privacy-safe dimensions only. This is the input to scoring and it must not carry a user identifier into the index.

04Policy list

blocked and demoted terms with an effective time, read at serve time so that a takedown is immediate rather than scheduled.

05Version manifest

the current and candidate index versions and their health, so that a rollback is a pointer change rather than a rebuild.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01A trie or finite state transducer…

A trie or finite state transducer held in memory is the classic serving structure, because the top-N list per prefix is precomputed and a lookup is a walk plus a read. A general-purpose search cluster can serve this workload but pays query planning cost the access pattern does not need.

02Offline build pipeline over query logs…

Offline build pipeline over query logs and catalogue data, producing an immutable versioned artifact. Immutability is what makes rollout and rollback symmetric.

03Two-version serving with an atomic pointer swap

load the candidate, warm it, then flip. Holding both versions is what the rollout memory budget is for.

04Edge and in-process cache keyed by…

Edge and in-process cache keyed by normalized prefix and locale, with the index version in the cache key so that a rollout invalidates by construction rather than by a flush.

05Policy filtering applied after retrieval and…

Policy filtering applied after retrieval and before ranking, reading the live blocked list rather than the version baked into the artifact.

06Observability

p99 by prefix length, cache hit ratio split by one, two and three-plus characters, index build duration and age, rollout warmup time, and the share of responses served by the degraded path.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

The whole serving path

Abridged. The order matters twice: normalization happens before the cache key is built, and policy filtering happens after retrieval so a takedown is never cached.

java
List<Suggestion> complete(String raw, Locale locale, UserId user) {
    String prefix = normalize(raw, locale);         // must match the build-time normalizer
    if (prefix.length() < MIN_PREFIX) return List.of();

    // the index version is part of the key, so a rollout invalidates by construction
    CacheKey key = new CacheKey(prefix, locale, index.version());
    List<Suggestion> candidates = cache.get(key, () -> index.topN(prefix, locale, N));

    // read live, not from the artifact: a term blocked at noon must vanish at noon
    List<Suggestion> allowed = policy.filter(candidates);

    return reranker.rerankOrIdentity(user, allowed, LIMIT);
}

Atomic version swap

Abridged. The candidate is warmed before it is visible, which is the difference between a rollout and a latency incident.

java
void activate(IndexArtifact candidate) {
    candidate.load();                       // both versions resident: this is the memory budget
    warmup.run(candidate, hottestPrefixes); // pay the page faults before users do

    if (!health.check(candidate)) {
        candidate.close();
        throw new RolloutRejected(candidate.version());
    }

    IndexArtifact previous = current.getAndSet(candidate);  // atomic pointer swap
    scheduler.schedule(previous::close, DRAIN_WINDOW);      // in-flight reads finish on the old one
}

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
Precomputing the top N per prefix…

Precomputing the top N per prefix makes reads trivial and makes personalization awkward, because a per-user reordering has to happen after retrieval. Retrieve globally and rerank per user, or accept that the index is the same for everyone.

02
A larger N per prefix gives…

A larger N per prefix gives reranking more to work with and multiplies index size by the same factor. Choose N from what the reranker actually consumes, not from what looks generous.

03
Rebuilding nightly is simple and leaves…

Rebuilding nightly is simple and leaves the index a day behind the world; incremental update keeps it fresh and makes the artifact mutable, which costs the atomic rollout that immutability provided.

04
Aggressive caching of short prefixes is…

Aggressive caching of short prefixes is where almost all the win is, and short prefixes are also where a policy takedown is most visible. Keep the policy filter outside the cached payload or a blocked term survives in cache for the length of the TTL.

05
Debouncing improves capacity and slightly degrades…

Debouncing improves capacity and slightly degrades the experience on fast typists. It is a real trade and belongs in the design discussion rather than being hidden in the client.

06
Spell correction and fuzzy matching improve…

Spell correction and fuzzy matching improve recall and expand the key space beyond what a per-prefix precomputation can cover, which usually means a second retrieval path rather than a bigger index.

Failure review — answers for this design
01

Which invariant can break?

A suggestion that policy has blocked must never be shown, and adjacent prefixes must be answered from the same index version. The first breaks when the block list is baked into the artifact instead of read live; the second when a rollout is not atomic and two replicas disagree.

02

Which metric detects it first?

p99 split by prefix length, and cache hit ratio for one and two character prefixes. A rollout that skipped warmup shows as a hit-ratio collapse on exactly those prefixes seconds before the latency budget is breached.

03

How is the blast radius contained?

Serving is read-only against an immutable artifact, so a bad build cannot corrupt anything — it can only be rejected or rolled back by a pointer change. Reranking and personalization sit behind a degraded path, so their loss costs relevance rather than suggestions.

04

Can retry duplicate or reorder work?

The serving path is idempotent and has nothing to duplicate. The build pipeline can process the same log window twice, so aggregation must be idempotent per window or a popular term is double-counted and outranks the truth.

05

How do we repair and prove recovery?

Roll the version pointer back to the last healthy artifact; nothing needs rebuilding because artifacts are immutable and retained. Recovery is proven when p99 by prefix length is back inside budget, the hit ratio for short prefixes has recovered, and a sampled set of blocked terms returns no suggestion from any replica.

Engineering deep dives

Indexes, ranking and freshness

Fast ranking comes from a bounded candidate set and a versioned derived index, not from querying the source of truth on every keystroke or feed read.

Separate retrieval from ranking

  • Retrieve a bounded candidate set using prefix, graph, time or score indexes; rank it with a versioned rule/model and keep a deterministic fallback.
  • Store the ranking/model version and stable tie-break key so pagination, audits and experiments can reproduce an ordering.

Control index freshness

  • Measure event-to-searchable lag by percentile and entity class. Rebuild into a new version, validate counts/checksums, then atomically switch readers.
  • Re-check authorization, deletion and hard availability constraints at read time; an eventually consistent candidate index must not bypass current policy.

Bound cost and abuse

  • Debounce typeahead, cap prefix/fuzzy expansion and cache popular anonymous prefixes. Personalization reduces cacheability and increases privacy review.
  • Track empty-result rate, candidate count, ranking latency, index size, stale-result complaints and quality metrics separately from availability.

Caching as a bounded copy

A cache is a disposable, stale copy with a failure mode. Its key, TTL and origin-protection plan are part of correctness.

Choose what may be stale

  • Include tenant, authorization dimension and schema version in keys. Never cache a security or monetary decision unless the product defines acceptable staleness.
  • Use cache-aside for simple reads, versioned keys for safe rollout and randomized TTLs to avoid synchronized expiry; cap negative-cache lifetime.

Protect the origin

  • Coalesce concurrent misses, refresh hot values ahead of expiry and bound rebuild concurrency. A cache outage must not instantly multiply origin load by the hit ratio.
  • Monitor hit ratio by key class, eviction, memory fragmentation, hot keys, fill latency and origin amplification—not only cache latency.

Compare tiers

  • L1 removes a network hop but multiplies stale copies; shared L2 centralizes data and invalidation but adds a network dependency and hotspot risk.
  • Choose LRU/LFU/TTL from access distribution and object value. If eviction loses authoritative state, the component is a database wearing a cache label.

Typeahead is a retrieval and ranking problem with a latency and quality budget. Define whether the product is suggesting queries, entities, products, or documents before choosing the index.

▸ DEEP DIVE · SENIOR
  • normalize Unicode, case, token boundaries, locale, transliteration, and safe query length before lookup. Prefix lookup cost includes top-K retrieval and ranking, not only prefix length.
  • use a versioned index pipeline: source change → normalized index event → build or update → validation → atomic alias/version switch. State freshness lag and rebuild behavior explicitly.
  • choose a p95/p99 target from measured input-to-render latency and dependency budgets rather than promising a universal 100 ms. Measure zero-result rate, CTR, MRR or conversion, latency, cache hit rate, and index lag.
  • fuzzy matching and typo tolerance need bounded expansion, a candidate cap, and a quality threshold. Personalized ranking is a separate candidate/reranking and privacy problem, not a free addition to the prefix trie.
  • debounce improves UI load but does not stop abuse. Add server-side rate, cost, cache, and concurrency controls, and avoid logging sensitive typed text without a retention policy.

Case metadata:

  • Workload: query rate by locale, prefix/fuzzy mix, catalogue size and personalization skew
  • Freshness: index freshness and ranking freshness are measured separately from API latency
  • Duplicate tolerance: query replay is harmless, while index events need stable IDs
  • Recovery owner: relevance/index owner and abuse-control owner

Security: Normalize by locale without collapsing tenant boundaries or logging raw sensitive queries. Rate-limit expensive fuzzy/personalized paths and define abuse/cost budgets.

Testing: Test Unicode normalization, locale changes, typo quality, stale/deleted catalogue entries, adversarial prefixes, index rebuild and p95/p99 latency; report relevance metrics separately from freshness.
