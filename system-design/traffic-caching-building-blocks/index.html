Traffic distribution and a defensible caching topology

Scope and problem framing

Design the read path for a horizontally scaled service. Decide which responses may be cached, where each copy lives, how it expires or is invalidated, and what happens when cache or origin is slow or unavailable.

Requirements

Functional requirements

  • Route traffic across healthy instances while preserving required affinity only where justified.
  • Serve safe static or public content at the edge and hot application data from bounded caches.
  • Propagate invalidation or version keys when several pods keep local copies.
  • Answer every cached response with enough metadata — version, age, source layer — that a stale answer can be traced to the layer that produced it.

Quality attributes

  • Define acceptable staleness per field or journey, not one TTL for the service.
  • Prevent stampede with request coalescing, jitter, stale-while-revalidate or prewarming.
  • Bound cache memory, key cardinality and fallback load on the source of truth.
  • Every layer must be removable. If turning off L1 or the CDN takes the service down, that layer is load-bearing infrastructure and has stopped being a cache.

Capacity and constraints

  • Size each layer by the traffic it sees, not by the traffic the product does: at ~250 rps peak (1M req/day) at T3, a 90% CDN hit ratio leaves 25 rps for the application and a further 90% L2 hit leaves 2.5 rps for the database. Each layer's miss rate is the next layer's peak, and that chain is the whole design.
  • A hit ratio is a capacity multiplier, and the leverage is at the top: moving CDN hit ratio from 90% to 95% halves origin traffic, while the same five points at L2 barely register because the traffic reaching it is already small.
  • Judge each layer per tier rather than adopting the stack wholesale:
    • a CDN is worth it from T1 for static assets and mandatory at T3 for any public payload
    • L1 in-process cache is worth it at T2 and mandatory at T4 for the hottest keys, where one key can exceed a single L2 node
    • L2 shared cache is not needed at T1, worth it at T2 to protect connection counts, mandatory at T3, and needs its own scaling story at T4.
  • Model the cold deploy, not only the steady state:a rolling restart empties every L1 at once, so the origin briefly takes the full uncached rate. If a T3 origin cannot serve 250 rps unaided, the cache is load-bearing and a deploy is an outage waiting for a busy afternoon.
  • Budget key cardinality as carefully as memory. A cache key that includes a user id turns a shared cache into a per-user one, and the hit ratio collapses to roughly the rate at which one user repeats a request.
  • Track hot-key share, object size, eviction rate and origin headroom, and treat the ratio of the hottest key to the median as a first-class number — a single key at 20% of traffic cannot be spread by adding nodes.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Cache key

namespace, schema version, tenant and authorization dimensions and a stable identifier. The schema version in the key is what makes a deploy that changes the payload shape safe without a flush.

02Cache value

compact payload, creation and version metadata and a bounded lifetime. Store the version beside the value or a reader cannot tell a fresh copy from an old one it just received.

03Invalidation event

entity id, new version, affected cache names and a deduplication id, so that a fan-out to N pods is idempotent and a replayed event is a no-op.

04Layer attribution

which layer served the response and how old it was, carried in a response header in non-production and in metrics everywhere. Without it, a staleness complaint has three suspects and no evidence.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01Edge

CDN for public and static objects with explicit cache-control and a purge strategy. A versioned URL is better than a purge, because a purge has to reach every edge and a new URL does not.

02L1

a bounded in-process cache — Caffeine or equivalent — for the hottest keys that tolerate staleness. Size it in entries with a weigher, never by trusting the objects to be small.

03L2

a Redis-compatible shared cache; the relational or document database remains the source of truth and must be able to state its own unaided capacity.

04Invalidation by version key rather than by delete wherever the write path can afford it

a new key is a write that cannot race a concurrent reader repopulating the old one.

05Request coalescing at whichever layer sits…

Request coalescing at whichever layer sits directly in front of the origin, plus TTL jitter, so a batch of keys written together does not expire together.

06Observability

hit ratio per layer, origin requests per second against origin headroom, eviction reason, staleness age at the p99, and the share of responses served by each layer.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

The version lives in the key

Abridged. A delete has to reach every layer and can be raced by a reader repopulating the old key; a new key cannot be raced at all, and the old one simply expires.

java
String cacheKey(String entity, long id, long version, String schemaVersion) {
    // schema version: a deploy that changes the payload shape is safe with no flush
    // entity version: an update writes a NEW key, so no reader can repopulate the old one
    return "%s:%s:%d:v%d".formatted(schemaVersion, entity, id, version);
}

Product read(long id) {
    long version = versions.current(id);          // cheap, authoritative, uncached
    return l2.get(cacheKey("product", id, version, SCHEMA), () -> db.load(id));
}

// an update bumps the version; nothing is deleted, and the old key ages out
void update(long id, ProductPatch patch) {
    db.apply(id, patch);
    versions.bump(id);
}

The miss chain, in one calculation

This is the arithmetic that decides whether the origin can survive a cold deploy. Each layer's miss rate is the next layer's peak.

bash
# T3 product traffic: 1M req/day -> ~250 rps peak (20x the 11.6 rps average)
#
#   client  --> 250 rps
#   CDN     --> 90% hit  ->  25 rps reach the application
#   L1      --> 60% hit  ->  10 rps reach the shared cache
#   L2      --> 90% hit  ->   1 rps reaches the database
#
# steady state: the database sees 1 rps and is bored.
#
# now the cold deploy: every L1 is empty and the CDN is unaffected.
#   CDN     --> 90% hit  ->  25 rps reach the application
#   L1      -->  0% hit  ->  25 rps reach the shared cache
#   L2      --> 90% hit  ->   2.5 rps reaches the database    <- survivable
#
# and the L2 outage, which is the case people do not plan for:
#   L1      -->  0% hit  ->  25 rps reach the database directly
# 25x the steady-state load. If the database cannot serve that, L2 is not a cache.

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
L1 removes a network hop and…

L1 removes a network hop and lets N pods hold N different stale versions. That is acceptable for a product listing and unacceptable for a permission check, so the layer is chosen per field rather than per service.

02
L2 centralizes invalidation and becomes a…

L2 centralizes invalidation and becomes a network dependency plus an overload amplifier on failure. It is the layer most likely to be treated as a cache while being operated as a database.

03
Cache-aside is simple and permits stale…

Cache-aside is simple and permits stale repopulation around a concurrent write; a versioned key removes the race and grows the key space. Pick the race away rather than trying to time it.

04
A long TTL raises hit ratio…

A long TTL raises hit ratio and widens the window in which an invalidation has not taken effect. TTL is the staleness contract with the reader, so it belongs in the design document rather than in a configuration file nobody reads.

05
Never cache balances, authorization decisions or…

Never cache balances, authorization decisions or checkout prices unless the business invariant explicitly tolerates the copy. The cost of a stale price is a refund; the cost of a stale permission is an incident.

06
Adding a layer always improves the…

Adding a layer always improves the steady state and always worsens the cold start and the debugging story. Three layers is a lot of places for one wrong answer to have come from.

Failure review — answers for this design
01

Which invariant can break?

A response must never be older than the staleness contract for the field it carries, and an authorization decision must never come from a cache that was populated before the permission changed. The first is a tuning failure; the second is why some fields must never enter a cache at all.

02

Which metric detects it first?

Hit ratio per layer, read alongside origin requests per second. A cardinality mistake — a user id accidentally in the key — shows as the hit ratio for one namespace collapsing while total traffic is unchanged, which is invisible in an aggregate hit-ratio dashboard.

03

How is the blast radius contained?

Each layer has a stated unaided capacity below it, so losing one layer degrades rather than cascades. Request coalescing and TTL jitter stop a single expiry from becoming a stampede, and no layer holds a field whose staleness the business has not accepted.

04

Can retry duplicate or reorder work?

Reordering is the hazard: a reader that missed before an invalidation can write the pre-invalidation value back afterwards, which is precisely what versioned keys prevent. Invalidation fan-out is at-least-once, so the deduplication id is what keeps a replayed event a no-op.

05

How do we repair and prove recovery?

Bump the schema or entity version rather than flushing, so readers move to fresh keys without the origin taking a cold-start spike. Recovery is proven when each layer's hit ratio returns to its own baseline, origin rate is back under headroom, and a sampled set of keys matches the source of truth.

Engineering deep dives

Caching as a bounded copy

A cache is a disposable, stale copy with a failure mode. Its key, TTL and origin-protection plan are part of correctness.

Choose what may be stale

  • Include tenant, authorization dimension and schema version in keys. Never cache a security or monetary decision unless the product defines acceptable staleness.
  • Use cache-aside for simple reads, versioned keys for safe rollout and randomized TTLs to avoid synchronized expiry; cap negative-cache lifetime.

Protect the origin

  • Coalesce concurrent misses, refresh hot values ahead of expiry and bound rebuild concurrency. A cache outage must not instantly multiply origin load by the hit ratio.
  • Monitor hit ratio by key class, eviction, memory fragmentation, hot keys, fill latency and origin amplification—not only cache latency.

Compare tiers

  • L1 removes a network hop but multiplies stale copies; shared L2 centralizes data and invalidation but adds a network dependency and hotspot risk.
  • Choose LRU/LFU/TTL from access distribution and object value. If eviction loses authoritative state, the component is a database wearing a cache label.

Reliability, overload and recovery

Reliability is a user-visible contract. Capacity, retries and failover must be designed as bounded control loops rather than emergency switches.

Prevent positive feedback

  • Give every call an end-to-end deadline; derive shorter per-hop timeouts from the remaining budget and cancel work the caller no longer needs.
  • Retry only classified transient failures, cap attempts, add exponential backoff with jitter and enforce a retry budget so recovery traffic cannot become the outage.

Degrade deliberately

  • Use admission control, bounded queues, concurrency limits and load shedding before saturation; queue depth without oldest-age is not enough to see stalled work.
  • Define which features fail closed, fail open, serve stale data or become read-only. Test the degraded contract with dependency latency, partial-region loss and bad configuration.

Prove recovery

  • Set RTO and RPO per journey, automate restore/failover where safe, and regularly restore production-shaped backups into an isolated environment.
  • Roll out by canary or cell, compare user SLIs, and keep rollback independent of the failing control plane. A failover plan that has never been exercised is an assumption.

For a read-heavy service, which caching pattern and invalidation contract would you choose, and how would you prevent stale decisions and cache stampedes?10-system-design-rate-limit.framework-building-blocks.q3

A cache is a bounded, disposable copy; choose it only after defining what may be stale and which decision must read the source of truth.

  • Cache-aside (lazy): the application reads the cache; on a miss it reads the database and populates the cache. It is the common default for derived reads.
  • Write-through: update the cache and database in the write path. It can reduce stale reads, but the two stores do not share one transaction; define retry and recovery when either write fails.
  • Write-behind: accept a cache write first and persist later. It improves write latency only when loss, replay, and ordering are explicitly acceptable.

Invalidation contract: commit the source-of-truth change first, record an outbox or invalidation event atomically with that change, and let consumers delete or version cache entries. TTL limits the damage from a missed event; it is not proof of freshness.

Stampede/thundering herd: when a hot key expires, many requests can rebuild it at once. Add TTL jitter, request coalescing (single-flight), refresh-ahead, and a bounded rebuild budget.

The race, drawn out. It is two threads and four steps, and every cache-aside deployment has it:

time    reader (cache miss)              writer (committed change)
----    ---------------------            ------------------------
t0      GET price:42        -> miss
t1      SELECT ... id=42    -> 100        // reads the OLD row
t2                                        UPDATE price=120; COMMIT
t3                                        DEL price:42        // deletes nothing
t4      SET price:42 = 100                // writes the OLD value back
//
// the cache now holds 100 for a full TTL, and both sides did exactly
// what they were told to. No retry and no ordering fixes this, because
// the reader's SELECT legitimately happened before the write.

A versioned key removes the race instead of narrowing it. The reader can no longer write into the key the next reader will look at:

// the version is authoritative, tiny, and cheap to read
long v = versions.get("price", id);          // 42 -> 7
Price p = cache.get("price:" + id + ":v" + v,   // price:42:v7
                     () -> db.load(id));
//
// the write bumps the version inside the same transaction as the row,
// so readers move to price:42:v8 the moment the change is visible.
// The stale v7 entry is unreachable and simply ages out.

Delayed double-delete — delete, wait, delete again — only shrinks the window. It is a mitigation with a tunable failure rate, and it should be described that way rather than as a fix.

Bound the rebuild, not just the expiry. Single-flight collapses concurrent misses for one key; a cold cache is many keys missing at once, which is a different failure:

ControlWhat it protects againstWhat it does not
TTL jitterkeys loaded together expiring togethera hot key that legitimately expires alone
Single-flightN concurrent misses on one key becoming N origin readsN different keys missing at once
Refresh-aheadthe expiry cliff on a key that is always hotkeys whose next read is unpredictable
Rebuild budgeta cold start or failover flooding the originnothing — this is the backstop the other three assume exists

The rebuild budget is a semaphore around the origin call, sized from what the database can serve unaided. If it is full, serve stale or fail fast — that decision is the contract, and it belongs in the design rather than in whatever the code happens to do.

Fintech:

For a monetary or authorization decision, read a strongly consistent ledger or policy source. A cache may support display data only when the product explicitly accepts its staleness.

▸ DEEP DIVE · SENIOR
  • cache-aside plus invalidation after a committed write is a useful default for derived reads, not a cross-store transaction. Include tenant, authorization dimension, and schema version in the key where they affect the result.
  • a read-miss fill can race a committed write. Use a versioned value or a post-commit invalidation path and retain a short TTL as recovery. Delayed double-delete is only a best-effort mitigation, never a correctness guarantee.
  • a hot key needs deliberate routing: coalesce rebuilds, use a small local cache for the hot subset, or replicate only when writes and invalidation reach every replica. Randomly reading key#1..N without that contract lowers the hit rate instead of adding capacity.

OTA: cache browsing results for seconds. When a supplier provides a feed, webhook, or poll result, normalize it through an invalidation pipeline; before a hold or charge, revalidate price and availability with the authoritative inventory or supplier boundary.

Recommendation boundary:

  • Cache-aside, versioned keys, TTL jitter, single-flight, and delayed double-delete are recommendations for derived reads, not correctness guarantees.
  • Before a correctness-critical mutation, revalidate price, inventory, policy, ledger, or authorization against its authority; make invalidation loss observable and repairable.
When should traffic be routed at L4 versus L7, and how do protocol behavior, connection reuse, health checks, and session or cache locality affect that choice?10-system-design-rate-limit.framework-building-blocks.q4
L4L7
Layertransport connection (IP/port)application protocol, commonly HTTP
Routing signaladdress and connection statepath, host, header, cookie, or RPC metadata
Useful controlslow-overhead connection distributionTLS termination, request routing, canary, WAF, and request-aware health checks

Choose the layer from the routing and operational decision you need, not from a belief that one layer always scales better. Round-robin, least-connections, weighted routing, and consistent hashing are policies with different fairness, locality, and failure behavior.

Drain connections and use health checks that represent the work the backend can actually serve.

Bottom line:

Stateless request handling makes horizontal scaling easier, but state still exists in databases, caches, queues, connections, and long-lived streams. Name where it lives and how it recovers.

▸ DEEP DIVE · SENIOR
  • L4 balances connections. L7 can inspect and route individual HTTP requests or RPC metadata. Neither removes the need for capacity, connection draining, and backpressure.
  • gRPC/HTTP2 multiplexes many RPCs over one connection.
  • an L4 proxy normally selects a backend per connection, so one busy client connection can be concentrated.
  • the answer is topology-dependent: use an HTTP/2-aware L7 proxy, or gRPC client-side balancing with enough backend connections; do not claim L7 is the only solution.
  • use consistent hashing only when locality is worth its skew and failure consequences. Sticky sessions are a compatibility choice, not a substitute for moving durable session state out of one instance.

OTA: an L7 gateway can centralize authentication and coarse rate limits, while internal gRPC clients still need deadlines, connection management, and service-level authorization.

Which responses may a CDN safely serve for this workload, how should cache keys, TTLs, and purge behavior be defined, and where must the origin remain authoritative?10-system-design-rate-limit.framework-building-blocks.q5

A CDN places content (static & cacheable) close to the user (edge) → reduces latency & load on the origin.

  • controlled via Cache-Control/TTL, cache key, invalidation/purge
  • edge compute for lightweight logic
  • not a fit for personalized/frequently-changing data unless configured carefully
▸ DEEP DIVE · SENIOR
  • CDN caches static & cacheable content at the edge near the user (PoP) → reduces latency + origin load + absorbs large spikes/DDoS at the static layer
  • Cache-Control/TTL, cache key (including select query params/headers), purge on change, edge compute (Workers/Lambda@Edge)

OTA: CDN for assets (destination images, JS/CSS), can cache popular search results (hot routes) with a short TTL at the edge; but personalized price/seat & checkout are not cached at the CDN. Consider stale-while-revalidate for fast UX.

  • Three things determine edge hit ratio, ranked by how often they're gotten wrong: cache key (one extra utm_* param or an Accept-Language header fragments the cache — normalize the query string before computing the key), TTL, then Vary.
  • Two directives worth remembering: stale-while-revalidate (serve the old version immediately while refreshing in the background — fast UX) and stale-if-error (if the origin is down, there's still a page to serve).
For a service running on ten pods, when do you use an L1 local cache, a shared L2 cache, or both—and how will you bound stale reads, invalidation loss, deploy compatibility, and origin fallback?10-system-design-rate-limit.framework-building-blocks.q6

Choosing where the cache lives is a consistency decision disguised as a performance one.

Local (Caffeine)Distributed (Redis)Multi-level
Read latencynanoseconds, in-heapa network round triplocal hit, else Redis
ConsistencyN pods, N versionsone shared versionbounded by the local TTL
Invalidationhard — must reach every podone deletedelete plus a broadcast
Capacitybounded by heap, duplicatedone dataset, sized independentlyhot subset local
If it diesnothing — the pod restarts colda dependency outage for everyonedegrades to the level below

The local-cache trade you are actually making: with a 60-second TTL and ten pods, a value updated now can be served stale by nine of them for up to a minute. That is fine for reference data and unacceptable for a balance or a permission (→ For a read-heavy service, which caching pattern and…).

To keep local caches honest you need a fan-out: publish an invalidation on a Redis pub/sub channel that every pod subscribes to, or make the key carry a version so a new value simply lands under a new key.

// multi-level: local absorbs the hot keys, Redis holds the truth
Fare quote(String route) {
    return local.get(route, k ->                    // L1: short TTL, per pod
           redis.get("fares:v3:" + k, () ->            // L2: shared, longer TTL
           db.load(k)));                                // source of truth
}
A rolling deploy makes both versions share one cache:

While the rollout runs, old and new code read the same Redis. Change the shape of a cached value without bumping the key prefix and the new pods fail deserializing old entries — on every request that hits a warm key.

▸ DEEP DIVE · SENIOR
  • treat the cache as a dependency that can fail and decide fail-open or fail-closed per use. Falling through to the database is right for a product page and wrong for a rate limiter that would then stop limiting (→ How would you implement a Redis-backed shared rate limiter…).
  • a cold restart after an eviction is a stampede against the database. Warm critical keys on startup, or coalesce misses so one loader wins (25-microservice.05-caching-pitfalls.q1).
  • keep values small and boring: Redis executes commands on a single thread, so one huge value or one KEYS scan adds latency to every other client (07-sql-nosql-db-engines.engine-by-engine.q6).
  • hot keys defeat a distributed cache the same way they defeat a shard; a small local cache in front of exactly those keys is the standard answer (25-microservice.05-caching-pitfalls.q2).
  • the annotation-level version of these decisions — TTL placement, key design, eviction on rollback — lives in (03-spring-boot-deep-build.ioc-container-transactions.q6).
