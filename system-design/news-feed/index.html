News feed with hybrid fan-out

Scope and problem framing

Publish posts and return a paginated home timeline from followed creators. The design must handle celebrity fan-out, privacy and deletion changes, ranking evolution and a feed that can degrade gracefully.

Requirements

Functional requirements

  • Create a post and either push it into follower timelines or leave it to be pulled at read time, according to the author's fan-out class.
  • Return a stable, cursor-paginated home timeline:merge materialized entries with pulled entries from high-fanout accounts, hydrate and rank.
  • Apply follow, unfollow, block, privacy change and deletion so that the change is visible on the next read even when timelines were written earlier.
  • Degrade to a deterministic chronological feed when ranking is unavailable, without changing the pagination contract.

Quality attributes

  • Posting must not wait for fan-out. The author sees their own post immediately; followers see it within a fan-out budget measured in seconds, not in the time it takes to write every timeline.
  • Read latency must be bounded regardless of how many high-fanout accounts a user follows, which is what caps the number of accounts that may be merge-on-read.
  • A materialized timeline entry is a candidate, never an authorization. Visibility is decided on read, so a block or a privacy change takes effect without rewriting history.
  • Ranking quality is allowed to degrade; feed availability is not. The fallback must be a real, tested path rather than an error page.

Capacity and constraints

  • Size the read path by timeline peak with the daily volume beside it: ~25 rps peak (100k feed opens/day) at T2, ~250 rps peak (1M/day) at T3, ~25,000 rps peak (100M/day) at T4. Feed traffic is consumer traffic with sharp morning and evening peaks, so plan 10–20× the average.
  • Write amplification, not post rate, is what sizes fan-out on write. At an average of 200 followers, 1M posts/day is 200M timeline writes/day — the fan-out pipeline is two orders of magnitude larger than the posting API and must be sized as its own system.
  • The distribution is what breaks the model, not the mean. One account with 10M followers produces as many timeline writes in a single post as 50,000 ordinary posts, which is the entire reason the hybrid exists.
  • Judge hybrid fan-out per tier:not needed at T1 and T2, where merge-on-read across everyone a user follows is cheap and one less pipeline to run; worth it at T3, where ordinary-author fan-out starts to dominate read cost; mandatory once a single account's follower count reaches six figures; needs its own scaling story at T4, where fan-out workers, timeline storage and the celebrity merge each scale on different signals.
  • Bound the materialized timeline rather than storing history:keeping the newest 500–1,000 candidates per user makes storage a function of user count instead of post count, and anything older is served by a query against the author's own posts.
  • Budget hydration separately from timeline reads. One feed page of 20 entries is 20 post fetches plus author and counter lookups, so the hydration cache — not the timeline store — is usually the first thing to saturate.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Post

post id ordered by time, author, content reference, visibility, created time, status and version. Time-ordered ids let a timeline hold references and still sort without hydrating.

02Follow edge

follower and followee, state, privacy decision and effective time, indexed both ways: by follower for the read path and by followee for fan-out.

03Timeline entry

user id as the partition key with post id descending as the clustering key, plus the candidate source (pushed or pulled) and the ranking feature version. Bounded per user, so the partition never grows without limit.

04Author fan-out class

the follower count bucket and the current strategy for that author, stored rather than computed, so a post and its later reads agree about how it was distributed.

05Ranking feature snapshot

the features and model version used for a rendered page, kept only long enough to explain and debug a feed, never as a permanent per-impression record.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01Hybrid fan-out is the core decision

push into follower timelines for ordinary authors, and leave high-fanout authors to be merged at read time. The threshold is a tuned number, not a constant, and it should be expressed in follower count because that is what drives the cost.

02Durable post store plus a follow/graph…

Durable post store plus a follow/graph index; a Kafka-compatible log carries fan-out work so that a slow timeline store applies backpressure to the pipeline rather than to the posting API.

03Wide-column or Redis-backed timeline store holding…

Wide-column or Redis-backed timeline store holding a bounded candidate list per user. The access pattern is a single partition read with a descending clustering key, which is exactly what these stores are good at.

04Stateless hydration and ranking services with…

Stateless hydration and ranking services with their own feature cache and a chronological fallback that is exercised in production, not only in a runbook.

05Final authorization on read against the follow, block and visibility state. This is what lets fan-out be eventually consistent

a stale candidate is filtered rather than leaked.

06Observability

fan-out lag by author class, timeline write amplification, merge cost for high-fanout reads, hydration cache hit ratio, and the share of pages served by the ranking fallback.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

Bounded timeline partition

Cassandra-style DDL. The clustering order is what makes a feed page a single sequential read, and the bound is enforced on write rather than by a background delete.

sql
CREATE TABLE timeline (
  user_id      bigint,
  post_id      bigint,        -- time-ordered, so DESC is chronological
  author_id    bigint,
  source       text,          -- 'push' or 'pull'
  feature_ver  int,
  PRIMARY KEY ((user_id), post_id)
) WITH CLUSTERING ORDER BY (post_id DESC);

-- one page is one partition read, no merge and no sort
SELECT post_id, author_id, source
FROM timeline
WHERE user_id = :user_id AND post_id < :cursor
LIMIT 20;

The hybrid read

Abridged. Two things carry the design: the celebrity set is bounded before the merge, and visibility is applied after it — never before.

java
List<Entry> homeTimeline(long userId, long cursor, int limit) {
    // pushed candidates: one partition read
    List<Entry> pushed = timeline.page(userId, cursor, limit * 2);

    // pulled candidates: only the accounts too large to fan out, and the set is
    // capped so a user who follows 400 celebrities cannot uncap the read.
    List<Long> celebrities = follows.highFanout(userId, MAX_MERGE_SOURCES);
    List<Entry> pulled = posts.recentByAuthors(celebrities, cursor, limit * 2);

    List<Entry> merged = mergeByPostIdDesc(pushed, pulled);

    // authorization happens here, on the merged candidates, because a stored
    // timeline entry predates the block or privacy change that may have followed it
    List<Entry> visible = visibility.filter(userId, merged);

    return ranker.rankOrFallback(userId, visible, limit);
}

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
Fan-out on write buys cheap reads…

Fan-out on write buys cheap reads with expensive, bursty writes; fan-out on read buys cheap writes with a merge on every request. Neither survives the follower distribution alone, which is why production feeds are hybrid and why the threshold is the thing to tune.

02
Bounding the timeline makes storage predictable…

Bounding the timeline makes storage predictable and makes deep pagination a different query. Decide early whether "load older" reads the timeline or falls back to the author's posts, because retrofitting the second path changes the cursor contract.

03
Materialized candidates are stale by construction.…

Materialized candidates are stale by construction. Filtering on read costs a lookup per entry and is the only thing standing between a privacy change and a leak, so it cannot be cached as aggressively as the timeline itself.

04
Ranking makes the feed better and…

Ranking makes the feed better and makes it non-deterministic, which makes bugs hard to reproduce and pagination hard to keep stable. Pinning the ranking version into the cursor is the usual price of a stable page.

05
Deleting a post cannot mean rewriting…

Deleting a post cannot mean rewriting every timeline that referenced it. Tombstone the post and filter on hydration, and accept that the entry is still occupying a slot in a stored timeline.

06
A celebrity threshold that is too…

A celebrity threshold that is too low turns ordinary authors into merge cost on every read; too high and one post stalls the fan-out pipeline for everyone. This is a live operational knob, not a design-time constant.

Failure review — answers for this design
01

Which invariant can break?

A reader must never see a post they are not entitled to see, and a page must not shift under them while they paginate. The first is protected by filtering on read rather than trusting the stored candidate; the second by pinning the ranking version and the cursor together.

02

Which metric detects it first?

Fan-out lag split by author class, and the age of the newest entry in a sampled set of timelines. Aggregate queue depth hides the failure that matters, because one celebrity post can be tens of millions of writes while the queue count barely moves.

03

How is the blast radius contained?

High-fanout authors are already off the write path, so their posts cannot stall ordinary fan-out. The merge source count is capped per read, the timeline is bounded per user, and ranking sits behind a fallback — so a ranking outage costs feed quality and a hydration outage costs a partial page.

04

Can retry duplicate or reorder work?

Yes.

  • Fan-out is at-least-once, so the same post can be written into a timeline twice; the primary key on (user_id, post_id) makes that write idempotent.
  • Reordering is harmless because the timeline is sorted by post id, not by arrival.
05

How do we repair and prove recovery?

Backfill from the post store for the affected follower ranges — the timeline is a derived cache and can always be rebuilt. Recovery is proven when fan-out lag returns to budget for every author class, a sampled set of timelines matches a recomputed one, and no page in the sample shows a post that the visibility check rejects.

Engineering deep dives

Asynchronous delivery and replay

Moving work off the request path trades immediate failure for lag, duplicates, ordering constraints and operational backlog.

Define delivery semantics

  • Assume at-least-once at service boundaries. Give each event a stable ID, partition key, schema version and event time; make every side effect idempotent.
  • Guarantee order only within the business entity that needs it. Global order limits parallelism and usually encodes no useful invariant.

Treat lag as user impact

  • Observe oldest-message age, input/output rate, retry count, poison messages and partition skew. Queue depth alone hides slow old work behind new small messages.
  • Use retry topics or delayed queues with expiry and a DLQ; DLQ is not resolution until it has ownership, alerting and a safe replay tool.

Evolve safely

  • Use backward/forward-compatible schemas and tolerant readers. Deploy consumers before producers when adding fields and preserve raw events for bounded replay.
  • Replay into an isolated output or shadow consumer first; throttle it so historical traffic cannot starve live processing or repeat external effects.

Indexes, ranking and freshness

Fast ranking comes from a bounded candidate set and a versioned derived index, not from querying the source of truth on every keystroke or feed read.

Separate retrieval from ranking

  • Retrieve a bounded candidate set using prefix, graph, time or score indexes; rank it with a versioned rule/model and keep a deterministic fallback.
  • Store the ranking/model version and stable tie-break key so pagination, audits and experiments can reproduce an ordering.

Control index freshness

  • Measure event-to-searchable lag by percentile and entity class. Rebuild into a new version, validate counts/checksums, then atomically switch readers.
  • Re-check authorization, deletion and hard availability constraints at read time; an eventually consistent candidate index must not bypass current policy.

Bound cost and abuse

  • Debounce typeahead, cap prefix/fuzzy expansion and cache popular anonymous prefixes. Personalization reduces cacheability and increases privacy review.
  • Track empty-result rate, candidate count, ranking latency, index size, stale-result complaints and quality metrics separately from availability.

  • fan-out on write improves common reads, but the read is still O(page size) plus ranking and possible candidate merging. A single sorted set cannot be both a chronological source and an unconstrained ML ranking system without defining score and refresh semantics.
  • use keyset cursors such as rank-or-time plus post ID, and carry a ranking or feed-generation version so pagination remains explainable as scores change.
