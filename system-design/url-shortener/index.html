URL shortener with a fast redirect path

Create a short code for a validated long URL and redirect it with low latency at a read-heavy scale. Support optional custom aliases and expiry without putting analytics or preview generation on the critical path.

Scope and problem framing

Create a short code for a validated long URL and redirect it with low latency at a read-heavy scale. Support optional custom aliases and expiry without putting analytics or preview generation on the critical path.

Requirements

Functional requirements

  • Create a short code for a destination URL, optionally with a caller-supplied custom alias, an owner and an expiry.
  • Resolve a code to its destination on the hot path and redirect, applying expiry, revocation and safety state.
  • Let an owner list, edit the destination behind a code, and revoke without ever reissuing the code to someone else.
  • Record a click asynchronously so that analytics never sits between the request and the redirect.

Quality attributes

  • Redirect latency is the product:a resolve should be one cache hit, and the p99 should stay in the low tens of milliseconds at the edge.
  • A code, once issued, is permanent. Reusing an expired code for a different destination turns an old link into an open redirect.
  • The redirect path must survive the analytics pipeline being down; a click that cannot be recorded is still a click that must be served.
  • Creation is allowed to be slower and stricter than resolution — it is where uniqueness, abuse scanning and quota live.

Capacity and constraints

  • Size the service by redirect peak with the daily volume beside it: ~2.5 rps peak (10k redirects/day) at T1, ~250 rps peak (1M/day) at T3, ~25,000 rps peak (100M/day) at T4. Link traffic is consumer traffic and concentrates 10–20× around a campaign send, so plan the peak from the campaign, not from the daily average.
  • Creates and redirects are not the same workload and must be sized apart. A read:write ratio of 100:1 or higher is normal, which is why the write path can stay a single relational primary long after reads have moved to a cache tier.
  • Judge the edge cache per tier:not needed at T1, where a single instance with an in-process map absorbs everything; worth it at T2, where it mostly saves database connections; mandatory at T3, because 250 rps of point lookups against a primary is a self-inflicted bottleneck; needs its own scaling story at T4, where the cache is a fleet with its own placement, warmup and eviction behaviour.
  • Storage is small and predictable:at 100 bytes of row per link, 100M links is about 10 GB before indexes — the corpus fits one node long after the traffic does not, which is why sharding a shortener is usually premature.
  • Redirect traffic is Zipf-like, so cache sizing is driven by the head, not the corpus. Measure the share of redirects served by the top 1% of codes before choosing a cache size; a few hundred megabytes commonly covers well over 90% of hits.
  • Budget the analytics stream separately from the redirect:one click event per redirect at T4 is 100M events/day, which is a bigger pipeline than the redirect service itself and must be allowed to lag or drop.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Link

short code as the primary key, destination URL, owner, created and expiry time, status (active/revoked/blocked) and a destination version so that an edit is auditable.

02Alias reservation

the normalized custom code under a unique constraint, with owner and lifecycle state. The uniqueness must be the database's, not the application's: two concurrent creates otherwise both pass a read-then-write check.

03Click event

code, coarse timestamp, referrer class, device class and country. Deliberately no raw IP and no user id: the analytics value is in the aggregate, and storing the identifier makes the table a liability.

04Safety verdict

code, scanner verdict, verdict time and source, kept beside the link rather than inside it so that a rescan never rewrites the row the redirect path reads.

05Counter allocation

when codes come from a counter, the block of ids an instance has claimed, so that a restart cannot replay a range that was already issued.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01Code generation is the first real…

Code generation is the first real decision.

  • A base62 encoding of a monotonic counter is collision-free by construction and needs no retry loop, but it leaks volume and makes codes enumerable; random codes need a uniqueness check on insert but reveal nothing.
  • Pick per product, not per taste.

02Relational store for links and aliases

the unique constraint on the alias is the whole point, and a shortener's write volume almost never justifies giving that up for a store that cannot enforce it.

03Read-through cache in front of resolve,…

Read-through cache in front of resolve, keyed by code, holding the destination and the status together. Caching the destination without the status is how a revoked link keeps redirecting for the length of the TTL.

04Asynchronous click pipeline behind a bounded queue

the redirect handler enqueues and returns. If the queue is full the event is dropped, because the alternative is that the analytics backlog decides whether the product works.

05Safety scanning on create and on…

Safety scanning on create and on a schedule, never on the redirect path. A synchronous reputation lookup inside resolve makes an external vendor an availability dependency of every click.

06Observability

redirect p99 split by cache hit and miss, cache hit ratio, create failures by cause, click-queue depth and drop rate, and the age of the newest safety verdict.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

Claim a custom alias without a read-then-write race

The unique index is what makes this safe. A SELECT-then-INSERT passes for both callers under concurrency and the second write silently wins.

sql
CREATE TABLE link (
  code         TEXT PRIMARY KEY,
  destination  TEXT NOT NULL,
  owner_id     BIGINT NOT NULL,
  status       TEXT NOT NULL DEFAULT 'active',
  expires_at   TIMESTAMPTZ,
  version      INT  NOT NULL DEFAULT 1,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- the alias is claimed by the insert itself, never by a prior check
INSERT INTO link (code, destination, owner_id, expires_at)
VALUES (:code, :destination, :owner_id, :expires_at)
ON CONFLICT (code) DO NOTHING
RETURNING code;

-- zero rows back means the code is taken: answer 409, do not retry the same code

Resolve, then record out of band

Abridged. The ordering is the point: the response is produced before anything touches the analytics path, and the enqueue can fail without affecting it.

java
public ResponseEntity<Void> resolve(String code) {
    Link link = cache.get(code, this::loadFromDb);   // one hit on the hot path

    if (link == null || link.revoked() || link.expired(clock.instant())) {
        return ResponseEntity.status(HttpStatus.GONE).build();
    }

    // 302, not 301: a permanent redirect is cached by the browser and the ISP,
    // so we would never see the click again and could not revoke the link.
    ResponseEntity<Void> response = ResponseEntity.status(HttpStatus.FOUND)
            .location(URI.create(link.destination()))
            .cacheControl(CacheControl.noStore())
            .build();

    clicks.offer(new ClickEvent(code, clock.instant(), classify(request)));  // bounded, may drop
    return response;
}

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
301 versus 302 is the decision people forget

a 301 is cached by the browser and the ISP, so later clicks never reach you — cheaper, but you lose the analytics and you lose the ability to revoke.

  • A 302 keeps every click on your infrastructure and costs you the traffic.
  • Most link products want 302 and should say so out loud.
02
Counter-derived codes make ids sequential and therefore enumerable

a competitor can walk your entire corpus. Random codes stop that and cost a uniqueness check plus a rare retry on insert.

03
Fan-out on the analytics side can…

Fan-out on the analytics side can be dropped under load; the redirect cannot. Keeping the two in one request is the single easiest way to turn an analytics incident into a product outage.

04
A long cache TTL protects the…

A long cache TTL protects the database and delays revocation. Either keep the TTL short enough that revocation is honoured within your abuse SLA, or accept that revocation needs an explicit cache invalidation path.

05
Custom aliases are a product feature…

Custom aliases are a product feature and a squatting surface. Reserving them per owner with a lifecycle is the cheap answer; letting anyone claim any string is how a shortener ends up hosting someone else's brand.

06
Deleting a link is not the…

Deleting a link is not the same as revoking it. Deletion frees the code for reuse and reuse is what creates an open redirect, so the safe default is a tombstone that keeps the code taken forever.

Failure review — answers for this design
01

Which invariant can break?

A code must always point at the destination its owner last set, or at nothing. It breaks when a code is freed and reissued, and when a cache entry outlives a revocation — both turn a link someone already published into a redirect to a destination they never approved.

02

Which metric detects it first?

Redirect status mix, not latency.

  • A rise in redirects for codes whose links are revoked, or in 404 and 410 for codes that were recently active, shows up long before anyone complains.
  • Watch it beside cache hit ratio: a hit ratio that jumps after a revocation deploy means stale entries are being served.
03

How is the blast radius contained?

The redirect path depends on the cache and nothing else on a hit. Safety scanning, analytics and the create path are all off it, so a scanner outage, a full click queue or a write-path incident degrade features rather than redirects.

04

Can retry duplicate or reorder work?

On the read path there is nothing to duplicate.

  • On create, a retried request with the same idempotency key must return the original code rather than mint a second one, or one campaign ends up with two live codes and split analytics.
  • Click events are at-least-once by design and the aggregation must be idempotent per event id.
05

How do we repair and prove recovery?

Rebuild the cache from the link table — it is a pure read-through, so a flush is safe and costs a latency spike. Recovery is proven when redirect p99 returns to its cache-hit baseline, the revoked sample set answers 410 on every edge, and the click backlog drains without the aggregate row counts moving twice.

Engineering deep dives

Caching as a bounded copy

A cache is a disposable, stale copy with a failure mode. Its key, TTL and origin-protection plan are part of correctness.

Choose what may be stale

  • Include tenant, authorization dimension and schema version in keys. Never cache a security or monetary decision unless the product defines acceptable staleness.
  • Use cache-aside for simple reads, versioned keys for safe rollout and randomized TTLs to avoid synchronized expiry; cap negative-cache lifetime.

Protect the origin

  • Coalesce concurrent misses, refresh hot values ahead of expiry and bound rebuild concurrency. A cache outage must not instantly multiply origin load by the hit ratio.
  • Monitor hit ratio by key class, eviction, memory fragmentation, hot keys, fill latency and origin amplification—not only cache latency.

Compare tiers

  • L1 removes a network hop but multiplies stale copies; shared L2 centralizes data and invalidation but adds a network dependency and hotspot risk.
  • Choose LRU/LFU/TTL from access distribution and object value. If eviction loses authoritative state, the component is a database wearing a cache label.

Observability and security review

Instrumentation should explain user impact and the responsible dependency without leaking identity or creating unbounded telemetry cost.

Start from user SLIs

  • Define success, latency, freshness and correctness SLIs at the system boundary; alert on error-budget burn, then use dependency metrics for diagnosis.
  • Correlate traces, metrics and structured logs with trace/span IDs. Preserve request, policy and schema versions but redact secrets and sensitive payloads.

Keep telemetry bounded

  • Never use user ID, object ID or raw URL as a metric label. Use logs/traces for high-cardinality detail and explicitly monitor cardinality overflow.
  • Sample by value: retain errors, slow paths and rare business failures at higher rates while keeping predictable storage and query cost.

Review the trust boundary

  • Authorize the object and action on every request, use least-privilege service identities and short-lived credentials, encrypt in transit/at rest and audit privileged changes.
  • Threat-model abuse, replay, enumeration, tenant crossover and data retention. Security controls need degraded behavior and recovery drills like every other dependency.

Design a URL shortener with custom aliases and analytics. How do redirect semantics and cache policy support mutable versus permanent destinations, while privacy, abuse prevention, and click measurement remain explicit?11-system-design-cases.the-big-prompts.q3

Core mapping: a short code resolves to a destination URL plus ownership, status, expiry, abuse, and analytics metadata.

Creation must normalize the destination, enforce uniqueness, and use a collision-safe code generator; use cryptographically random codes when non-enumerability is a security requirement.

Read path: CDN or edge cache → redirect service → cache / key-value store → redirect response; emit redirect events asynchronously so analytics cannot slow the redirect.

▸ DEEP DIVE · SENIOR
  • redirect status is not an analytics strategy. Immutable mappings can use 301 or 308 with an explicit long cache policy. Mutable mappings normally use 302 or 307 with explicit no-store or bounded cache lifetime. A 302 can also be cached when headers allow it.
  • click counting is inherently approximate because browsers, proxies, bots, prefetchers, and cached redirects may bypass the origin. Record server or edge redirect events, filter abuse, and disclose the measurement definition.
  • a public shortener may intentionally redirect to arbitrary HTTP/S destinations. Validate and normalize scheme and URL, scan or block abusive destinations, rate-limit creation, and make allowlists a product policy rather than a universal rule.
  • custom aliases need ownership checks and reservation rules. Protect users with phishing and malware controls, report-and-takedown workflows, privacy-aware logging, and expiration or deletion policies.
  • size the code space from expected creations, retention, collision retry, and whether codes may be reused; do not infer capacity from a single fixed traffic number.

Case metadata:

  • Workload: create/redirect QPS, alias mutations, region and bot skew
  • Freshness: immutable redirects may be cached while mutable aliases need a stated revalidation bound
  • Duplicate tolerance: create request key and click-event deduplication policy
  • Recovery owner: redirect/abuse owner, with analytics treated as a projection

Provider and security boundary: Apply the chosen RFC 9110/9111 semantics and name the CDN/cache version and headers. 301/308 versus 302/307 is a permanence and method-preservation decision, not a universal CDN rule.

Do not fetch arbitrary destinations server-side unless the product has an isolated SSRF-safe scanner.

Security and tests: Test alias ownership, reserved-code collision, scheme validation, takedown propagation, cache invalidation, redirect method behavior, bot/pre-fetch measurement and privacy-safe logs. Rate-limit creation and scanning; never treat click analytics as proof that a human visited.
