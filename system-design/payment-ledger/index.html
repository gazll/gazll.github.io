Correct payment and money-transfer system

Accept a transfer or payment command exactly once from the customer's perspective, preserve accounting invariants across retries and external providers, expose a truthful state and recover discrepancies without deleting history.

Scope and problem framing

Accept a transfer or payment command exactly once from the customer's perspective, preserve accounting invariants across retries and external providers, expose a truthful state and recover discrepancies without deleting history.

Requirements

Functional requirements

  • Post a balanced double-entry transaction:every movement debits one account and credits another, and the two sides are written in one atomic unit or not at all.
  • Answer a balance for any account at any point in time, and answer it the same way twice.
  • Reverse a posting by writing a compensating entry, never by editing or deleting the original.
  • Reconcile against the external source of truth — the PSP, the bank statement, the card network file — and produce a break report rather than a silent adjustment.

Quality attributes

  • The ledger must balance at all times:the sum of every debit equals the sum of every credit, and that is an invariant a database constraint should enforce rather than a nightly job discover.
  • Entries are immutable. An auditable ledger is one where history cannot change, which is why correction is always a new entry and never an update.
  • Every write is idempotent under retry, because the caller is a network away and will retry. A duplicated posting in a ledger is not a glitch, it is money that does not exist.
  • Reads of a balance are allowed to be slightly behind; writes are not allowed to be wrong. This is the one design on the site where correctness outranks latency without argument.

Capacity and constraints

  • Size the posting path by peak transaction rate with the daily volume beside it: ~2.5 rps peak (10k postings/day) at T1, ~25 rps peak (100k/day) at T2, ~250 rps peak (1M/day) at T3. Payment traffic is consumer traffic and concentrates 10–20× around paydays, campaign windows and month end.
  • Ledgers are usually smaller than teams expect and are almost never write-bound before they are query-bound. A T3 ledger at 1M postings/day writes 2M entry rows/day, which one well-indexed relational primary handles comfortably; the pressure comes from balance queries, not from postings.
  • Judge a materialized balance per tier:not needed at T1 and T2, where summing an account's entries is a fast indexed aggregate; worth it at T3 for hot accounts, where the entry count per account grows without bound; mandatory once any single account accumulates millions of entries, because the aggregate stops being bounded; needs its own scaling story at T4, where the running balance becomes its own consistency problem with the entries it summarizes.
  • Model the account distribution, not the average. A merchant settlement account or a platform fee account receives a share of every transaction, so a handful of accounts hold most of the entries and are the only ones that need a snapshot.
  • Budget reconciliation as its own workload:it reads the entire day's entries plus the entire external file, on a schedule, and it must not compete with the posting path for the same primary.
  • Retention is not optional here. Financial records carry a legal retention period, so plan partitioning and archival from the first schema rather than discovering it when the table stops fitting.

Data model

Compare records by ownership and responsibility before choosing storage. A record is authoritative, operational or derived; mixing those roles creates unclear consistency boundaries.

Record / modelFields, ownership and responsibility

01Account

id, owner, type, currency and status. Currency belongs on the account, not on the entry, so that a transaction can never accidentally mix units within one account.

02Transaction

id, an idempotency key from the caller, a type, an external reference and the posting time. This is the unit that must balance and the unit a retry deduplicates against.

03Entry

transaction id, account, a signed amount in minor units, and the running sequence within the account. Immutable and append-only, with no update path at all.

04Balance snapshot

account, an entry sequence as of which the balance was computed, and the amount. A snapshot plus the entries after it is what keeps a balance query bounded.

05Reconciliation break

the external reference, what the ledger says, what the counterparty says and a resolution state. A break that has no row is a break nobody is working on.

Compare the models on
  • transaction boundary and invariant
  • read/write path and indexes
  • partition key and hot-key risk
  • retention, audit and privacy
  • whether it can be rebuilt after loss

Technology choices

Treat this as a decision map, not a shopping list. Each component must solve a named constraint and carry an explicit operational cost.

Layer / optionChoice, purpose and boundary

01A relational database with real constraints is the right choice and the constraint is the point

a CHECK that the transaction sums to zero, a unique index on the idempotency key, and a foreign key from entry to transaction do more for correctness than any amount of application code.

02Money is an integer in minor units

or an exact decimal — and never a float. This is not a style preference: binary floating point cannot represent 0.10, so a float ledger is wrong by construction and the error accumulates.

03Idempotency is a stored key with…

Idempotency is a stored key with the response, not a check-then-write. Storing the key in the same transaction as the postings is what makes a retry return the original result instead of racing it.

04Append-only entries with a per-account sequence,…

Append-only entries with a per-account sequence, so a balance is a snapshot plus a bounded scan and the ordering within an account is never ambiguous.

05Reconciliation as a scheduled job against…

Reconciliation as a scheduled job against a read replica, producing breaks into a queue that a human owns. An automatic adjustment that nobody sees is how a reconciliation process hides the bug it was built to find.

06Observability

postings per second and their latency, the balance-check invariant run continuously rather than nightly, idempotency-key hit rate, snapshot lag in entries, open break count by age, and the time from external file arrival to reconciliation complete.

Challenge every choice with
  • simplest viable alternative
  • consistency and latency impact
  • failure and degraded mode
  • team/on-call capability
  • migration and exit trigger

Code samples

Balanced double-entry posting

The journal is accepted only when debit and credit balance inside the same local transaction.

sql
BEGIN;

INSERT INTO journal_transaction (id, idempotency_key, currency)
VALUES (:journal_id, :key, :currency)
ON CONFLICT (idempotency_key) DO NOTHING;

INSERT INTO posting (journal_id, account_id, direction, amount)
VALUES
  (:journal_id, :debit_account, 'DEBIT', :amount),
  (:journal_id, :credit_account, 'CREDIT', :amount);

SELECT 1
FROM posting
WHERE journal_id = :journal_id
GROUP BY journal_id
HAVING SUM(CASE WHEN direction = 'DEBIT' THEN amount ELSE -amount END) = 0;
COMMIT;

Runpsql ledger.sql --set amount=1250 --set currency=VND

Idempotency that survives a retry storm

The key is stored in the same transaction as the postings. A check-then-write lets two concurrent retries both pass the check, and the ledger gains money that never existed.

sql
CREATE TABLE transaction (
  txn_id           uuid PRIMARY KEY,
  idempotency_key  text NOT NULL,
  external_ref     text,
  posted_at        timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT txn_idem UNIQUE (idempotency_key)
);

BEGIN;
  -- the insert IS the lock: a concurrent retry blocks here, then finds the row
  INSERT INTO transaction (txn_id, idempotency_key, external_ref)
  VALUES (:txn_id, :idem_key, :external_ref)
  ON CONFLICT (idempotency_key) DO NOTHING;

  -- zero rows means someone already posted this: return their result, post nothing
  -- otherwise write both legs here, inside the same transaction
COMMIT;

A bounded balance query

Without the snapshot this is a full scan of the account, which is fine until a settlement account holds ten million entries.

sql
-- snapshot + the entries written after it: a fixed cost regardless of account age
SELECT s.amount + COALESCE(SUM(e.amount), 0) AS balance
FROM balance_snapshot s
LEFT JOIN entry e
       ON e.account_id = s.account_id
      AND e.account_seq > s.account_seq
WHERE s.account_id = :account_id
GROUP BY s.amount;

-- the invariant, run continuously rather than nightly: this must always return 0
SELECT SUM(amount) FROM entry WHERE txn_id = :txn_id;

Trade-offs

Each row is a tension the design accepts—not a universal best practice. Review both sides and record the condition that would reverse the decision.

01
Deriving a balance from entries is…

Deriving a balance from entries is always correct and grows unbounded; snapshotting is bounded and introduces a second thing that can disagree with the first. Snapshot only the accounts that need it, and verify snapshots against a full recomputation on a schedule.

02
Strong consistency on the posting path…

Strong consistency on the posting path costs throughput and is the correct trade. A ledger that accepts eventual consistency for balances has to answer what happens when two withdrawals both read the stale balance, and the honest answer is usually that it must not.

03
Storing the authorization and the capture…

Storing the authorization and the capture as separate transactions is more rows and is what lets you answer "what was reserved versus what was taken". Collapsing them into one loses the distinction permanently.

04
A single global ledger is simplest…

A single global ledger is simplest and eventually becomes the write bottleneck; partitioning by account or by currency scales and makes a cross-partition transaction a distributed problem. Delay the split, and when it comes, split along a boundary transactions rarely cross.

05
Reversal entries keep history honest and…

Reversal entries keep history honest and mean the balance of an account is not the sum of what a user thinks happened. Reporting has to explain reversals rather than hide them, which is a product cost paid for an audit benefit.

06
Enforcing the balance invariant as a…

Enforcing the balance invariant as a database constraint costs write throughput on every posting. It is the cheapest correctness insurance in the design, and it is the first thing to be removed under load pressure by someone who does not know why it is there.

Failure review — answers for this design
01

Which invariant can break?

Debits must equal credits for every transaction, and a caller's retry must never produce a second posting.

  • The first is protected by a constraint that the transaction sums to zero
  • the second by storing the idempotency key inside the same transaction as the entries rather than checking for it first.
02

Which metric detects it first?

The balance invariant run continuously, plus snapshot lag measured in entries.

  • A nightly check finds the break the morning after the money moved, which is exactly one business day too late
  • running it per transaction makes the failure a rejected write instead of an incident.
03

How is the blast radius contained?

Entries are immutable and append-only, so no failure can rewrite history — the worst case is entries that should not exist, which are corrected by reversal and remain visible. Reconciliation runs against a replica, so it cannot slow the posting path while it investigates.

04

Can retry duplicate or reorder work?

Duplication is the central risk and is answered by the stored idempotency key. Reordering is harmless within an account because the per-account sequence is assigned at write time, but it does mean a balance read between two legs of a transfer must never be possible — which is why both legs are one database transaction.

05

How do we repair and prove recovery?

Correct by posting reversal entries and recomputing affected snapshots from the entries, never by editing rows. Recovery is proven when every transaction sums to zero, every recomputed snapshot matches its stored value, and the reconciliation break list is empty or has an owner and a resolution for each remaining row.

Engineering deep dives

Correctness across money and inventory

The database protects local invariants; idempotency, state machines and reconciliation protect the workflow around it.

Make commands repeatable

  • Persist idempotency key, request fingerprint and original response together. Reject key reuse with different parameters and define retention from the maximum retry window.
  • Represent pending and unknown outcomes explicitly. After a timeout, query authoritative provider state before retrying or compensating an irreversible action.

Keep invariants local

  • Put uniqueness, balance and legal state transitions in one transaction and enforce them with constraints, conditional updates or locks—not a cache lock.
  • Choose isolation from the anomaly to prevent. Serializable transactions can abort under contention, so the whole transaction needs a bounded retry path.

Close the distributed gap

  • Write business state and an outbox record atomically; consumers deduplicate effects. Exactly-once inside one platform does not make an external PSP or airline atomic.
  • Reconcile independent statements, retain immutable audit history and repair by compensating entries. Monitor aged pending states and unmatched totals as correctness SLIs.

Asynchronous delivery and replay

Moving work off the request path trades immediate failure for lag, duplicates, ordering constraints and operational backlog.

Define delivery semantics

  • Assume at-least-once at service boundaries. Give each event a stable ID, partition key, schema version and event time; make every side effect idempotent.
  • Guarantee order only within the business entity that needs it. Global order limits parallelism and usually encodes no useful invariant.

Treat lag as user impact

  • Observe oldest-message age, input/output rate, retry count, poison messages and partition skew. Queue depth alone hides slow old work behind new small messages.
  • Use retry topics or delayed queues with expiry and a DLQ; DLQ is not resolution until it has ownership, alerting and a safe replay tool.

Evolve safely

  • Use backward/forward-compatible schemas and tolerant readers. Deploy consumers before producers when adding fields and preserve raw events for bounded replay.
  • Replay into an isolated output or shadow consumer first; throttle it so historical traffic cannot starve live processing or repeat external effects.

Design a wallet-to-wallet payment system. Which ledger invariants must be atomic, and how do you handle idempotency, PSP timeouts or unknown outcomes, and reconciliation without coupling the design to an OTA booking flow?11-system-design-cases.the-big-prompts.q1

Scope and invariants: transfer money between wallets; no duplicate debit or credit, no money created or lost, an immutable audit trail, and an explicit state for every external outcome.

Source of truth: the Ledger Service owns append-only, double-entry postings. A completed internal transfer writes balanced debit and credit entries in one local ACID transaction.

Available balance and reserved/pending balance must be defined separately; a cache may serve display data only when its staleness contract is explicit, never the final authorization decision.

Idempotent command: POST /transfers carries an Idempotency-Key. In one local transaction, persist the key and canonical request fingerprint, create a transfer intent, and write an outbox event.

The same key with a different fingerprint is rejected; the same key with the same fingerprint returns the recorded transfer resource.

External boundary: do not hold a database transaction open while calling a PSP. A worker calls the PSP with a stable provider idempotency key. Persist callbacks and status-query results idempotently.

A timeout is UNKNOWN, not failure or success: query the provider, retry only with the same provider key where safe, then reconcile against settlement records.

Pin the chosen provider/API version, account/region, key scope/retention, and status/webhook contract; this case deliberately does not assume another PSP behaves like Stripe.

The canonical provider-contract checklist is in (09-distributed-tx-fintech.correctness-where-money-is-involved.q1) and (09-distributed-tx-fintech.correctness-where-money-is-involved.q2).

Lifecycle: PENDING → SUCCEEDED | FAILED | REVERSED, with UNKNOWN/RECONCILING for ambiguity. Compensation is a new reversal entry, never mutation or deletion of a posted ledger entry.

Answer frame: invariant → authority → projection → failure recovery. State one of each before choosing components; keep the ledger and PSP boundary explicit.

Key takeaway:

Keep the money invariant inside one ledger transaction; cross the PSP boundary through durable intent, idempotency, status queries and reconciliation—not a distributed rollback.

Case metadata:

  • Workload: transfer rate, amount and tenant mix, plus ledger latency
  • Freshness: ledger state is synchronous while balance projections have an explicit bound
  • Duplicate tolerance: caller key, provider key and replay deduplication
  • Recovery owner: ledger and reconciliation service

State transition guard: One possible model is PENDING -> SUCCEEDED | FAILED; UNKNOWN -> RECONCILING -> SUCCEEDED | FAILED | RECONCILIATION_REQUIRED; and COMPENSATING -> REVERSED | RECONCILIATION_REQUIRED. Every edge needs the ledger version and evidence that authorizes it.

Design an idempotent, asynchronous `POST /payments` contract. How are request fingerprinting, duplicate/replay behavior, durable state transitions, PSP execution, unknown outcomes, and reconciliation defined?11-system-design-cases.the-big-prompts.q11

POST /payments requires an Idempotency-Key scoped to the caller and endpoint.

  1. Canonicalize the semantic request and store its fingerprint. In one local DB transaction, insert the unique idempotency row with IN_PROGRESS, create the Payment resource/intent, and write an outbox command. Do not call the PSP inside that transaction.
  2. If the same key and fingerprint arrive again, return the recorded payment resource and its current state. If the same key carries a different fingerprint, reject it as a conflict; never silently reuse a key for a different amount or payee.
  3. Creation may return 201 Created with Location and status=PENDING; that creates a durable resource, not a claim that money has moved. The client reads the resource to observe the final state.
  4. A worker calls the PSP with a stable provider idempotency key. Webhooks, polling, and status queries update the same payment state idempotently. After a timeout, mark the outcome UNKNOWN/RECONCILING; do not issue a fresh charge.
  5. Keep idempotency records for the documented retry window and retain payment/ledger audit records according to reconciliation and compliance policy.
  6. Pin the PSP's contract with the canonical checklist in (09-distributed-tx-fintech.correctness-where-money-is-involved.q2): API/version, account/region, key scope/retention, payload-mismatch and concurrent-reuse behavior, status inquiry, webhook authenticity/replay, settlement/reversal.

202 confirms resource acceptance, not settled money. Reconciliation resolves a payment that remains ambiguous.

Key takeaway:

The atomic unit is local intent + idempotency state + outbox. The PSP is an at-least-once external boundary, so its result is confirmed by idempotent callbacks/status queries and reconciliation.

  • Benefit: the API never claims synchronous success while the PSP outcome is unknown.
  • Cost: clients must poll or receive a webhook, operation records need retention, and canonical fingerprint rules become part of the public contract.

Case metadata:

  • Workload: payment request rate, amount/currency/tenant mix and PSP quota
  • Freshness: local acceptance is immediate, PSP status is asynchronous with an explicit unknown-age budget
  • Duplicate tolerance: caller idempotency key, provider key and webhook/event ID
  • Recovery owner: payment state machine and reconciliation service

State transition guard: A durable graph can be:

  • RECEIVED -> PROCESSING -> PENDING | UNKNOWN -> SUCCEEDED | FAILED | RECONCILIATION_REQUIRED
  • a confirmed charge: SUCCEEDED -> COMPENSATING -> COMPENSATED | RECONCILIATION_REQUIRED

202 means durable acceptance of processing, never proof of success.
