Pegasus là một dự án nền tảng danh mục - Marketplace Engineering. Đây là một trong những dự án tách biệt hoàn toàn hệ thống catalog ra khỏi hệ thống TIKI.VN. TIKI.VN là một hệ thống lớn với ranh giới không rõ ràng giữa nhiều team và nhiều lĩnh vực. Tất cả các module chia sẻ database và có thể truy cập trực tiếp vào database khác. Để scale, chúng tôi phải chia TIKI.VN thành các hệ thống nhỏ hơn, đặc biệt là Catalog System — xử lý hàng triệu sản phẩm của TIKI.

Chiến lược của chúng tôi:

  • Đầu tiên: ngăn các module khác truy cập trực tiếp vào catalog data source bằng cách cung cấp đầy đủ read/write API
  • Thứ hai: migrate data sang catalog-owned database và chặn mọi direct access

Chúng tôi có ba module:

  • Mercury: replicate mọi thay đổi từ write side (MySQL) sang read side (MongoDB), làm backbone cho product replication.
  • Pegasus: cung cấp read Product API cho mọi caller; đây là API có throughput cao nhất của TIKI.
  • Arcturus: cung cấp API xử lý mọi inventory transaction cho order placement và tích hợp với warehouse system.

Pegasus là read Product API của TIKI. Vì mọi customer touchpoint trên e-commerce website đều liên quan đến product, đây là API có throughput cao nhất của TIKI và ngăn direct access vào catalog MongoDB. Pegasus có các thách thức:

  • Reliability: xử lý mọi traffic để lấy dữ liệu sản phẩm từ TIKI
  • High throughput và low latency: xử lý ít nhất 10k request/giây, TP95<5ms

Approach của chúng tôi để thiết kế Pegasus là:

  • Dùng in-memory để cache product data
  • Subscribe product-change event từ Mercury để invalidate cache
  • Dùng compression để giảm payload size và tận dụng CPU/network.
  • Non-blocking architecture

Pegasus architecture:

Pegasus dựa trên Gridgo framework và tuân theo architectural guideline của nó. Nó bao gồm các thành phần chính:

  • Entry-point: Truy cập vào ứng dụng
  • REST API: Cung cấp API để khách hàng query/invalidate product
  • Kafka consumer: Sử dụng tin nhắn từ Kafka để invalidate product
  • gRPC: Cung cấp gRPC wrapper cho API
  • In-memory cache: key-value data structure để lưu product cache
  • Compressor: compressor có thể config để compress data khi lưu trữ và serve

Entry point

REST API

Pegasus dùng Vert.x connector cho REST API. Mọi HTTP request bắt đầu từ Vert.x internal event loop, sau đó được routed tới processor tương ứng và execute theo một strategy có thể config. Pegasus hỗ trợ các strategy sau:

  • default: Chạy trên cùng một thread với event loop. Không nên dùng strategy này: dù MongoDB client async, một số phần như DNS lookup vẫn sync. Compression cũng CPU-bound, nên single thread không tận dụng hết CPU.
  • executor: Chạy processor bằng Java ExecutorService. Số lượng thread cũng config được. Benchmark cho thấy quá nhiều thread không có lợi ích rõ ràng và còn có thể làm app chậm hơn.
  • Disruptor: Thực thi processor bằng cách sử dụng Disruptor. Thử nghiệm cho thấy việc sử dụng Disruptor trong trường hợp này sẽ không có lợi ích gì so với ExecutorService.

Kafka consumer

Pegasus consume Kafka topic index.catalog.invalidate_product do Mercury tạo ra để invalidate product cache. Invalidation được thực hiện bằng cách evict cache entry; product chỉ được load lại ở lần access tiếp theo.

gRPC

REST API đã xử lý được request có throughput cao và latency thấp. Benchmark cho thấy với 40 open connections, API có thể đạt 24K RPS với TP99 20ms cho single-product API. Tuy nhiên, Tala chủ yếu viết bằng PHP và PHP không có built-in HTTP connection pool, nên mỗi PHP request mở 2–3 connection tới Pegasus. Có lúc lên khoảng 15K open connections và dễ overload load balancer; L7 load balancer có thể làm throughput giảm một nửa và latency tăng 100%.

In-memory cache

Pegasus dùng Guava cho product cache trong in-memory. Đây là một Map đơn giản từ product ID tới product payload. Payload thường là JSON đã transform (xem thêm ở phần Compressor).

Cache thực chất là một chuỗi loader dùng Decorator pattern. Loader cơ bản nhất là DirectMongoLoader, query trực tiếp từ MongoDB. Loader này được bọc trong GuavaLoader, lưu payload vào Guava Loading Cache và chỉ gọi loader khi cache miss.

Với single API, logic rất đơn giản: trả payload khi cache hit; khi cache miss thì query product từ MongoDB.

Với multi API, logic phức tạp hơn: query các product bị thiếu trong cache, merge với product đã có (sau khi decompress), sort theo thứ tự trong request rồi compress trước khi trả response cho client.

Ngoài ra còn có một số tối ưu hóa trong thành phần này:

  • Promise cache: Thay vì cache product payload, chúng tôi cache Promise của payload. Khi multiple threads truy cập cùng product ID và gọi get(Long id), chỉ một thread chạy loader; các thread còn lại chờ. Cách này giảm context switch và giữ thread management đơn giản.
  • Consistent hashing: Bật consistent hashing trong LB có thể tăng cache hit lên khoảng 95% (từ 85%). Hiện tại feature này bị disable vì cần thêm work ở LB và không dùng được L4 LB.
  • GuavaLoader cũng có thể bọc trong OutputCacheLoader để cache toàn bộ response trong một Guava Loading Cache khác. Cách này hữu ích cho multi-product query dưới heavy load. Benchmark cho thấy TP90 có thể xuống dưới 1 giây với payload 200KB và 8000 open connections. Bandwidth khoảng 10 Gbps, transfer rate khoảng 7 Gbps (0,9 GB/s). OutputCacheLoader phù hợp với hot deal sale khi cache hit cao; thông thường cache hit sẽ thấp.

Compressor

Pegasus hỗ trợ configurable Compressor cho product payload. Có thể config compressor riêng cho single query và multi query. Để tối ưu hai API này, chúng tôi dùng application server riêng cho từng API.

  • Để query các sản phẩm đơn lẻ: http://pegasus.xxx
  • Để query nhiều sản phẩm: http://pegasus-query.xxx

Dù codebase giống nhau, config của mỗi API khác nhau:

Với single API, nên cache payload đã gzip và trả trực tiếp cho client vì GZIP nhỏ hơn, giảm payload size, đồng thời không cần compress/decompress những product đã có trong cache.

Với multi API, không thể trả cache trực tiếp nên giữ compressed version trong cache không có lợi. Thay vào đó chỉ cache plaintext version. Khi trả về client, Snappy compress hiệu quả hơn Gzip dù payload tăng khoảng 2x–3x. Benchmark cho thấy latency giảm 50% sau khi chuyển sang Snappy (15ms xuống 6ms).

Một header đặc biệt sẽ cho biết compression algorithm được dùng: compression. Client dùng thông tin này để decompress tương ứng.
