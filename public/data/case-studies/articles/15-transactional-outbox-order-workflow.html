1. The problem is not choosing the right order

A client sends a request to Service A. A must update its own data and publish a message that asks Service B to create related data. These actions belong to two resource managers: a database and a message broker. A local transaction cannot commit both automatically.

OrderCrash windowObservable state
Commit DB, then publishA crashes after commit, before publishA changed, but B is never notified
Publish, then commit DBA crashes after publish, before commitB handles a change A never committed
Publish inside DB transactionBroker confirms, then DB rolls backThe message escaped; rollback cannot recall it

Retrying the entire request is not a complete solution either: the client can time out after A committed, resend, and trigger another execution. The right question is: which consistency boundary can the system actually commit atomically?

2. Start with the real-world process

Use the order as the root aggregate. Creating an order, taking payment, reserving inventory and shipping are not one long transaction; they form a workflow of separate commitments, each with a state and a compensation path.

  1. Order Service creates an order in CREATED.
  2. The user checks out: the order moves to PAYMENT_PENDING.
  3. Payment Service succeeds: the order moves to PAID; on failure it moves to PAYMENT_FAILED.
  4. Inventory Service reserves stock: success produces INVENTORY_RESERVED; rejection requests a refund.
  5. Only after both money and stock are confirmed does Shipping Service receive a shipment request.

3. One commit for the business row and delivery intent

Service A does not publish directly inside the request transaction. It writes both business state and the event to its database. A commit preserves both; a rollback removes both.

BEGIN;

UPDATE orders
SET status = 'PAYMENT_PENDING', version = version + 1
WHERE id = 'order-123' AND version = 7;

INSERT INTO outbox_events (
  event_id, aggregate_id, aggregate_version,
  event_type, payload, status, created_at
) VALUES (
  'evt-456', 'order-123', 8,
  'PaymentRequested', '{...}', 'PENDING', CURRENT_TIMESTAMP
);

COMMIT;

event_id is the stable identity for retries. aggregate_id groups events for one order; aggregate_version helps consumers detect stale or out-of-order events. The payload should carry the contracted data rather than forcing consumers to read Service A's private database.

4. The relay publishes without pretending to be exactly-once

A relay claims PENDING rows, publishes them, waits for broker acknowledgement, then marks them PUBLISHED. Multiple workers may use leases or FOR UPDATE SKIP LOCKED to avoid claiming the same batch. On publish failure, the row remains durable and is retried with backoff.

Where does the relay stop?After restartDesign requirement
Before broker acknowledgementPublish againThe event is not lost
After acknowledgement, before marking publishedMay publish twiceThe consumer must be idempotent
After marking publishedDo not claim againRetain for audit, then clean up by policy

This is at-least-once delivery. Calling it exactly-once merely moves the duplicate into a less visible corner; end-to-end correctness still needs stable identity and idempotent side effects.

5. Service B uses an Inbox to turn duplicates into no-ops

Service B must not read an event_id, see that it is absent, and then insert the business row. Two concurrent consumers can both pass that check. The deduplication marker and business mutation must commit in one local transaction.

BEGIN;

WITH accepted AS (
  INSERT INTO processed_messages (consumer_name, event_id, processed_at)
  VALUES ('payment-service', 'evt-456', CURRENT_TIMESTAMP)
  ON CONFLICT DO NOTHING
  RETURNING event_id
)
INSERT INTO payments (order_id, amount, status)
SELECT 'order-123', 500000, 'AUTHORIZED'
FROM accepted;

COMMIT;

In addition to event deduplication, the business table should have a constraint for the intent, such as UNIQUE(order_id, payment_attempt). Event identity blocks replay of one message; the business key blocks two different messages that accidentally request the same side effect.

6. Outbox transports events; a Saga controls the business

Outbox does not know which order transition is legal. The order state machine encodes invariants and compensating actions.

EventLegal transitionNext action
PaymentSucceededPAYMENT_PENDING → PAIDEmit InventoryReservationRequested
PaymentFailedPAYMENT_PENDING → PAYMENT_FAILEDStop the workflow
InventoryReservedPAID → INVENTORY_RESERVEDEmit ShipmentRequested
InventoryRejectedPAID → REFUND_PENDINGEmit RefundRequested

Choreography works when the flow is short and ownership is clear. As branches, timeouts and compensations multiply, an orchestrator can make the state machine more visible. In either style, every service writes only its own database and emits through its own outbox.

7. The API promises only what is durable

When the Order Service transaction commits, the whole workflow is not complete. The API should return 202 Accepted with a pending state:

HTTP/1.1 202 Accepted
Location: /orders/order-123

{
  "orderId": "order-123",
  "status": "PAYMENT_PENDING"
}

The client may poll the resource, receive an SSE/WebSocket notification, or accept a webhook. A client retrying the same checkout intent should send an idempotency key so Order Service returns the existing order instead of starting a second Saga.

8. The production work that is often omitted

  • Lag: measure the age of the oldest PENDING row, not only queue depth.
  • Retry: use exponential backoff with jitter; separate transient failure from invalid payloads.
  • Poison event: move it to an error state or DLQ with an alert and replay procedure; never hot-loop forever.
  • Ordering: partition by aggregate_id when per-order ordering matters; consumers still validate versions.
  • Retention: archive or delete outbox and inbox rows according to the promised deduplication window.
  • Reconciliation: compare business state with downstream event/state to locate stuck workflows.
  • Tracing: carry correlation_id and causation_id through every event.

9. Failure cases that must be tested

  1. Business transaction rolls back: neither the business change nor an outbox row exists.
  2. Crash after commit, before the first poll: the restarted relay still publishes the event.
  3. Crash after broker acknowledgement, before updating outbox: B receives a duplicate but creates one side effect.
  4. Two relays claim concurrently: one row is not processed in parallel outside the chosen claim mechanism.
  5. Two consumers receive the same event concurrently: the inbox unique constraint adjudicates.
  6. An old event version arrives after a new one: the state machine rejects or reconciles it.
  7. Inventory rejects after payment succeeds: the Saga creates exactly one refund intent.
  8. The client times out and retries: its idempotency key returns the same order.

10. Design conclusion

Do not choose “save first” or “send first.” Service A commits the business row and outbox row in one local transaction; the relay publishes with retries; Service B uses a transactional inbox and business constraints for idempotency. Above that delivery mechanism, the order state machine or Saga defines real-world sequencing and compensation.

Transactional Outbox converts an uncontrolled atomicity gap into two visible problems: observable eventual delivery and identified duplicate processing. That is an operable trade-off, not magic that removes every failure.

11. Review questions

  1. Why does wrapping publish inside a database transaction still not make the dual write atomic?
  2. At which relay crash point is a duplicate created, and why can it not mark PUBLISHED before publishing?
  3. How should the inbox be designed so two concurrent consumers cannot both create a payment?
  4. When is per-aggregate ordering required, and how does a consumer protect itself with versions?
  5. If payment succeeds but inventory is unavailable, what is the compensating action and which service owns that decision?
