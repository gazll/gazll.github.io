1. The problem is not choosing the right order

Case boundary: this is a repository-authored design example, not a claim that a named production system uses these exact tables. The generic Outbox, broker-delivery and API-contract background belongs to Topic 09, Topic 08 and Topic 17. This case follows one concrete order through its local commits, relay crashes, duplicate handling and business recovery.

A client sends a request to Service A. A must update its own data and publish a message that asks Service B to create related data. These actions belong to two resource managers: a database and a message broker. A local transaction cannot commit both automatically.

OrderCrash windowObservable state
Commit DB, then publishA crashes after commit, before publishA changed, but B is never notified
Publish, then commit DBA crashes after publish, before commitB handles a change A never committed
Publish inside DB transactionBroker confirms, then DB rolls backThe message escaped; rollback cannot recall it

Retrying the entire request is not a complete solution either: the client can time out after A committed, resend, and trigger another execution. The useful question is: which consistency boundary can the system actually commit atomically? Here it is Service A's local database; publication and downstream effects remain later, observable steps.

2. Start with the real-world process

Use the order as the root aggregate. Creating an order, taking payment, reserving inventory and shipping are not one long transaction; they form a workflow of separate commitments, each with a state and a compensation path owned by the relevant domain.

  1. Order Service creates an order in CREATED.
  2. The user checks out: the order moves to PAYMENT_PENDING.
  3. Payment Service succeeds: the order moves to PAID; on a confirmed failure it moves to PAYMENT_FAILED.
  4. Inventory Service reserves stock: success produces INVENTORY_RESERVED; rejection creates a refund intent.
  5. Only after both money and stock are confirmed does Shipping Service receive a shipment request.

Order Service owns the workflow state, Payment Service owns the payment attempt and provider reference, Inventory Service owns stock, and Shipping Service owns shipment state. A refund is a new business operation, not a database rollback. If a provider call times out after the request may have reached it, the order must remain PAYMENT_UNKNOWN until a provider status query, callback or reconciliation job establishes the outcome.

3. One commit for the business row and delivery intent

Service A does not publish directly inside the request transaction. It writes both business state and the event to the same local database and transaction. A successful database commit preserves both under that database's configured durability contract; a rollback removes both. The broker is outside this atomic boundary, so the relay publishes later.

BEGIN;

UPDATE orders
SET status = 'PAYMENT_PENDING', version = version + 1
WHERE id = 'order-123' AND version = 7;
-- require affected rows = 1; otherwise reject a stale command

INSERT INTO outbox_events (
  event_id, aggregate_id, aggregate_version,
  event_type, payload, status, created_at
) VALUES (
  'evt-456', 'order-123', 8,
  'PaymentRequested', '{...}', 'PENDING', CURRENT_TIMESTAMP
);

COMMIT;

event_id is the stable identity for retries. aggregate_id groups events for one order; aggregate_version lets a consumer validate the sequence, but it does not reorder or repair events by itself. If the consumer has version 8 and receives version 7, it can record a stale duplicate as a no-op; if it receives version 9 before 8, it must queue a gap or request repair rather than apply the event blindly. The payload should carry the contracted data rather than forcing consumers to read Service A's private database.

4. The relay publishes without pretending to be exactly-once

For this case, a relay claims PENDING rows with a short, expiring lease, publishes them, waits for the broker's documented acknowledgement, then records the local observation as PUBLISHED. A lease is a recovery mechanism, not proof that an old worker has stopped. FOR UPDATE SKIP LOCKED can help queue-like claiming, but its skipped view is not a general correctness read; the application still needs expiry, reclaim and duplicate-safe publication.

The fields, claim order and LIMIT below are illustrative. Lease duration, batch size and ordering key must be chosen from the broker/database workload and failure measurements.

BEGIN;

SELECT event_id
FROM outbox_events
WHERE status = 'PENDING'
  AND (lease_until IS NULL OR lease_until < CURRENT_TIMESTAMP)
ORDER BY aggregate_id, aggregate_version, created_at, event_id
FOR UPDATE SKIP LOCKED
LIMIT 50;

UPDATE outbox_events
SET status = 'CLAIMED', lease_owner = :worker,
    lease_until = :lease_until, claim_token = :token
WHERE event_id IN (:claimed_ids);

COMMIT;
-- publish outside the claim transaction
-- acknowledge, then update only with the same claim_token
Where does the relay stop?After restart or lease expiryDesign requirement
Claimed, before publishReclaim after lease_until; the old worker may still have been pausedOldest-claimed alert, bounded work and a reclaim path
After broker acknowledgement, before marking publishedMay publish twiceStable event ID, Inbox/business-key protection and a conditional status update
After marking publishedDo not claim againRetain for audit, repair and cleanup by an explicit policy

In this article, PUBLISHED means that the relay observed the broker publication boundary; it does not mean that a consumer acknowledged the message or that the order business effect completed. This is at-least-once delivery. Calling it exactly-once merely moves the duplicate into a less visible corner; end-to-end correctness still needs stable identity and idempotent side effects.

UPDATE outbox_events
SET status = 'PUBLISHED', lease_owner = NULL, lease_until = NULL
WHERE event_id = :event_id
  AND claim_token = :token;

If that conditional update affects zero rows, the worker lost its claim or a repair process changed the row. It must not overwrite the newer state; the publication may still be a harmless duplicate.

5. Service B uses an Inbox to turn duplicates into no-ops

Service B must not read an event_id, see that it is absent, and then insert the business row. Two concurrent consumers can both pass that check. The deduplication marker and the local business mutation must commit in one local transaction, with a unique key scoped to the consumer and event.

BEGIN;

WITH accepted AS (
  INSERT INTO processed_messages (consumer_name, event_id, processed_at)
  VALUES ('payment-service', 'evt-456', CURRENT_TIMESTAMP)
  ON CONFLICT DO NOTHING
  RETURNING event_id
)
INSERT INTO payments (order_id, payment_attempt, amount, status)
SELECT 'order-123', 1, 500000, 'AUTHORIZATION_PENDING'
FROM accepted;

COMMIT;

The example uses PostgreSQL-style illustrative SQL; the invariant is portable even when the syntax is not. The inserted row is a local authorization intent, not proof that the external provider has authorized the payment. The Inbox must have a uniqueness rule such as UNIQUE(consumer_name, event_id), while the business table needs a separate intent rule such as UNIQUE(order_id, payment_attempt). Event identity blocks replay of one message; the business key blocks two different messages that accidentally request the same side effect.

If the event ID is already present, the consumer records a no-op. If the same ID arrives with a conflicting payload, it goes to quarantine rather than silently changing history. A notification or another downstream effect after this transaction belongs to Service B's own outbox; never commit the Inbox marker first and assume the later effect will happen.

6. Outbox transports events; the order workflow controls the business

The generic Saga choice is covered in Topic 09; the queue acknowledgement boundary is covered in Topic 08. This case keeps only the transitions needed to implement this order. Outbox transports a durable intent; the order state machine decides which event is legal and which business action follows.

Event or outcomeLegal transitionNext action
PaymentSucceededPAYMENT_PENDING → PAIDEmit InventoryReservationRequested
PaymentFailedPAYMENT_PENDING → PAYMENT_FAILEDStop the workflow
Provider status confirms success after timeoutPAYMENT_UNKNOWN → PAIDUse the original provider reference; do not create a new charge
InventoryReservedPAID → INVENTORY_RESERVEDEmit ShipmentRequested
InventoryRejectedPAID → REFUND_PENDINGEmit one RefundRequested intent
Refund fails or remains unknownREFUND_PENDING → RECONCILIATION_REQUIREDAlert the owner; reconcile before retrying a new intent

Choreography can fit this short flow when ownership is clear. If branches, timeouts and compensations multiply, an orchestrator can make the state machine and durable workflow state more visible. Either way, compensation is a new business transaction, not a rollback of a completed remote effect. Every service writes only its own database and emits through its own outbox.

7. The API promises only what is durable

When the Order Service transaction commits, the whole workflow is not complete. The endpoint can return 202 Accepted only after durable acceptance, with a status resource that is authorized for the same tenant and order. The values below are illustrative; actual retry hints and expiry must follow measured workload, provider contracts and product SLOs:

HTTP/1.1 202 Accepted
Location: /orders/order-123
Retry-After: 3
Content-Type: application/json

{
  "orderId": "order-123",
  "status": "PAYMENT_PENDING",
  "expiresAt": "2026-08-23T12:05:00Z",
  "links": {
    "self": "/orders/order-123"
  }
}

The client may poll the resource, receive an SSE/WebSocket notification, or accept a webhook. A client retrying the same checkout intent should send one stable idempotency key so Order Service returns the existing order instead of starting a second workflow. A key reused with different parameters is a conflict, not permission to create another order. See Topic 17 for the general status/error contract; this case adds the concrete states PAYMENT_UNKNOWN, REFUND_PENDING, RECONCILIATION_REQUIRED and terminal expiry.

PAYMENT_UNKNOWN means the request outcome is not yet known, not that payment failed. The service queries the provider, accepts the signed callback or runs reconciliation under the original provider key/reference. If the status resource expires, it exposes a terminal failure or manual-review state according to product policy; it must not hide the item or blindly send a new charge.

8. The production work that is often omitted

  • Lag: measure outbox_oldest_pending_age_seconds and the oldest claimed age, not only queue depth; assign an owner and a repair runbook.
  • Claim recovery: count expired leases and conditional mark failures; alert when a reclaimed row keeps publishing duplicates.
  • Retry: choose one retry owner per hop, use deadlines, exponential backoff with jitter and a retry budget, and classify non-retriable payload errors.
  • Poison event: move it to an error state or DLQ with an alert, schema check, authorized redrive and replay procedure; never hot-loop forever.
  • Ordering: partition by aggregate_id when per-order ordering matters; consumers still validate versions and route gaps to repair.
  • Retention: keep Outbox history for the maximum duplicate, replay and reconciliation window promised by the product; do not copy a provider's key TTL without checking scope.
  • Inbox: monitor duplicate no-ops, growth and cleanup age; the durable business key must remain safe even after an Inbox row expires.
  • Reconciliation: measure provider-unknown items, refund debt and RECONCILIATION_REQUIRED age; compare authoritative business state with downstream state.
  • Tracing: carry opaque correlation_id, causation_id and trace context through every event, but never put secrets or full payment/PII payloads in trace attributes.
  • Access: tenant-scope status, DLQ and replay operations; record who redrove an event and why.
  • Relay choice: polling is the example here; CDC/outbox routers are alternatives with their own connector lag, schema, offset and replay operations.

9. Failure cases that must be tested

  1. Business transaction rolls back: neither the business change nor an outbox row exists.
  2. Database commit succeeds but the process dies before the response: the same client key returns the existing order.
  3. Relay claims a row and dies before publish: lease expiry makes it reclaimable and the oldest-claimed alert fires.
  4. Relay publishes successfully, then dies before updating Outbox: B receives a duplicate but creates one side effect.
  5. A stale worker updates after its lease is stolen: the claim token prevents it from overwriting the newer state.
  6. Two consumers receive the same event concurrently: the Inbox unique constraint adjudicates.
  7. A mutant commits the Inbox marker before the business effect: the test fails because the effect would be lost on crash.
  8. An old event arrives after a new one: the state machine no-ops a stale duplicate or queues a version gap for repair.
  9. A provider times out after transmission: the workflow queries the original reference and never retries with a new intent.
  10. The same provider callback and an authorized replay arrive twice: both are harmless and do not create a second refund or charge.
  11. Inventory rejects after payment succeeds: exactly one refund intent is created; a failed refund enters reconciliation.
  12. An incompatible event schema is redriven: compatibility and quarantine checks run before production effects.
  13. Inbox or Outbox retention expires: the business key, audit policy and reconciliation path still define safe behavior.

10. Design conclusion

Do not choose “save first” or “send first.” In this order implementation, Service A commits the business row and Outbox row in the same local transaction; the leased relay publishes with at-least-once semantics; Service B commits its Inbox marker and business-key-guarded effect together. Above that delivery mechanism, the order state machine defines legal transitions, provider-unknown handling and compensation.

Transactional Outbox converts an uncontrolled atomicity gap into visible, owned work: durable local intent, eventual broker publication, identified duplicate processing and reconciliation for outcomes that cannot be observed immediately. It does not make a payment provider, broker consumer or compensation step exactly once.

11. Review questions

  1. Why does wrapping publish inside a database transaction still not make the dual write atomic?
  2. At which relay crash point is a duplicate created, and why can it not mark PUBLISHED before broker acknowledgement?
  3. What expires a relay claim, and how does a claim token stop an old worker from overwriting a reclaimed row?
  4. How do the Inbox event key and the payment business key protect different invariants?
  5. What should happen when version 9 arrives while version 8 is missing?
  6. If payment times out after transmission, why is PAYMENT_UNKNOWN safer than sending a new charge?
  7. If payment succeeds but inventory is unavailable, which service owns the refund decision and what happens if compensation also fails?
