Một booking system tạo hai airline record cho cùng passenger và flight, chỉ cách nhau vài mili-giây. Lần điều tra đầu đổ lỗi cho crawler rồi chặn User-Agent của nó. Alert im suốt hai năm rưỡi. Sau đó cùng defect quay lại dưới dạng request HEAD.

Bug thật không nằm ở identity của request. Nó nằm trong check-then-act window mà mọi request đều đi qua. Incident này cho thấy một diagnosis hợp lý vẫn có thể tạo metric thuyết phục trong khi invariant bị vi phạm chưa hề được sửa.

1. Invariant và unsafe boundary

OTA có Python web tier sau load balancer và Java booking backend. Backend lưu booking state trong SESSION_INFO, rồi gọi GDS để tạo PNR của hãng và itinerary number, hay ITN, của OTA. Một booking intent phải tạo đúng một PNR và một ITN.

Session state đi qua Init → Booking → Complete hoặc Error. Browser gọi /reservation/book; backend đọc Init, đổi sang Booking, rồi bắt đầu một asynchronous GDS call.

Endpoint nhận cả POST lẫn GET vì payment redirect của 3-D Secure quay về qua GET URL. Như vậy một state-changing action có thể bị browser, link scanner hoặc security software fetch. Method filter giảm accidental call, nhưng correctness vẫn phải chịu được duplicate request từ bất kỳ nguồn nào.

2. Evidence thực sự nói gì?

Một scheduled query—not exception hay customer report—phát hiện incident:

SELECT session_id, COUNT(itn_no)
FROM itinerary_tracking
WHERE tracked_at >= <15 minutes ago>
GROUP BY session_id
HAVING COUNT(itn_no) > 1;

Grouping key là chi tiết quyết định. Alert không nói “cùng passenger book hai lần”. Nó nói một session sinh nhiều ITN, tín hiệu mạnh rằng một booking intent đã bị execute trùng.

Incident hiếm—thường từ không đến hai case mỗi tháng—nhưng đắt. Airline có thể hủy cả hai duplicate reservation, churning có thể sinh Agency Debit Memo, còn double ticketing kéo theo manual refund. Case xảy ra ban đêm nguy hiểm hơn vì xử lý phụ thuộc business hour.

Staging không reproduce được race, nên team dựng lại hai request từ compressed log trên mọi backend instance, nối bằng transaction key rồi đặt hai timeline cạnh nhau. Evidence hữu ích xuất hiện: request đến cách nhau 2 ms và cùng lọt qua read/write window dài 25 ms.

3. Guard chỉ là check-then-act

if (BOOKING_PROCESSED.equals(productInfo.getBookingStatus())) {
    return FAILED;
}
if (BOOKING_COMPLETED.equals(productInfo.getBookingStatus())) {
    return FAILED;
}

productInfo.setBookingStatus(BOOKING_PROCESSED);
sessionTable.update(...);
new BookingThread(...).start();

Guard này chặn request đến sau khi status update. Nó không thể chặn hai request cùng đọc trước khi update nào commit. Code nhìn tuần tự; production execution thì không.

Hai request còn rơi vào hai application instance khác nhau. Java synchronized hay local cache lock không thể bảo vệ invariant. Database row là shared point duy nhất mà cả hai bắt buộc đi qua.

4. Một false fix đầy thuyết phục

Bảy trong chín duplicate pair chứa token google-bot trong User-Agent. Incident được gọi là “Googlebot crawl booking page”, và tên gọi ấy dẫn thẳng tới solution.

Chính evidence lại phản bác diagnosis. Source IP thuộc consumer network, không phải verified Google range. User-Agent không khớp crawler format của Google. Quan trọng nhất, nó xuất hiện cạnh mobile request thật của user ngay sau 3-D Secure redirect. Một duplicate về sau thậm chí bị backend guard từ chối, nhưng web tier chỉ log error rồi tiếp tục.

Patch được release chặn User-Agent đó tại nginx và thêm client-side suppression. Monitoring ghi nhận 117 request bị block trong 33 ngày và không còn duplicate alert. Số liệu hoàn toàn thật, nhưng chỉ chứng minh một observed trigger đã biến mất. Nó không chứng minh booking creation đã atomic.

Đây là diagnostic trap: khi cause được gọi theo vẻ ngoài—“Googlebot”—solution sẽ nhắm vào vẻ ngoài. Correctness fix phải nhắm vào invariant mà mọi duplicate đều phải đi qua.

5. Cùng mechanism, khác bộ đồ

Hai năm rưỡi sau, hai request tới cách nhau 23 ms với User-Agent bình thường của browser. Lần này duplicate là request HEAD. Framework routing xử lý HEAD như GET, nên metadata probe chạy thẳng vào booking handler.

Bộ đồ đổi từ suspicious User-Agent sang unexpected HTTP method. Mechanism nền vẫn y hệt: cả hai request đọc cùng session state, qua cùng guard và bắt đầu hai booking riêng.

Optimistic-lock token hiện có cũng không phân xử được race. Nó tái sử dụng update timestamp có resolution một giây. Hai request cách nhau 23 ms thấy cùng rounded value nên cả hai update đều match. Tăng precision chỉ làm collision ít hơn, không làm nó bất khả thi; probability reduction không phải correctness guarantee.

6. Đưa quyết định vào một atomic write

Permanent fix thêm integer column VERSION. Mọi session update đều increment nó, còn booking transition match version đã đọc:

UPDATE SESSION_INFO
   SET VALUE   = ?,
       UPD_DT  = ?,
       VERSION = VERSION + 1
 WHERE TRANSACTION_KEY    = ?
   AND AUTHENTICATION_KEY = ?
   AND VERSION            = ?;
int count = jdbcManager.updateBySqlFile(sqlFileName, sessionInfo).execute();
if (count != 1) {
    return FAILED; // another request won the transition
}

Giờ check và act là cùng một statement. Hai contender có thể đọc cùng version, nhưng chỉ một bên update được. Winner đổi version; predicate của loser match zero row. Affected-row count chính là atomic decision.

Web tier đồng thời route HEAD sang handler trả 405 Method Not Allowed kèm Allow: GET, POST. Nó loại một accidental trigger đã biết và làm HTTP semantics đúng hơn. Đây là defense in depth, không phải concurrency guarantee.

7. Verify invariant, rollout và rollback

Schema migration dùng VERSION INT DEFAULT 0 NOT NULL, nên live session đang tồn tại nhận token hợp lệ mà không cần backfill riêng. Execution plan trước và sau predicate được so sánh để xác nhận hot update giữ nguyên access path.

Test assert outcome thay vì implementation detail: hai concurrent booking call cho một success và một failure; năm call cho đúng một success; update bình thường increment version; HEAD không bao giờ chạm booking API. Một controlled delay nới rộng window 23 ms, biến probabilistic race thành deterministic integration test.

Thay đổi đi qua năm repository, bốn product line, mười hai screen và một shared session table. Team chạy 17 unit test cùng 39 integration scenario, monitor rejection lẫn booking signal sau release và chuẩn bị sẵn revert change. Additive database column được giữ khi rollback vì old code có thể bỏ qua nó an toàn.

8. Fix này đảm bảo gì—và không đảm bảo gì?

Version check hoạt động vì hai duplicate request chia sẻ một session row. Duplicate từ hai session, device hoặc expired session có thể vượt boundary này. API design mạnh hơn dùng idempotency key sinh theo booking intent và bảo vệ bằng unique constraint; mọi retry khi đó trả original outcome thay vì tạo booking khác.

State-changing command cũng không nên ẩn sau fetchable GET. Redirect của 3-D Secure có thể về một idempotent confirmation endpoint, rồi endpoint đó submit hoặc resume booking command dưới cùng intent key.

Bài học kỹ thuật rất gọn: xác định invariant, tìm shared serialization point và để một atomic write chọn winner. Edge filter giảm noise. Nó không thể thay database-enforced correctness.

9. Review checklist

  1. Check-then-act không phải mutual exclusion. Hãy hỏi ai có thể write giữa read và action.
  2. Timestamp là version token yếu. Resolution và clock semantics tạo collision mà monotonic integer tránh được.
  3. Alert im không chứng minh invariant. Đo cả duplicate bị reject lẫn normal transition thành công.
  4. Multi-instance lock cần shared arbitration. Local synchronization không bảo vệ work được route sang process khác.
  5. Test race một cách tất định. Inject barrier hoặc delay rồi assert đúng một committed side effect.
  6. Ghi rõ boundary. Optimistic locking bảo vệ một row; idempotency bảo vệ một business intent.

10. Ghi chú ẩn danh

Bài viết dựa trên một production incident có thật. Company, brand, person, ticket, host, IP, booking và internal URL identifier đã được loại bỏ. Code, SQL và timeline được rút gọn nhưng giữ nguyên concurrency behavior.
