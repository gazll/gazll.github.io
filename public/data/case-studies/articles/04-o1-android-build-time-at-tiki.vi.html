The problem

Build time luôn là vấn đề lớn đối với các Android developer. Để giảm build time, developer thường chia project thành nhiều module để tận dụng parallel execution của Gradle. Tại Tiki, chúng tôi modularize project theo approach “per feature”, nghĩa là mỗi feature nằm trong một module riêng.

Khi phát triển feature mới hoặc duy trì feature cũ, các nhà phát triển Tiki thường phải thực hiện những thay đổi trong :data module khiến toàn bộ dự án phải compile lại vì hầu hết các feature module của chúng tôi đều dựa trên nó. Toàn bộ quá trình sẽ mất khoảng 5–8 phút. Bạn càng có nhiều module/feature thì quá trình xây dựng sẽ càng mất nhiều thời gian. Chúng tôi gọi đây là O(n) build time.

Chúng tôi muốn phát triển nhanh, do đó việc phát triển các feature mới phải nhanh, điều này dẫn đến vấn đề cốt lõi là build time của chúng tôi phải nhanh. 5–8 phút không phải là nhanh vì mỗi ngày có khoảng 10–20 build được thực hiện. Lãng phí tổng cộng 50–160 phút mỗi ngày hoàn toàn không hiệu quả.

The solution

Hóa ra, Gradle không cần phải compile lại các module bị ảnh hưởng nếu chúng không được đưa vào dự án ngay từ đầu.

Giả sử bạn đang làm việc trên Màn hình chính trong :home module, bạn chỉ quan tâm đến những thay đổi chỉ trên Màn hình chính (vì việc compile lại các feature module khác không có ý nghĩa gì đối với bạn, nó chỉ lãng phí thời gian!). Vì lý do đó, chúng tôi quyết định tạm thời loại trừ các feature module khác để Gradle không phải compile lại chúng.

Ý tưởng rất đơn giản, chúng ta sẽ sử dụng dòng lệnh Gradle với một tham số tùy chỉnh để biết chúng ta nên đưa module nào vào build đó.

./gradlew :app:installDebug -Ponly="home"
// app/build.gradle
apply plugin: 'com.android.application'

def include(moduleName) {
if (hasProperty('only')) {
return only.split(",").contains(moduleName)
}
return true
}

dependencies {
implementation 'androidx.appcompat:appcompat:1.0.2'
if (include("home")) {
implementation project(":home")
}
if (include("detail")) {
implementation project(":detail")
}
if (include("search")) {
implementation project(":search")
}
}

Đối với lệnh xây dựng cụ thể này, chỉ có 3 module được compile lại nếu có gì đó thay đổi trong :data module.

Implementation detail

Trong GitHub project bên dưới, tôi đã tạo một sample project để minh họa ý tưởng này. Phần tiếp theo thảo luận một số challenge khi áp dụng ý tưởng vào codebase thực tế.

nlgtuankiet/modularization ↗

Đầu tiên, chúng ta phải compile ứng dụng. Vì tất cả feature module đều bị exclude khỏi project, :app module không thể resolve class được khai báo trong feature module. Số lượng reference tùy thuộc codebase; với codebase của chúng tôi chỉ có hai reference:

Activity class: chúng tôi dùng một static method trong Activity class để tạo starter intent cho navigation. Để loại bỏ reference này, cách đơn giản nhất là dùng reflection.

// :detail module

class DetailActivity : DaggerAppCompatActivity() {
// omitted

companion object {
@JvmStatic
@Keep
fun starterIntent(context:Context, productId:String): Intent {
return Intent(context, DetailActivity::class.java).apply {
putExtra("productId", productId)
}
}
}
}
// :app module

override fun detailIntent(context:Context, productId:String): Intent {
// old way
// return DetailActivity.starterIntent(context = context, productId = productId)

// new way
return Class.forName("com.nlgtuankiet.modularization.detail.DetailActivity")
.getDeclaredMethod("starterIntent", Context::class.java, String::class.java)
.invoke(null, context, productId) as Intent
}

Mặc dù reflection dễ triển khai nhưng có thêm một số runtime cost, trong project mẫu chúng tôi dùng một cách khác dựa trên Dagger 2 là @BindOptionalOf để loại bỏ nhược điểm này. Tôi không đi sâu hơn vì phần này liên quan đến Dagger 2, nhưng bạn có thể xem source code để biết cách triển khai.

Activity's Dagger module: theo best practice của Dagger 2, mỗi activity có một module tương ứng và AppComponent trong :app module reference tới tất cả các module này.

// :app
@Singleton
@Component(
modules = [
AndroidSupportInjectionModule::class,
HomeActivityModule::class,
DetailActivityModule::class,
SearchActivityModule::class
]
)
interface AppComponent

// :home
@Module
interface HomeActivityModule {
@ContributesAndroidInjector
fun activity(): HomeActivity
}

Lúc đầu, chúng tôi cố gắng tạo ra một sản phẩm độc lập Component cho từng hoạt động thay vì Subcomponent từ AppComponent, do đó AppComponent, không cần phải tham chiếu đến module của hoạt động nữa. Tái cấu trúc từ Subcomponent để Component tốn thời gian và chúng tôi có rất nhiều module để cấu trúc lại. Cách tiếp cận này sẽ giải quyết được vấn đề nhưng cũng sẽ đòi hỏi nhiều thời gian (và chúng tôi không muốn điều đó!).

Cuối cùng, chúng tôi nghĩ ra một technique đơn giản gọi là fake source set: tạo một fake source set để thay thế real source đang bị thiếu.

Đồng thời include source set tương ứng với các module bị exclude.

// app/build.gradle
def include(moduleName) {
if (hasProperty('only')) {
return only.split(",").contains(moduleName)
}
return true
}
android {
sourceSets {
if (project.hasProperty("only")) {
new File(projectDir, "src/fake").listFiles().each { f->
if (!include(f.name)) {
// include fake source set
main.java.srcDir "src/fake/${f.name}"
}
}
}
}
}

Theo cách này, AppComponent chỉ cần reference một empty module và có thể compile thành công. Vấn đề đã được giải quyết!

The result

Sau khi triển khai ý tưởng này vào dự án Tiki Android, build time đã giảm đi một nửa. Một trong những điểm cộng của việc này là kích thước APK gỡ lỗi trở nên thực sự nhỏ do tất cả feature của ứng dụng bị loại trừ, điều này cũng sẽ tiết kiệm rất nhiều thời gian khi triển khai APK trên thiết bị thử nghiệm.

Như bạn có thể thấy, với thiết lập này, bất kể dự án của bạn lớn đến đâu hay bạn có bao nhiêu module, build time của bạn vẫn giữ nguyên và đó là lý do tại sao chúng tôi gọi đây là O(1) build time.
