1. A booking action that is also a fetchable URL

The system is an OTA selling international flights, hotels and packages. One core serves five brands plus metasearch traffic, split into two tiers: a Python web/BFF tier running many instances behind a load balancer, and a Java booking backend that holds session state in a SESSION_INFO table and calls the GDS to create the airline record.

Two identifiers matter. The ITN is the itinerary number, the OTA's own booking record. The PNR is the record at the GDS. One user intent should produce exactly one of each.

The booking flow runs input → confirm → complete. On the last step the browser calls /reservation/book, the web tier forwards to the backend, the backend reads the session, checks its status, marks it in progress, and spawns an asynchronous thread that calls the GDS to create the PNR and generate the ITN.

Session state is a four-value machine: Init (booking allowed), Booking (in progress), Complete (finished), Error (failed). Between reading that status and writing it there is a gap, and business logic runs inside the gap.

One architectural detail becomes the centre of the story: /reservation/book accepts both GET and POST. It has to accept GET, because once 3-D Secure finishes authenticating, the payment gateway redirects the user back into the flow — and a redirect is always a GET.

Put differently: the act of creating a booking is a fetchable URL. And on the internet, anything fetchable will be fetched — by browsers, by security software, by proxies, by anything that sees a link.

2. The alert was more specific than anyone read it as

Nobody reported it. There was no exception in the logs either. A periodic SQL batch found it:

SELECT   t.session_id, COUNT(t.itn_no)
FROM     itinerary_tracking t
         JOIN order_item o ON o.itn_no  = t.itn_no
         JOIN orders     r ON r.order_id = o.order_id
WHERE    t.session_id IS NOT NULL
  AND    r.interline_flag <> '1'
  AND    t.tracked_at >= <15 minutes ago>
GROUP BY t.session_id
HAVING   COUNT(t.itn_no) > 1

The detector groups by session_id. It does not compare passenger names or flight numbers. It asks a much narrower question: did one browsing session produce more than one ITN?

So from day one the thing being alerted on was never "a customer booked twice by mistake". It was one session, two bookings — the signature of concurrent duplicate requests, not of two independent user actions. For the whole of the first investigation, nobody read the alert that way.

Plus exactly one case on the hotel side, in July 2023. One or two a month, with the December 2023 cluster triggering the investigation. The gap between flights and hotels — 17 cases against 1 — gets explained in §3.10, and the explanation is not in the code.

A duplicate record in an internal system sounds like a display bug. In travel it is not. The ticketing team named three kinds of damage.

The airline may cancel both records. On detecting two bookings with the same passenger on the same flight, the carrier's system cancels them itself — and cancels both, not keeping one. Only a record that has already been ticketed is safe. In the "booked, not yet ticketed" state, this incident can leave the customer with no seat at all.

Churning penalties are real money. Booking then cancelling repeatedly is penalised through ADMs (Agency Debit Memos), roughly 5,000 JPY per record on average. Essentially every carrier penalises it and a few are strict about it.

Double ticketing creates a refund obligation, which drags in a manual refund process.

And the thing that turns it from a bug into an operational risk: the window for handling it depends on business hours. The only way to limit damage is a human cancelling one of the two records before the airline acts. An incident overnight or at the weekend has nobody to act on it.

This is why a low-frequency incident still got prioritised: its expected cost is not proportional to how often it happens, but to when it happens.

3.2 Investigating something you cannot reproduce

Staging could not reproduce it, so the work became log archaeology:

  1. Ask for the complete list of duplicate ITN pairs per month — not a few samples. This is the step usually skipped: investigate only two pairs and the distribution of causes comes out wrong.
  2. For each pair, zgrep the ITN across all compressed backend logs on every instance for that day.
  3. From the first log line find the transaction key, then grep again by that key to recover both flows in full.
  4. Put the two flows side by side in columns and compare every timestamp.

3.3 Twenty-five milliseconds

Nothing mysterious is happening. Two requests read the same value before either manages to write.

3.4 There was a guard, and it was not one

// Read the status from the session
if (productInfo.getBookingStatus() != null) {
    if (BOOKING_PROCESSED.equals(productInfo.getBookingStatus())) {
        return FAILED;   // "Booking is in progress"
    }
    if (BOOKING_COMPLETED.equals(productInfo.getBookingStatus())) {
        return FAILED;   // "Booking is already completed"
    }
}

// ... only then write the status and start the booking thread
productInfo.setBookingStatus(BOOKING_PROCESSED);
sessionTable.update(...);
new BookingThread(...).start();

This is check-then-act, not mutual exclusion. It stops requests arriving late, after the first has finished writing. It does not stop requests arriving at the same time — and "at the same time" is the definition of the problem.

Two factors deepen the hole. Booking runs asynchronously and the GDS call takes seconds, so the window in which both requests see stale state is far wider than a database transaction. And the two requests land on different instances behind the load balancer, which makes every in-process lock — synchronized, a local lock, an in-memory cache — useless by structure rather than by configuration. The only place the two requests meet is the database.

3.5 The "Googlebot" turned out not to be Googlebot

Of nine duplicate pairs, seven carried a User-Agent containing the string google-bot, one was a suspected double-click, and one on the hotel side was never explained. From there the ticket named the cause "Googlebot crawling the booking page". The evidence inside the investigation file itself says otherwise.

First, the IPs do not belong to Google. Reverse DNS on those IPs resolves to Japanese consumer ISPs: mobile carriers, residential ADSL and fibre, MVNOs. Real Googlebot comes from Google's ranges and verifies by reverse DNS to googlebot.com.

Second, the UA is not Googlebot's UA. Real Googlebot sends:

Mozilla/5.0 (Linux; Android 6.0.1; Nexus 5X Build/MMB29P) AppleWebKit/537.36
(KHTML, like Gecko) Chrome/W.X.Y.Z Mobile Safari/537.36
(compatible; Googlebot/2.1; +http://www.google.com/bot.html)

The booking logs only contain the token google-bot — hyphenated, no bot.html URL, no Mozilla prefix. The investigation file noted this while discussing robots.txt: "per Google's documentation this is not an authentic google-bot, so it may not work". Correct observation — used to reject the robots.txt solution, not to revisit the diagnosis.

Third, and most decisive, it travels with the real user. One trace from October 2024, same endpoint, within the same second:

13:17:11,535  /reservation/book   ua=google-bot          remote ip 106.x.x.92
13:17:11,538  /reservation/book   ua=google-bot          → started_booking
13:17:11,563  /reservation/book   ua=Mozilla/5.0 (iPhone; CPU iPhone OS 17_6_1 …)
                                  referer=<3-D Secure authentication gateway>
                                  remote ip 106.x.x.9x
13:17:11,565  /reservation/book   ua=Mozilla/5.0 (iPhone …)  → started_booking
13:17:11,684  /reservation/book   ua=google-bot          → started_booking
13:17:11,810  /reservation/book   ua=google-bot
              WARNING BookingAsync has error status, but can continue this,
                      {'message': 'Booking is in progress', 'id': '101'}

Read the last three lines. The third google-bot request was caught by the guard — the backend returned exactly Booking is in progress. The web tier logged it at WARNING, with the phrase "but can continue this", and carried on.

The guard was not silent. It spoke. The caller was written to ignore what it said. A defensive check in the backend is worth exactly as much as the caller's handling of its result.

Putting the three pieces together: something on the user's own device or network replays the booking URL right after the 3-D Secure redirect returns, self-identifying as google-bot. That fits security software scanning a link, a browser extension, or a carrier proxy. It does not fit a search engine.

The "Googlebot" diagnosis led straight to a "block Googlebot" solution. The wrong name chose the patch.

The team saw the right solution in 2024. Optimistic locking was on the table, properly estimated, and rejected on 21 days against 2. The stated reasons were defensible at the time: option 4 removes every request carrying that UA, addressing most of the observed causes; options 2 and 3 were "relatively complex, hard to test on staging or production, and testing them would affect the live product".

That second reason is the one worth pausing on. Being unable to verify a solution had become the reason to reject the correct one. And the trap is the word most: option 4 eliminates seven of nine observed cases, so the metrics will look good. It does not eliminate the mechanism.

3.7 What shipped: two config files and one piece of JavaScript

if ($http_user_agent ~* (google-bot)) {
    return 403;
}

Placed in the config block for the booking paths, not globally. The team enumerated the URLs that need indexing — product detail pages, listings, lowest-fare calendars, search waiting pages — and confirmed none sit under /reservation. The second change disabled the booking button after the first click, across all three product modules and both desktop and mobile builds.

One consequence nobody wrote down: the pattern google-bot is hyphenated, so it does not match the real crawler's Googlebot/2.1. In practice the rule only blocks the fake UA — the SEO worry was unfounded, but correct by accident.

3.8 Reproducing a race with two lines of cURL

There was no load-testing tool for a flow involving 3-D Secure, so the reproduction was manual — and simple enough to be worth learning:

  1. Reach the confirm screen in a real browser, open DevTools, Copy as cURL to capture the live session's headers and cookies.
  2. Create a script with two cURL calls to /reservation/book using the same transaction key — one carrying user-agent: google-bot, one keeping the normal UA.
  3. Run it and read the status codes: 503 means blocked, 302 means through.
  4. Verify at the data layer, not just at the HTTP layer.

Step 4 is what gives the test its value. The HTTP code only tells you the request was blocked; only the table tells you whether a duplicate booking was created.

The checkpoints were: the button is disabled after the click; the UA is blocked on /reservation/* but allowed elsewhere, to avoid over-blocking; and authentic Googlebot is unaffected, tested by taking the official UA from Google's documentation, firing it at the URLs that need indexing, and cross-checking against real Googlebot log entries on those same URLs.

3.9 No acceptance testing possible — and what replaced it

Simulating the UA returned the expected 503, but the normal booking flow returned 500, and suspicion pointed at the interaction with 3-D Secure. Reproducing that on staging together with a real payment flow was not feasible.

The decision was to release and verify against production logs for one month, with two acceptance conditions: booking requests carrying that UA are blocked and countable in the logs, and real users' original bookings still complete normally.

The second condition matters as much as the first. A patch that also blocks real users makes the alerts stop just as effectively as a correct one — so the criteria must include positive evidence, not only the absence of errors.

4. What the first round left behind

Three things were untouched: check-then-act in the backend, not one line changed; /reservation/book still accepting GET, still a fetchable URL; and the caller still ignoring Booking is in progress.

What got fixed was the list of intruders anyone had been caught seeing at the door. That list is never complete.

5. Second round — same behaviour, different costume

Roughly a year and a half later: same passenger, same itinerary, two ITNs, two PNRs, 23 milliseconds apart.

5.1 This time there were nginx logs

The second investigation moved far faster — ticket opened on the 8th, root cause on the 11th — because it read the nginx logs rather than only application logs, and nginx records the HTTP method, which the application logs do not.

03:59:50   GET   /reservation/confirm   referer=…/input?is_three_d_secure_error=1
03:59:57   HEAD  /reservation/card_settle_error?…   referer: -
04:02:22   GET   /reservation/book_after_three_d_secure?…result=0…
04:02:22   HEAD  /reservation/book    referer: -   status 302   <- the copy
04:02:22   GET   /reservation/book    referer: -   status 302   <- the real one

The user had failed 3-D Secure once and retried — a long session with several returns, exactly the kind where things go wrong. A HEAD request appeared twice, both with no referer, both trailing a URL the browser had just encountered; the second targeted the booking endpoint itself. Its User-Agent was identical to the user's browser. There was no google-bot left to block. And again the two book requests landed on two different web instances.

The backend logs show both running to completion: same transaction id, same authentication id, and both returning success. The team's conclusion on the source: any layer in front — browser, proxy, CDN, load balancer — can emit a HEAD to probe; per the logs, most likely the browser or antivirus software.

5.2 First cause — HEAD is routed into the GET view

The framework routes HEAD into the same view as GET, which follows the HTTP spec: HEAD is GET without a body. But the spec also says both must be safe — no side effects. Here GET creates a booking, so HEAD creates a booking.

The trap worth remembering: HEAD is what browsers, security software, prefetchers, link previews and monitoring probes emit constantly, usually without anyone knowing. If your GET has side effects, so does your HEAD.

5.3 Second cause — the version that could not work

The most valuable detail of the whole incident: the system already had an optimistic-lock-like mechanism, using the row's update timestamp as the version.

UPDATE SESSION_INFO
   SET VALUE = /*value*/, UPD_PSN = /*updPsn*/, UPD_DT = /*updDt*/
 WHERE TRANSACTION_KEY = /*transactionKey*/
   AND date_format(UPD_DT, '%Y%m%d%H%i%s') = /*updDtAsVersion*/

Resolution: seconds. There was even code adding one second when the update timestamp equalled the current version, purely so the WHERE clause would not block itself. Meanwhile the two requests were 23 milliseconds apart. Both read the same UPD_DT, both saw Init, both conditional updates matched, both reported success.

A version whose resolution is coarser than the arrival rate of requests is not a version. It only looks like a lock. The mechanism existed, was carefully written and commented, and was structurally incapable of catching the thing it was built for.

5.4 Six options across two tiers

At the web tier there were two: declare HEAD as its own view in the routing config and have it refuse, or check the request method inside the booking handler. The first was chosen, because a constraint on method belongs to routing configuration, not to business code — in config it lives in one place and does not require remembering an extra branch in every new handler.

At the backend there were four:

#OptionTrade-offEst.
1Raise the timestamp to microsecond precisiondistinguishes finer, but only reduces the probability; the format change touches many places4 days
2Add a separate booking-status columneasier to follow, but must stay in sync with the status inside the blob, and old data needs backfilling6 days
3Add a VERSION columnindependent of datetime precision; every update must increment it5 days
4Add a string match against the JSON blobeasiest, only the update changes; cannot use an index, breaks if the JSON format changes3 days

The cheapest option was rejected, and rejected for the right reason. Option 4 costs three days and would work. It was rejected on two grounds that are both about the future rather than the present: it couples correctness to the serialization format of a blob column, and it cannot use an index. This is the kind of argument usually flattened by "but it works".

Option 1 exposes a very common way of thinking wrongly. Raising clock resolution from seconds to microseconds makes collisions far less likely — but not impossible. The investigation file says it outright: "it only reduces the chance of duplicate bookings; for requests identical down to the microsecond a duplicate booking is still possible". A correctness bug is not fixed by making it rarer.

5.5 The decision moves to the row count

At the web tier, two views on one endpoint, split by method:

config.add_view(
    context        = BookContext,
    view           = context_as_view,
    attr           = 'view_book_metadata',
    request_method = ('HEAD'),
)

config.add_view(
    context        = BookContext,
    view           = context_as_view,
    attr           = 'view_book',
    request_method = ('POST', 'GET'),
)
def view_book_metadata(self):
    logger.info('API booking with request method HEAD rejected')
    return HTTPMethodNotAllowed(headers={'Allow': 'GET, POST'})

Two small details done right: returning 405 with an Allow header, which is correct HTTP and tells the client what is permitted, and logging every rejection — that log line is precisely what makes monitoring-based acceptance possible when acceptance testing is not.

At the backend, the state transition turns from read-then-decide into a conditional write:

UPDATE SESSION_INFO
   SET VALUE   = /*value*/,
       UPD_DT  = /*updDt*/,
       VERSION = VERSION + 1
 WHERE TRANSACTION_KEY    = /*transactionKey*/
   AND AUTHENTICATION_KEY = /*authenticationKey*/
   AND VERSION            = /*version*/
int count = jdbcManager.updateBySqlFile(sqlFileName, sessionInfo).execute();
if (count != 1) {
    return error(...);        // lost the race
}

And the caller turns "lost the race" into a correct business answer:

sessionOut = setUpdateInformation(productInfo, request);
if (sessionOut.getErrorDetail() != null) {
    // update matched no rows -> re-read to see who won
    ProductInfo info = selectSessionInfo(...).getProductInfo();
    if (BOOKING_PROCESSED.equals(info.getBookingStatus())) {
        logger.error("Duplicate request booking detected. Booking is already progressing");
        return FAILED;
    }
}

This is the real turning point. The decision no longer lives in the value that was read; it lives in the number of rows updated. count != 1 is an atomic event adjudicated by the database. There is no gap between check and act, because they are the same statement.

5.6 The schema change was reviewed as its own artifact

ALTER TABLE <schema>.SESSION_INFO
  ADD COLUMN VERSION int DEFAULT 0 NOT NULL
  COMMENT 'Version number for optimistic locking'
  AFTER GOODS_VALUE;

DEFAULT 0 NOT NULL is what makes this migration backward compatible: every existing row — that is, every booking session open at deploy time — gets zero with no backfill, and the new statement matches them immediately.

The document also carried a before/after execution plan comparison. The old and new statements were explained side by side with execution times, and the result was the same access path on the same table: the added predicate did not change the query plan. This is the step usually skipped. Adding a condition to a statement that sits on the path of every transaction can sink performance, and proving it does not is far cheaper than discovering the opposite in production.

Third, the execution procedure was written down command by command: host, account, and the dated path of the SQL file.

This matrix is why a five-day patch drags a large release behind it: the regression surface is combinatorial, not linear.

The boundary between browser and web tier was tested for order and count, not merely for "a HEAD gets blocked": HEAD alone, GET alone, HEAD then GET, GET then HEAD, five HEADs then a GET, and both simultaneously — repeated across four product lines.

The boundary between web tier and backend is where the lock itself was tested: two concurrent requests with the same transaction key must produce one success and one failure that writes nothing; five concurrent requests must produce exactly one success; and — the sharpest technique in the whole round — a processing delay was injected into the first request before the second was sent. A 23 ms race cannot be reproduced reliably by clicking fast; widening the window turns a probabilistic event into a deterministic one.

End-to-end cases booked real itineraries across each combination and recorded the number of ITNs actually created as evidence, expecting exactly one every time. A small group verified the migration: a new session starts at zero, updates increment, and a transaction created before the ALTER reads as zero — the "what happens to sessions open at deploy time" question asked as a test case rather than discovered at 2 a.m. A final group regressed things outside the change's scope that nevertheless share the session table.

All thirty-nine passed.

5.9 The cost of fixing it late

The blast radius of the second fix: five repositories, four product lines, five brands plus metasearch, twelve screens, thirty-nine integration cases, seventeen unit tests and a schema change. Compare with the first round: two nginx config files and one piece of JavaScript.

Putting the guard in the right place after three years is far more expensive than putting it there at the start — not because the code is harder, but because the number of surfaces to re-verify has multiplied. The 21-day estimate rejected in 2024 was ultimately delivered with five days of effort; the difference is not in writing the code, it is in everything around it.

5.10 A way back, built on day one

Acceptance testing was again impossible, so the release conditions were written as three substitute legs: source review, because correctness here lives in the structure of a statement and is readable by eye — the WHERE VERSION = ? clause is either there or it is not; review of the integration scenarios, inspecting the cases instead of the results; and post-release monitoring.

The day after release, revert MRs were prepared for the modules. This is a standby path back, not a rollback that happened: the patch was not removed, the MRs simply sit ready to merge so that backing out takes minutes rather than requiring the change to be written backwards under incident pressure.

That is the fourth leg. When you cannot prove a patch correct before releasing it, what you prepare is a low cost of being wrong. The team could not raise confidence, so they lowered the cost of the bad scenario.

One detail done right: the database script is not on the revert list. Adding a column with a default is backward compatible — the old code does not read it, the new code needs it. Reverting the column would turn one rollback into two migrations.

7. Ten takeaways

  1. Check-then-act is not mutual exclusion. Reading a flag and then acting on it is only correct if nobody writes that flag in between. This guard lived for years, read as reasonable, and worked — for every request that arrived late. Its failure condition is invisible when the code is read sequentially.
  2. A version coarser than the arrival rate of requests is not a version. A timestamp as a version token looks entirely sensible until two events fall into the same rounding interval — and two duplicate requests are by definition two events close together. A monotonic integer has no resolution to lose.
  3. Making a correctness bug rarer is not fixing it. This is the line between "less frequent" and "impossible", and it is worth holding even when the weaker option costs a day less.
  4. Blocking by identity requires an infinite list; blocking by nature requires it once. A UA string is never a complete enumeration. The write points are finite: one row that both requests must pass through.
  5. The name you give the cause chooses the solution. Call it "Googlebot" and blocking Googlebot is the obvious patch. The contradicting evidence was already in the investigation file; nobody revisited the diagnosis because the alerts had stopped.
  6. A defensive check is worth what the caller does with its result. The backend returned Booking is in progress; the web tier logged a warning and carried on. That is worse than no guard, because the log made everyone believe protection existed.
  7. In a multi-instance system, the only place two requests meet is shared storage. Every in-process lock is meaningless structurally, not by configuration.
  8. "The alerts stopped" is not "it is fixed". Reasonable criteria, real data, wrong conclusion — and 2.5 years between fixing the symptom and learning that was all it was. The question worth asking in that review: if the cause we believe in is wrong, what would we see?
  9. Being unable to verify something is not a reason to choose the weaker solution — but it was. The deep options were rejected partly for being hard to test; six months later the same reason dropped acceptance testing for the patch that was chosen. When "hard to test" becomes a selection criterion, the system drifts toward patches that are easy to test rather than correct.
  10. When you cannot raise confidence, lower the cost of being wrong. Measurable log conditions, scenario review, monitoring, pre-built reverts. That is risk management, not risk denial.

If it were designed again

The strongest defence is not blocking the second request but making it harmless: an idempotency key generated per booking intent, sent with the request, with a unique constraint behind it. The second request — wherever it comes from, whatever method, whatever the gap — receives the first request's result rather than creating a new booking.

The optimistic lock works because both duplicates share the same session row. That assumption carries the entire patch and is written down nowhere. Two tabs, two devices, or a retry after session expiry would be invisible to it.

And at the design level: an action that creates a booking should not be a GET URL. It is one only because 3-D Secure returns the user by redirect. The correct pattern is redirecting to an idempotent confirmation endpoint which then performs the command — and then nothing can create a booking by fetching a URL.

8. Practice questions

  1. A booking endpoint has the guard if (status != PROCESSED) { book(); }. What does this guard stop and what does it not stop? Rewrite it correctly.
  2. Why can a HEAD request execute business logic? Which layer do you defend at, and why not inside the handler?
  3. You have an optimistic lock using UPDATE … WHERE updated_at = ? where updated_at is a second-resolution timestamp. Identify the failure condition and propose a fix.
  4. Given the four backend options in §5.4, estimated at 3, 4, 5 and 6 days, pick one and defend it. What is wrong with the 3-day option?
  5. Design idempotency for a booking-creation API. Where is the key generated, how long does it live, and what does a repeat request receive?
  6. You are adding a version column for optimistic locking to a table under live traffic. What is the rollout sequence such that no request fails during deploy? What about sessions that are already open?
  7. You cannot reproduce a race condition on staging. Design the acceptance criteria that would let you release.
  8. How do you write a deterministic integration test for a race with a 23 ms window?
  9. Your alert groups by session id and fires when the count exceeds one. What is that alert actually telling you about the cause?
  10. Your patch produced 33 days with no alerts and 117 recorded blocks. What does this evidence prove, and what does it not prove?

Company name, brand and site names, personal names, internal ticket ids, booking numbers, hosts, IPs, session tokens and internal URLs have been removed. People are referred to by role. Modules are named after their function. Code, logs and SQL are shortened, de-identified excerpts that keep the logic intact.

Industry vocabulary — GDS, PNR, ITN, churning and ADMs, 3-D Secure, HEAD, optimistic locking, and generic table and column names — is kept, because it is what makes the account readable and it identifies no organisation.
