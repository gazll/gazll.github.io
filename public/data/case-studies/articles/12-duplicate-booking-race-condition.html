A booking system created two airline records for one passenger and flight, only milliseconds apart. The first investigation blamed a crawler and blocked its User-Agent. Alerts stopped for two and a half years. Then the same defect returned as a HEAD request.

The real bug never lived in the request's identity. It lived in a check-then-act window shared by every request. This incident shows how a plausible diagnosis can produce convincing metrics while leaving the violated invariant untouched.

1. The invariant and the unsafe boundary

The OTA had a Python web tier behind a load balancer and a Java booking backend. The backend stored booking state in SESSION_INFO and called a GDS to create the airline PNR and the OTA itinerary number, or ITN. One booking intent must create exactly one PNR and one ITN.

Session state moved through Init → Booking → Complete or Error. The browser called /reservation/book; the backend read Init, changed it to Booking, then started an asynchronous GDS call.

The endpoint accepted both POST and GET because a 3-D Secure payment redirect returned through a GET URL. That made a state-changing action fetchable by browsers, link scanners and security software. Method filtering could reduce accidental calls, but correctness still had to survive duplicate requests from any source.

2. What the evidence actually said

A scheduled query—not an exception or customer report—detected the incident:

SELECT session_id, COUNT(itn_no)
FROM itinerary_tracking
WHERE tracked_at >= <15 minutes ago>
GROUP BY session_id
HAVING COUNT(itn_no) > 1;

The grouping key matters. The alert did not mean “the same passenger booked twice.” It meant one session produced multiple ITNs, a strong signal of duplicate execution inside one booking intent.

The incidents were rare—usually zero to two per month—but expensive. Airlines may cancel both duplicate reservations, churning can trigger Agency Debit Memos, and double ticketing creates manual refunds. Overnight incidents were worse because intervention depended on business hours.

Because staging could not reproduce the race, the team reconstructed both requests from compressed logs across every backend instance, joined them by transaction key, and placed their timelines side by side. That revealed the useful evidence: the requests arrived 2 ms apart and both crossed a 25 ms read/write window.

3. The guard was check-then-act

if (BOOKING_PROCESSED.equals(productInfo.getBookingStatus())) {
    return FAILED;
}
if (BOOKING_COMPLETED.equals(productInfo.getBookingStatus())) {
    return FAILED;
}

productInfo.setBookingStatus(BOOKING_PROCESSED);
sessionTable.update(...);
new BookingThread(...).start();

This guard stopped requests that arrived after the status update. It could not stop two requests that read before either update committed. The code looked sequential; production execution was not.

The requests also landed on different application instances. A Java synchronized block or local cache lock could never protect the invariant. The database row was the only shared point through which both requests passed.

4. A convincing false fix

Seven of nine investigated pairs contained the token google-bot in their User-Agent. The incident was named “Googlebot crawling the booking page,” and the proposed fix followed the name.

The same evidence contradicted that diagnosis. The source IPs belonged to consumer networks, not verified Google ranges. The User-Agent did not match Google's documented crawler format. Most importantly, it appeared beside the real user's mobile request immediately after the 3-D Secure redirect. A later duplicate was even rejected by the backend guard, but the web tier logged the error and continued.

The released patch blocked that User-Agent at nginx and added client-side suppression. Monitoring then showed 117 blocked requests over 33 days and zero duplicate alerts. Those numbers were real, but proved only that one observed trigger had been removed. They did not prove that booking creation had become atomic.

This is the diagnostic trap: when the cause is named by appearance—“Googlebot”—the solution targets appearance. A correctness fix must target the invariant every duplicate must cross.

5. Same mechanism, different costume

Two and a half years later, two requests arrived 23 ms apart with the user's normal browser User-Agent. This time the duplicate was a HEAD request. Framework routing treated HEAD like GET, so the metadata probe executed the booking handler.

The costume changed from a suspicious User-Agent to an unexpected HTTP method. The underlying mechanism was identical: both requests read the same session state, passed the same guard and started separate bookings.

The existing optimistic-lock token also could not adjudicate the race. It reused an update timestamp with one-second resolution. Requests 23 ms apart observed the same rounded value, so both updates matched. Increasing precision would make collision less likely, not impossible; probability reduction is not a correctness guarantee.

6. Move the decision into one atomic write

The permanent fix introduced an integer VERSION column. Every session update incremented it, and the booking transition matched the version previously read:

UPDATE SESSION_INFO
   SET VALUE   = ?,
       UPD_DT  = ?,
       VERSION = VERSION + 1
 WHERE TRANSACTION_KEY    = ?
   AND AUTHENTICATION_KEY = ?
   AND VERSION            = ?;
int count = jdbcManager.updateBySqlFile(sqlFileName, sessionInfo).execute();
if (count != 1) {
    return FAILED; // another request won the transition
}

Now check and act are one statement. Two contenders may read the same version, but only one can update it. The winner changes the version; the loser's predicate matches zero rows. The affected-row count is the atomic decision.

The web tier separately routed HEAD to a handler returning 405 Method Not Allowed with Allow: GET, POST. That removed a known accidental trigger and improved HTTP semantics. It was defense in depth, not the concurrency guarantee.

7. Verify the invariant, rollout and rollback

The schema migration used VERSION INT DEFAULT 0 NOT NULL, so existing live sessions received a valid token without a separate backfill. Execution plans before and after the predicate were compared to confirm the hot update kept the same access path.

Tests asserted outcomes, not implementation details: two concurrent booking calls produced one success and one failure; five produced exactly one success; ordinary updates incremented the version; and HEAD never reached the booking API. A controlled delay widened the 23 ms window, turning a probabilistic race into a deterministic integration test.

The change crossed five repositories, four product lines, twelve screens and a shared session table. The team ran 17 unit tests and 39 integration scenarios, monitored rejection and booking signals after release, and prepared revert changes in advance. The additive database column stayed during rollback because old code safely ignored it.

8. What this fix guarantees—and what it does not

The version check works because both duplicate requests share one session row. Duplicates from two sessions, devices or expired sessions can bypass that boundary. The stronger API design is an idempotency key created per booking intent and protected by a unique constraint; every retry then returns the original outcome instead of creating another booking.

A state-changing command should also not be hidden behind a fetchable GET. The 3-D Secure redirect can land on an idempotent confirmation endpoint, which then submits or resumes the booking command under the same intent key.

The technical lesson is compact: identify the invariant, find the shared serialization point, and let one atomic write choose the winner. Edge filters reduce noise. They cannot replace database-enforced correctness.

9. Review checklist

  1. Check-then-act is not mutual exclusion. Ask what can write between the read and the action.
  2. A timestamp is a poor version token. Its resolution and clock semantics create collisions a monotonic integer avoids.
  3. Quiet alerts do not prove the invariant. Measure both rejected duplicates and successful normal transitions.
  4. Multi-instance locks need shared arbitration. Local synchronization cannot protect work routed to another process.
  5. Test races deterministically. Inject a barrier or delay, then assert exactly one committed side effect.
  6. Record the boundary. Optimistic locking protects one row; idempotency protects one business intent.
